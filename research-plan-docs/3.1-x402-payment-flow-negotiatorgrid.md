## 1. Protocol Versions: V1 vs V2

x402 has two protocol versions. **Kite currently uses V1** (`x402Version: 1` with the `gokite-aa` scheme). The x402 foundation SDK (V2) uses `x402Version: 2`. This is critical for NegotiatorGrid — we must support the version Kite uses.

| Feature | V1 | V2 |
|---------|----|----|
| Version field | `x402Version: 1` | `x402Version: 2` |
| Amount field | `maxAmountRequired` | `amount` |
| Resource info | Inside each `accepts` entry | Top-level `resource` object |
| Network format | Loose string (e.g., `"kite-testnet"`) | CAIP-2 strict (e.g., `"eip155:84532"`) |
| Extensions | Not present | `extensions` field on PaymentRequired and PaymentPayload |

**Source**: [x402 core schemas — GitHub](https://github.com/x402-foundation/x402/blob/main/typescript/packages/core/src/schemas/index.ts)

## 2. Complete 7-Step Payment Flow

### Step 1: Client sends GET/POST to resource

```
GET /api/weather?location=San+Francisco HTTP/1.1
Host: x402.dev.gokite.ai
```

No special headers required. Standard HTTP request.

### Step 2: Server returns 402 Payment Required

**HTTP Response:**
```
HTTP/1.1 402 Payment Required
Content-Type: application/json
```

**Response Header (V2 standard):**
```
PAYMENT-REQUIRED: <base64-encoded PaymentRequired JSON>
```

**Kite V1 — returns JSON body directly (no base64 header):**
```json
{
  "x402Version": 1,
  "error": "X-PAYMENT header is required",
  "accepts": [
    {
      "scheme": "gokite-aa",
      "network": "kite-testnet",
      "maxAmountRequired": "1000000000000000000",
      "resource": "https://localhost:8099/api/weather",
      "description": "Weather API - Public endpoint with query params",
      "mimeType": "application/json",
      "outputSchema": { ... },

      "maxTimeoutSeconds": 300,
      "asset": "0x0fF5393387ad2f9f691FD6Fd28e07E3969e27e63",
      "extra": null,
      "merchantName": "Weather Service"
    }
  ]
}
```


### Step 3: PaymentRequirements Object — Full Schema

#### V2 Schema (Zod from source code):
```typescript
// PaymentRequirementsV2Schema
{
  scheme: string,           // "exact" | "upto" | "gokite-aa"
  network: string,          // CAIP-2 format: "eip155:84532", or "kite-testnet" (V1)
  amount: string,           // Atomic units: "10000" = $0.01 USDC (6 decimals)
  asset: string,            // Token contract address
  payTo: string,            // Seller's wallet address
  maxTimeoutSeconds: number, // Positive integer, payment validity window
  extra: Record<string, unknown> | null  // ← EXTENSIBLE FIELD
}
```

#### V1 Schema (Kite uses this):
```typescript
// PaymentRequirementsV1Schema
{
  scheme: string,              // "gokite-aa"
  network: string,             // "kite-testnet"
  maxAmountRequired: string,   // Amount in wei
  resource: string,            // URL string
  description: string,         // Human-readable
  mimeType?: string,
  outputSchema?: object | null,
  payTo: string,
  maxTimeoutSeconds: number,
  asset: string,
  extra: Record<string, unknown> | null  // ← EXTENSIBLE FIELD
}
```

#### V2 PaymentRequired (full 402 response envelope):
```typescript
{
  x402Version: 2,
  error?: string,
  resource: {
    url: string,
    description?: string,
    mimeType?: string
  },
  accepts: PaymentRequirementsV2[],   // Array, min 1 element
  extensions?: Record<string, unknown>  // ← EXTENSIBLE FIELD
}
```

**Source**: [x402 TypeScript core schemas](https://github.com/x402-foundation/x402/blob/main/typescript/packages/core/src/schemas/index.ts), [x402 TypeScript payment types](https://github.com/x402-foundation/x402/blob/main/typescript/packages/core/src/types/payments.ts)

### ⭐ Can We Add a Custom `deal_hash` Field?

**YES — via the `extra` field.**

The `extra` field on `PaymentRequirements` is typed as `Record<string, unknown> | null` (in TypeScript) / `map[string]interface{}` (in Go). It is explicitly designed for scheme-specific and custom data. The Zod validation passes through any key-value pairs.

**NegotiatorGrid approach — embed `deal_hash` in `extra`:**
```json
{
  "scheme": "exact",
  "network": "eip155:84532",
  "amount": "15000",
  "asset": "0x036CbD53842c5426634e7929541eC2318f3dCF7e",
  "payTo": "0xSellerAddress",
  "maxTimeoutSeconds": 60,
  "extra": {
    "name": "USDC",
    "version": "2",
    "deal_hash": "0xabc123...def456",
    "negotiation_round": 5,
    "negotiation_protocol": "negotiatorgrid-v1"
  }
}
```

**Alternatively, use the top-level `extensions` field on PaymentRequired (V2 only):**
```json
{
  "x402Version": 2,
  "resource": { "url": "...", "description": "..." },
  "accepts": [...],
  "extensions": {
    "negotiatorgrid": {
      "deal_hash": "0xabc123...def456",
      "final_price": "15000",
      "rounds": 5,
      "strategy": "time_dependent_concession"
    }
  }
}
```

Both `extra` and `extensions` survive the x402 SDK pipeline — the facilitator does not strip unknown fields from these maps. The `extra` field is available in both V1 and V2; `extensions` is V2 only.

**Source**: [x402 core schemas](https://github.com/x402-foundation/x402/blob/main/typescript/packages/core/src/schemas/index.ts) — `OptionalAny = z.record(z.unknown()).optional().nullable()`

### Step 4: Client Constructs Payment — EIP-712 Signing

The client selects one entry from the `accepts` array and constructs a `PaymentPayload`.

#### For `exact` scheme with EIP-3009 tokens (USDC):

The client signs an EIP-712 `TransferWithAuthorization` message:

**EIP-712 Domain:**
```typescript
{
  name: "USD Coin",       // Token name (from extra.name)
  version: "2",           // Token version (from extra.version)
  chainId: 84532,         // From network (CAIP-2 reference)
  verifyingContract: "0x036CbD53842c5426634e7929541eC2318f3dCF7e"  // asset address
}
```

**EIP-712 Types:**
```typescript
{
  TransferWithAuthorization: [
    { name: "from", type: "address" },
    { name: "to", type: "address" },
    { name: "value", type: "uint256" },
    { name: "validAfter", type: "uint256" },
    { name: "validBefore", type: "uint256" },
    { name: "nonce", type: "bytes32" }
  ]
}
```

**EIP-712 Message:**
```typescript
{
  from: "0xBuyerAddress",     // Client's wallet
  to: "0xSellerAddress",      // payTo from PaymentRequirements
  value: "10000",             // amount from PaymentRequirements
  validAfter: "0",            // Unix timestamp — payment not valid before
  validBefore: "1712700000",  // Unix timestamp — now + maxTimeoutSeconds
  nonce: "0x<random-32-bytes>"  // Random bytes32 for replay protection
}
```

**Signing:** `keccak256("\x19\x01" + domainSeparator + structHash)` → signed with client's private key.

**Source**: [x402 EVM eip712.go](https://github.com/x402-foundation/x402/blob/main/go/mechanisms/evm/eip712.go)

#### For `exact` scheme with Permit2 (any ERC-20):

**EIP-712 Domain:**
```typescript
{
  name: "Permit2",
  chainId: 84532,
  verifyingContract: "0x000000000022D473030F116dDEE9F6B43aC78BA3"  // Canonical Permit2
}
```

**EIP-712 Types:**
```typescript
{
  PermitWitnessTransferFrom: [
    { name: "permitted", type: "TokenPermissions" },
    { name: "spender", type: "address" },
    { name: "nonce", type: "uint256" },
    { name: "deadline", type: "uint256" },
    { name: "witness", type: "Witness" }
  ],
  TokenPermissions: [
    { name: "token", type: "address" },
    { name: "amount", type: "uint256" }
  ],
  Witness: [
    { name: "to", type: "address" },
    { name: "validAfter", type: "uint256" }
  ]
}
```

**Source**: [x402 EVM constants.go](https://github.com/x402-foundation/x402/blob/main/go/mechanisms/evm/constants.go)

#### Constructed PaymentPayload (V2):
```typescript
{
  x402Version: 2,
  resource: { url: "https://api.example.com/premium-data" },
  accepted: {
    // The selected PaymentRequirements entry (echoed back)
    scheme: "exact",
    network: "eip155:84532",
    amount: "10000",
    asset: "0x036CbD53842c5426634e7929541eC2318f3dCF7e",
    payTo: "0xSellerAddress",
    maxTimeoutSeconds: 60,
    extra: { "name": "USDC", "version": "2", "deal_hash": "0x..." }
  },
  payload: {
    // EIP-3009 variant:
    signature: "0x<65-byte-signature>",
    authorization: {
      from: "0xBuyerAddress",
      to: "0xSellerAddress",
      value: "10000",
      validAfter: "0",
      validBefore: "1712700000",
      nonce: "0x<random-32-bytes>"
    }
  },
  extensions: {}
}
```

**V1 PaymentPayload (simpler):**
```typescript
{
  x402Version: 1,
  scheme: "exact",
  network: "base-sepolia",
  payload: {
    signature: "0x...",
    authorization: { from, to, value, validAfter, validBefore, nonce }
  }
}
```

**Source**: [x402 TypeScript EVM types](https://github.com/x402-foundation/x402/blob/main/typescript/packages/mechanisms/evm/src/types.ts)

On successful settlement:

## 3. Dynamic Pricing — Critical for NegotiatorGrid

### Can the server dynamically set the price in PAYMENT-REQUIRED?

**YES — the price is NOT static.** This is the most important finding for NegotiatorGrid.

#### Evidence 1: Price is set at middleware configuration time, not compile time

The x402 middleware takes a `RouteConfig` object:
```typescript
{
  "GET /weather": {
    accepts: [{
      scheme: "exact",
      price: "$0.001",   // ← This is a configuration value
      network: "eip155:84532",
      payTo: evmAddress,
    }]
  }
}
```

But the price is converted to `amount` in the `PaymentRequirements` only when the 402 response is generated. The server controls this value.

**Source**: [x402 Quickstart for Sellers](https://docs.x402.org/getting-started/quickstart-for-sellers)

#### Evidence 2: The `upto` scheme proves dynamic pricing is a first-class concept

The `upto` scheme explicitly supports variable pricing:
- Client authorizes a **maximum** amount
- Server settles only what was **actually used** via `setSettlementOverrides(res, { amount: "..." })`
- Supports raw atomic units, percentages, or dollar values

```typescript
setSettlementOverrides(res, { amount: String(actualUsage) });
```

**Source**: [x402 Quickstart for Sellers — upto scheme](https://docs.x402.org/getting-started/quickstart-for-sellers)

#### Evidence 3: The middleware does NOT enforce price immutability

Looking at `server.go`, the `x402ResourceServer` stores scheme registrations and facilitator clients, but the actual `PaymentRequired` response is constructed per-request. There is no mechanism that prevents generating different `amount` values per request.

**Source**: [x402 Go server.go](https://github.com/x402-foundation/x402/blob/main/go/server.go)

#### Evidence 4: Academic validation

The CPMM paper (March 2026) explicitly describes "Capability-Priced Micro-Markets" where prices are the output of a negotiation process, using HTTP 402/x402 as the payment mechanism. It formalizes "agent interactions as a repeated bilateral game with incomplete information" and demonstrates convergence to a Radner equilibrium.

**Source**: [Capability-Priced Micro-Markets (CPMM), Huang et al., March 2026](https://www.semanticscholar.org/paper/3bb6f801c96fe9c90eeed45cdc165fe02492c776)

### NegotiatorGrid Integration Pattern

```
┌──────────┐     ┌───────────────────┐     ┌──────────────┐     ┌─────────────┐
│  Buyer   │     │  NegotiatorGrid   │     │  Seller      │     │ Facilitator │
│  Agent   │     │  (Negotiation     │     │  Service     │     │ (Pieverse/  │
│          │     │   Layer)          │     │              │     │  CDP)       │
└────┬─────┘     └────────┬──────────┘     └──────┬───────┘     └──────┬──────┘
     │                    │                       │                    │
     │ 1. Request resource│                       │                    │
     ├───────────────────►│                       │                    │
     │                    │ 2. Negotiate price    │                    │
     │                    │◄─────────────────────►│                    │
     │                    │  (multiple rounds)    │                    │
     │                    │  Result: agreed_price │                    │
     │                    │  + deal_hash          │                    │
     │                    │                       │                    │
     │ 3. Return 402 with │negotiated price       │                    │
     │◄───────────────────┤                       │                    │
     │  amount=agreed_price                       │                    │
     │  extra.deal_hash=0x...                     │                    │
     │                    │                       │                    │
     │ 4. Sign EIP-712 payment                    │                    │
     │ (transferWithAuthorization)                │                    │
     │                    │                       │                    │
     │ 5. Retry with PAYMENT-SIGNATURE            │                    │
     ├───────────────────►│──────────────────────►│                    │
     │                    │                       │ 6. Verify + Settle │
     │                    │                       ├───────────────────►│
     │                    │                       │    tx_hash         │
     │                    │                       │◄───────────────────┤
     │ 7. 200 OK + resource                       │                    │
     │◄──────────────────────────────────────────┤                    │
     │  PAYMENT-RESPONSE: {tx_hash, ...}          │                    │
```

### Implementation Approach for NegotiatorGrid

**Option A: Pre-402 Negotiation (Recommended)**

1. Buyer agent discovers seller endpoint
2. NegotiatorGrid negotiation protocol runs (A2A or custom)
3. Negotiation produces `agreed_price` + `deal_hash` (keccak256 of deal terms)
4. Seller dynamically generates 402 response with `amount = agreed_price`
5. `extra.deal_hash` links the 402 to the negotiation
6. Standard x402 payment flow executes at the agreed price

**Option B: upto Scheme Approach**

1. Seller advertises `scheme: "upto"` with `price: "$1.00"` (max)
2. Buyer signs authorization for up to $1.00
3. NegotiatorGrid negotiation occurs
4. Seller calls `setSettlementOverrides(res, { amount: negotiated_price })`
5. Client only pays the negotiated amount

**Option B has a drawback**: the buyer must authorize the maximum upfront before knowing the negotiated price. Option A is cleaner — the buyer signs only the agreed amount.

### Kite uses V1 — NegotiatorGrid implications

Kite's weather demo uses `x402Version: 1` with the `gokite-aa` scheme. This means:
- Amount field = `maxAmountRequired` (not `amount`)
- No top-level `resource` object — it's inside each `accepts` entry

- Header name is `X-PAYMENT` (not `PAYMENT-SIGNATURE`)

**Recommendation**: NegotiatorGrid should support both V1 and V2. Use V1 for Kite testnet demo, V2 for standard x402 facilitators. The `extra` field works in both.

## 5. Payment Schemes Summary

### `exact` — Fixed price (default)
- Client pays the exact advertised price
- Works across all networks (EVM, SVM, Stellar, Aptos)
- EIP-3009 (`transferWithAuthorization`) for USDC-like tokens
- Permit2 fallback for any ERC-20

### `upto` — Usage-based billing
- Client authorizes a maximum; server settles actual usage
- EVM only (Permit2-based)
- TypeScript and Go SDKs only (no Python yet)
- Server calls `setSettlementOverrides(res, { amount })` before responding

### `gokite-aa` — Kite Account Abstraction
- Kite-specific scheme
- V1 protocol
- Used with Kite Agent Passport

## 6. Security Considerations for NegotiatorGrid

| Threat | Mitigation |
|--------|------------|
| Replay attacks | Nonce-based: each EIP-3009 nonce is `bytes32` (random), each Permit2 nonce is `uint256` |
| Time-bounded | `validAfter` / `validBefore` (EIP-3009) or `deadline` (Permit2) |
| Price manipulation | `deal_hash` in `extra` cryptographically links 402 amount to negotiation outcome |
| Facilitator trust | On-chain verification possible; tx hash in `SettleResponse` can be verified on-chain |
| Duplicate settlement (Solana) | Built-in `SettlementCache` in SVM mechanism (120s TTL) |
| Cross-chain replay | EIP-712 domain separator includes `chainId` and `verifyingContract` |

**Source**: [Avalanche x402 Security](https://build.avax.network/academy/blockchain/x402-payment-infrastructure/03-technical-architecture/07-security-considerations), [x402 Facilitator docs](https://docs.x402.org/core-concepts/facilitator)
