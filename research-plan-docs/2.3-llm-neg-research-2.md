### 1. The 110+ Negotiation Task Benchmark

AgenticPay comprises **111 tasks** across **8 multi-agent configurations**, built from a factorial combination of scenario × market structure. The benchmark is organized along two axes:

| **Financial Assets** | Luxury Watch, Business Acquisition |

Product values range from **\$350 to \$120,000**, deliberately spanning consumer and enterprise price ranges.

Tasks scale along three orthogonal dimensions — number of buyers (B), number of sellers (S), and product set size (P):

| Category Code | Structure | Example |
|---|---|---|

| **MBMPMS** | Multi-buyer, multi-product, multi-seller | Full market (many-to-many) |

The benchmark splits into **31 basic tasks** (testing core mechanics with synthetic products) and **80 realistic tasks** (instantiating all 10 business scenarios under varied market configurations).

**Interaction modes:** Each task category supports both *parallel* interaction (agent reasons over multiple simultaneous negotiations) and *sequential* interaction (agent decides whether to continue, switch, or commit), doubling the effective behavioral complexity.

### 2. Structured Action Extraction Layer

AgenticPay uses a **prompt-enforced structured token format** combined with a **regex-based parser** to extract numeric bids and deal decisions from free-form LLM text. This is not a separate learned module — it is a deterministic, rule-based extraction pipeline baked into each environment's `step()` method.

#### Format Enforcement (System Prompt)

Every agent's system prompt contains a hard constraint:

> "CRITICAL: In each turn, you MUST make exactly ONE price offer for the product using the format:  
> `### BUYER_PRICE($X) ###`  
> This specific format is required for the system to correctly extract your offer price."

Sellers use an analogous `### SELLER_PRICE($X) ###` token. Deal acceptance is signaled by the exact string `MAKE_DEAL` anywhere in the response.

> "If you decide to accept the deal and want to make a transaction, you MUST include the exact phrase `MAKE_DEAL` in your response."

#### Parser Implementation (`_extract_price` method)

The environment's `_extract_price(text: str) → Optional[float]` method applies a three-priority regex cascade:

```
Priority 1 (preferred):
  r'###\s*(?:BUYER_PRICE|SELLER_PRICE)\s*\(\$[\d,]+\.?\d*\)\s*###'
  → Matches ### BUYER_PRICE($8,750) ###

Priority 2 (backward compatibility):
  r'###\s*\$[\d,]+\.?\d*\s*###'
  → Matches ### $100.50 ###

Priority 3 (fallback):
  \$[\d,]+\.?\d*         → plain dollar amounts
  [\d,]+\.?\d* dollars?  → "100 dollars"
  [\d,]+\.?\d* USD       → "100 USD"
  price.*?[\d,]+         → "price 100"
  offer.*?[\d,]+         → "offer 100"
```

The parser always takes the **last** match in the string (to capture the most recent offer when an LLM revises mid-response), strips commas before float conversion, and rejects non-positive values. When a model fails to produce a parseable price, the round is counted toward `overflow_rate` (prices outside the bargaining zone) or produces no action update.

#### Agreement Detection (`_check_agreement` method)

A deal is reached when either:
1. `|buyer_price - seller_price| ≤ price_tolerance` (default: 1.0), or  
2. `seller_price ≤ buyer_price` (seller accepts buyer's offer).

Both conditions require that both prices have been set in the current round. Agreement is *also* triggered immediately if either party emits `MAKE_DEAL`.

Termination also occurs via timeout (round count exceeds `max_rounds`, default 20) or feasibility violation (agreed price outside the bargaining zone `[pmin, pmax]`).

Additionally, both buyer and seller agents are required to perform **mental modeling** before each response — a chain-of-thought structured block enclosed in `<mental_model>` tags estimating the opponent's reservation price, their strategy, and the agent's own strategy — though this is not parsed by the extractor; it is purely for reasoning scaffolding.

*Source: [GitHub: agenticpay/envs/single_buyer_product_seller/Task1_basic_price_negotiation.py](https://github.com/SafeRL-Lab/AgenticPay/blob/main/agenticpay/envs/single_buyer_product_seller/Task1_basic_price_negotiation.py); [agenticpay/agents/buyer_agent.py](https://github.com/SafeRL-Lab/AgenticPay/blob/main/agenticpay/agents/buyer_agent.py)*

### 4. Welfare Metrics: Social Surplus, Individual Utility, Pareto Efficiency

AgenticPay formalizes welfare measurement through three complementary score functions, all normalized within the **bargaining zone** `Z = pmax − pmin`.

#### Score Calculation (Algorithm 1 from the paper)

Given final price `p`, buyer max price `pmax`, seller min price `pmin`, deal round `t`, max rounds `T`, discount factor `γ`:

```
Z = pmax - pmin                         # Bargaining zone width
d = γ^(t-1)                             # Efficiency discount (penalizes late deals)

if pmin ≤ p ≤ pmax:
    rb = (pmax - p) / Z                 # Buyer utility ∈ [0,1]  (social surplus share)
    rs = (p - pmin) / Z                 # Seller utility ∈ [0,1] (social surplus share)
    Q  = 4 * rb * rs                    # Quality term ∈ [0,1]   (Pareto proxy, peaks at rb=rs=0.5)

    GlobalScore = d * (D + Q*W + E)     # Social surplus metric
    BuyerScore  = d * (D + rb*W + E)    # Individual buyer utility
    SellerScore = d * (D + rs*W + E)    # Individual seller utility
else:
    d = γ^(T-1)                         # Maximum-penalty discount
    GlobalScore = BuyerScore = SellerScore = -F * (1 - d)  # Failure penalty
```

Benchmark parameters: `D=30` (deal completion bonus), `W=55` (quality bonus, `W > D` intentionally prioritizes deal quality over mere agreement), `E=15` (efficiency bonus), `γ=0.99`, `F=15` (failure penalty).

#### Conceptual Mapping of Each Metric

**Social Surplus (GlobalScore):** The quality term `Q = 4·rb·rs` is the product of both parties' normalized utilities, scaled to peak at 1.0 when surplus is split equally (50/50). This is equivalent to maximizing the **Nash product** in classical bargaining theory — it rewards outcomes on the Pareto frontier that are also equitable. A deal struck at the exact midpoint of the bargaining zone achieves `Q = 1.0`.

**Individual Utility (BuyerScore / SellerScore):** Each party's score is proportional to their fractional share of the surplus. BuyerScore rises as price falls toward `pmin`; SellerScore rises as price rises toward `pmax`. These are zero-sum within an agreement and capture distributive efficiency.

**Pareto Efficiency:** The framework implicitly proxies Pareto efficiency through the GlobalScore's symmetry requirement. A deal that maximizes `Q = 4·rb·rs` subject to `rb + rs = 1` is Pareto-optimal — no reallocation improves one party without harming the other. Failed negotiations (timeout/overflow) receive negative scores, strongly penalizing deadlock (a Pareto-dominated outcome).

**Efficiency discount `d = γ^(t-1)`:** Rewards earlier agreements. With `γ=0.99` and `T=20`, a round-1 deal receives full bonus (`d≈1`), while a round-20 deal receives approximately `d = 0.99^19 ≈ 0.827` — an ~17% efficiency penalty.

*Source: [arXiv:2602.06008](https://arxiv.org/abs/2602.06008), Section 4.4, Algorithm 1*

### 5. Mapping Welfare Metrics to On-Chain Attestation

The AgenticPay welfare metrics have a natural structural correspondence to on-chain attestation in blockchain negotiation systems. The following analysis connects the paper's formalism to attestation primitives.

#### Feasibility for On-Chain Attestation

| AgenticPay Metric | On-Chain Analogue | Attestation Approach |
|---|---|---|
| **BuyerScore / SellerScore** | Individual utility per party | Each party signs a statement: "I received utility `rs=0.73` in deal at price `p=$110`." Verified against committed `pmin`/`pmax` via ZK proof (hiding reservation values). |
| **GlobalScore (social surplus)** | Joint welfare outcome | Smart contract computes `Q = 4·rb·rs` from attested individual utilities; no reservation prices need to be revealed if parties attest their own `r` values and their sum equals 1. |
| **Pareto efficiency flag** | Outcome validity | Contract checks `pmin ≤ p ≤ pmax` (agreed price in bargaining zone); this is the on-chain feasibility condition, equivalent to a Pareto-improvement over no-deal. |
| **Avg. rounds / efficiency discount** | Process quality | Round count `t` is trivially verifiable on-chain (block timestamps or message count); `d = γ^(t-1)` can be computed deterministically. |

#### Key Design Challenges

1. **Private reservation prices:** `pmin` and `pmax` are private and must not be on-chain in plaintext. Attestation requires either (a) ZK proofs that `p ∈ [pmin, pmax]` without revealing the bounds, or (b) a trusted third party (TEE) that computes and attests scores without exposing reservation values.

2. **LLM output authenticity:** On-chain systems would need the negotiation transcript hash committed on-chain or generated inside a verifiable compute environment (e.g., dstack/TDX) for the welfare scores to be trustless.

3. **Score composability:** Because `GlobalScore`, `BuyerScore`, and `SellerScore` are all derived from the same normalized utility pair `(rb, rs)`, a single compact attestation tuple `(p, pmax, pmin, t)` — with reservation prices revealed to the contract under ZK — suffices to compute all three. This makes the metric set natively composable for multi-party settlement contracts.

4. **Pareto proof without full transcript:** The core on-chain claim is simply: "deal was reached at price `p`, both parties had their constraints satisfied." This is a minimal attestation — essentially equivalent to a signed trade receipt with a welfare label.

*Analysis extrapolated from [arXiv:2602.06008](https://arxiv.org/abs/2602.06008), Section 4.4 and game-theoretic foundations cited therein (Myerson & Satterthwaite 1983, Rubinstein 1985)*

### 1. LP-Solver-Based Offer Optimization

ASTRA formulates offer generation as a **linear programming problem**, executed as a Python tool call from within the LLM pipeline. This is the paper's central technical contribution: replacing LLM guesswork on optimal offers with provably optimal combinatorial allocation.

#### The LP Formulation

In the CaSiNo MIB domain, items (food X, water Y, firewood Z) are available in quantities 0–3 each. The agent seeks an allocation `(X, Y, Z)` maximizing a weighted combination of its own score and its partner's score:

```python
def solve_LP(max_point, lambda, agents_value, partner_value):
    """
    Args:
        max_point: upper bound on agent's own score (Smax)
        lambda: self-interest weight ∈ [0,1]; 1 = purely self-interested
        agents_value: dict {food, water, firewood} — agent's item values
        partner_value: dict {food, water, firewood} — inferred partner item values (IPP)
    """
    X = LpVariable("X", 0, 3, cat='Integer')   # food agent gets
    Y = LpVariable("Y", 0, 3, cat='Integer')   # water agent gets
    Z = LpVariable("Z", 0, 3, cat='Integer')   # firewood agent gets

    # Objective: maximize weighted sum of own + partner's score
    agent_score  = A_F*X + A_W*Y + A_FW*Z
    partner_score = B_F*(3-X) + B_W*(3-Y) + B_FW*(3-Z)  # partner gets remainder

    objective = agent_score + (1 - lambda) * partner_score
    constraint: agent_score ≤ max_point   # Smax cap

    return problem.solve()  # PuLP LP solver
```

**Objective (Equation 3 from paper):**
> Maximize `Sa + (1 − λ) · Sp`, subject to `Sa ≤ Smax`

- **λ near 1:** Agent prioritizes self-interest (competitive mode)
- **λ near 0:** Agent balances both utilities (cooperative mode)
- **Smax:** Upper bound on own score, preventing the agent from demanding too much

#### Parameter Sampling for Robustness

To generate a diverse candidate set rather than a single optimal offer, the LP is solved multiple times with varied parameters:
- **λ** is sampled in the range `[λ_determined ± 0.3]` in 0.1 increments
- **Smax** is decremented by 1 point at a time down to 10 points below the main value

This produces **N offer candidates** (top-N by agent score), which are then passed to Stage 3 for final selection.

*Source: [arXiv:2503.07129](https://arxiv.org/abs/2503.07129), Section 2.3 (Stage 2), Figure 8 (Appendix A.3)*

### 2. Stance Classification for Opponent Modeling

ASTRA's opponent modeling (Stage 1) classifies the partner's behavior along two dimensions — **Fairness** and **Stance** — both computed directly from score comparisons rather than from text embeddings.

#### Fairness Classification

Fairness is determined by comparing the point gap between the two parties in the partner's most recent offer:

```
Fairness = {
    Fair   if |SP_agent - SP_partner| ≤ θ_f  OR  SP_partner ≤ PMS/2
    Unfair otherwise
}
```

Where:
- `SP_agent` = agent's score *under the partner's latest offer*
- `SP_partner` = partner's score *under the partner's latest offer*
- `θ_f = 4` (fairness threshold, set at a 35% share of total score, derived from inequity aversion literature: Fehr & Schmidt 1999, ultimatum game experiments)
- `PMS` = possible maximum score

#### Stance Classification (3-way)

Stance captures the partner's *directional* movement — whether they are becoming more or less generous:

```
ΔSp = SP_partner^(t) - SP_partner^(t-1)

Stance = {
    Generous  if ΔSp < 0   (partner's own score decreased → they conceded)
    Neutral   if ΔSp = 0   (no change)
    Greedy    if ΔSp > 0   (partner's own score increased → they demanded more)
}
```

The combined `(Fairness × Stance)` grid produces 6 cells, each associated with a specific λ value for the LP objective:

| | Fair | Unfair | Unknown |
|---|---|---|---|
| **Generous** | λ = 0.3 | λ = 0.3 | λ = 0.5 |
| **Neutral** | λ = 0.8 | λ = 0.9 | λ = 0.6 |
| **Greedy** | λ = 0.5 | λ = 0.4 | λ = 0.5 |

(Values from Figure 3 heatmap of average λ by stance/fairness in paper)

**Interpretation:** Against a greedy+unfair partner, the agent sets λ≈0.9 (maximally self-interested). Against a generous+fair partner, λ drops to 0.3 (cooperative). This implements the Tit-for-Tat (TFT) principle: mirror the opponent's level of cooperation.

*Source: [arXiv:2503.07129](https://arxiv.org/abs/2503.07129), Section 2.3 (Stage 1), Equations 1–2, Figure 3, Appendix A.2*

### 3. How ASTRA Combines LLM Reasoning with Game-Theoretic Optimization

ASTRA is a **modular hybrid pipeline** in which the LLM and the LP solver perform distinct, non-overlapping roles at each turn. The system is not end-to-end; each module has a specific function:

| Module | Powered By | Role |
|---|---|---|
| Preference Asker | LLM (GPT-4o-mini) | Generates natural-language question to elicit partner's item priorities early in negotiation |
| Preference Consistency Checker | LLM | Detects when inferred partner preferences (IPP) contradict observed behavior |
| Preference Updater | LLM | Refines IPP after each turn based on new utterances |
| Fairness/Stance Assessor | Rule-based (score arithmetic) | Classifies partner behavior using point-gap formulas |
| LP Solver | PuLP (Python) | Generates Pareto-efficient offer candidates given current IPP and λ |
| Virtual Partner Agent (VPA) | LLM (GPT-4o) | Scores each offer candidate for partner acceptance probability (PAP) |
| Strategy Assessor | LLM (GPT-4o) | Selects the best negotiation tactic (from 9 tactics) and ranks offers |
| Response Generator | LLM (GPT-4o) | Produces the final natural-language response embedding the selected offer |

The overall integration is best described as: **LLM generates parameters → LP solver generates optimal offers → LLM selects and expresses the best one.**

*Source: [arXiv:2503.07129](https://arxiv.org/abs/2503.07129), Section 2, Figure 2*

---

### 4. Architecture: LLM → LP → LLM

The pipeline is strictly **unidirectional** at each turn, with three passes through different modules:

```
Turn t:
┌─────────────────────────────────────────────────────────────────────────────┐
│ STAGE 1: Opponent Modeling                                                  │
│   LLM (GPT-4o-mini) reads dialogue history                                 │
│   → Updates Inferred Partner Preferences (IPP)                              │
│   → Rule engine computes Fairness + Stance from score deltas               │
│   → Maps (Fairness, Stance) → λ value for LP                               │
│                                                                             │
│ STAGE 2: Offer Optimization (LP Solver as Tool)                             │
│   LP solver called with (agents_value, partner_value=IPP, λ, Smax)         │
│   → Solved N times with λ ± 0.3 perturbations and Smax decrements          │
│   → Returns top-N offer candidates {(X, Y, Z)} sorted by agent score       │
│                                                                             │
│ STAGE 3: Final Offer Selection                                              │
│   Virtual Partner Agent (LLM) scores each candidate for acceptance prob.   │
│   LLM evaluates each candidate against 9 negotiation tactics               │
│   → Selects best tactic + ranks offers (5 evaluations, majority vote)      │
│   → Final Score = α·PAP + β·SA (α=0.35, β=0.65 optimal)                  │
│   → Winning offer (X*, Y*, Z*) embedded in natural-language response       │
└─────────────────────────────────────────────────────────────────────────────┘
```

**Critical architectural point:** The LP solver takes as input **LLM-generated parameters** (specifically the IPP, which is the LLM's estimate of what the partner values) and outputs **mathematically optimal allocations** given those parameters. The LLM does not directly generate the allocation numbers — it generates the inputs to the optimizer. This decoupling is what guarantees Pareto-optimality of the output offers (conditional on accurate IPP).

**9 Negotiation Tactics** evaluated in Stage 3 are divided into:
- *Competitive* (4): Aggressive Early Offer (AEO), Reciprocal No Concession (RNC), Logrolling with Greed (LGR), Competitive Strategic Concession (CSC)
- *Collaborative* (5): Logrolling (LGR), Mutual Gain Focus (MGF), Reciprocal Concession (RC), Non-Concessive Reciprocity (NCR), Logrolling with Incremental Concession (LIC), Reference Effect Offer (REO) *(names inferred from Figure 4 abbreviations)*

*Source: [arXiv:2503.07129](https://arxiv.org/abs/2503.07129), Sections 2.1–2.3, Figure 2, Appendix A.3–A.4*

- **~28% of ASTRA's offers were novel** to expert participants (they had not independently considered the offer)
- ASTRA's offers were rated as **moderately better** than experts' own best offers (mean = 2.25, t = 13.47, p < 0.001)
- Objectively, ASTRA's offers were **3.6 points more favorable** than expert-generated offers

#### Pareto Optimality Analysis

When plotting offer distributions on the agent-partner score plane, ASTRA's offers (blue points) cluster near the **Pareto Frontier** (green markers), while the baseline PartnerAgent's offers (red points) are substantially interior to it. This confirms that LP-based generation achieves efficiency that pure LLM prompting does not.

#### vs. Pure LLM (Ablation without ASTRA)

"Ours w/o ASTRA" (same LLM, no LP solver) scores 20.75 in agreement cases vs. ASTRA's 24.34 — a **3.59-point gap** (roughly one item of medium priority). The walk-away rate drops dramatically from 17% to 4%, suggesting that without ASTRA's LP-guided confidence, the agent accepts worse deals rather than walking away.

#### vs. Pure Game-Theoretic (RL Agent)

The RL agent (PPO-trained Flan-T5 on CaSiNo, Chawla et al. 2023 method) scores 18.86 with 0% walk-away — it always reaches agreement but never achieves an advantage. ASTRA gains 5.48 more points in agreement cases while accepting strategic deadlocks when warranted.

*Source: [arXiv:2503.07129](https://arxiv.org/abs/2503.07129), Tables 1–4, Figures 3–7, Sections 4.1–5.4*

## Cross-Project Synthesis

| Dimension | AgenticPay | ASTRA |
|---|---|---|
| **Setting** | Buyer-seller price negotiation, scalar price, 10 domains | Multi-issue bargaining (MIB), item allocation, CaSiNo domain |
| **Action space** | Continuous price offers → extracted by regex | Discrete item counts → generated by LP solver |
| **Opponent modeling** | Mental modeling prompt (not parsed) | Explicit IPP tracking + Fairness/Stance classification |
| **Optimization** | None (pure LLM policy) | LP solver with dynamic λ parameter |
| **LLM role** | Full policy (generate and decide) | Parameter generator + offer selector + response generator |
| **Evaluation** | 111-task benchmark, 5 LLMs compared | Simulation vs. 4 baselines + human evaluation |
| **Best agent** | Claude Opus 4.5 (GlobalScore 86.9, 3.7 rounds) | ASTRA powered by GPT-4o (24.34 pts, EMNLP 2025) |
| **Core weakness** | Open-weight LLMs fail in long-horizon convergence | Limited to 3-item MIB; LP formulation is pre-specified |
| **On-chain relevance** | Welfare scores (rb, rs, Q) directly map to ZK-attestable trade receipts | Pareto-optimal offers could be generated trustlessly inside TEE |

Both projects independently identify the same fundamental gap: **LLMs can negotiate but cannot reliably optimize.** AgenticPay quantifies this gap across a large benchmark; ASTRA proposes a hybrid architecture to close it via tool-integrated LP solving.
