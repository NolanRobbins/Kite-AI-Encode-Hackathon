## 2. Gasless Integration

### How It Works [Source 2]

No paymaster contract. Kite uses **EIP-3009 signed meta-transactions** with a centralized **relayer service** at `https://gasless.gokite.ai`. Users sign an off-chain `transferWithAuthorization` message; the relayer submits it on-chain and pays gas.

### API Reference [Source 2]

**Service Endpoint**: `https://gasless.gokite.ai`

**List Supported Tokens**: `GET /supported_tokens`

**Submit Transfer**: `POST /testnet` or `POST /mainnet`

Request body follows EIP-3009:
```json
{
  "tokenAddress": "0x...",
  "from": "0x...",
  "to": "0x...",
  "value": "1234567890123456",
  "validAfter": "1234567891",
  "validBefore": "1234567892",
  "nonce": "0x...",
  "v": 28,
  "r": "0x...",
  "s": "0x..."
}
```

Response: `{ "txHash": "0x..." }`

**Constraints**:
- `validBefore` must be within 30 seconds from current time
- `validAfter` must be greater than latest block timestamp
- Each nonce can only be used once

### No Paymaster — This Is Relayer-Based

There is **no paymaster contract address**. GitHub search for "paymaster" across the entire `gokite-ai` org returned zero results [Source 5]. The gasless model is:
1. User signs EIP-3009 `transferWithAuthorization` off-chain
2. Relayer at `gasless.gokite.ai` submits the tx on-chain
3. Relayer pays gas in $KITE
4. User's stablecoin transfer executes without user holding gas tokens

For the AA SDK path, gasless works differently: the bundler at `https://bundler-service.staging.gokite.ai/rpc/` handles UserOperation submission, and the AA wallet itself can be configured for sponsored gas.

## 6. `addSessionKeyRule()` — Can It Accept Dynamic `valueLimit`?

### Answer: YES — Full Solidity Signature Found [Source 9]

From the [kite-agentic-settle](https://github.com/bolajahmad/kite-agentic-settle) hackathon project, which implemented a working `KiteAAWallet.sol`:

```solidity
function addSessionKeyRule(
    address sessionKeyAddress,   // The ephemeral key
    bytes32 agentId,             // Agent identity
    uint256 sessionIndex,        // Derivation index
    uint256 valueLimit,          // ← MAX PER-TRANSACTION (dynamic, set to negotiated price)
    uint256 dailyLimit,          // ← MAX PER-DAY aggregate
    uint256 validUntil,          // Expiry timestamp
    address[] calldata allowedRecipients,  // ← Lock to counterparty address
    bytes calldata metadata      // Arbitrary metadata (deal terms hash?)
) external onlyRegistered
```

### Key Findings

1. **`valueLimit` is a `uint256` parameter** — set it to any value at call time. After each negotiation concludes at price P, call `addSessionKeyRule(sessionKey, agentId, index, P, dailyMax, expiry, [counterparty], dealMetadata)`.

2. **`dailyLimit` provides aggregate caps** — e.g., "this agent can spend max 1000 USDT/day across all transactions."

3. **`allowedRecipients` locks the counterparty** — the session key can ONLY pay addresses in this array. Set to `[sellerAddress]` after negotiation.

4. **`validUntil` sets deal expiry** — the session key auto-expires. Set to negotiation deadline.

5. **`metadata` is arbitrary bytes** — encode the full deal terms hash here for on-chain attestation.

6. **You CAN'T update an existing session key's valueLimit.** You must **revoke the old key** and **create a new one** with the updated limit. The contract provides `revokeSessionKey(address)` for this.

### Viem ABI for TypeScript [Source 9]

```typescript
import { parseAbi } from "viem";

const kiteAAWalletAbi = parseAbi([
  "function addSessionKeyRule(address sessionKeyAddress, bytes32 agentId, uint256 sessionIndex, uint256 valueLimit, uint256 dailyLimit, uint256 validUntil, address[] allowedRecipients, bytes metadata) external",
  "function revokeSessionKey(address sessionKeyAddress) external",
  "function revokeAllAgentSessions(bytes32 agentId) external",
  "function executePayment(address sessionKey, address recipient, address token, uint256 amount) external",
  "function getSessionRule(address sessionKey) external view returns (address user, bytes32 agentId, uint256 valueLimit, uint256 dailyLimit, uint256 validUntil, bool active)",
  "function getSessionAllowedRecipients(address sessionKey) external view returns (address[])",
  "function isSessionValid(address sessionKey) external view returns (bool)",
  "function getDailySpend(address sessionKey) external view returns (uint256 spent, uint256 windowStart)",
  "function deposit(address token, uint256 amount) external",
  "function withdraw(address token, uint256 amount) external",
]);
```

### NegotiatorGrid Pattern

```
Negotiation concludes at price P with seller 0xSeller:

1. Generate random session key address
2. addSessionKeyRule(
     sessionKeyAddr,
     negotiatorAgentId,
     0,                          // session index
     P,                          // valueLimit = negotiated price
     P * 10,                     // dailyLimit (allow multiple deals)
     block.timestamp + 3600,     // 1 hour expiry
     [0xSeller],                 // only pay this seller
     keccak256(dealTermsJSON)    // metadata = deal hash
   )
3. executePayment(sessionKeyAddr, 0xSeller, testUSDT, P)
4. Session key auto-expires or revoke after use
```

**Note**: The `KiteAAWallet.sol` from Source 9 is a hackathon implementation, not an official Kite contract. The official `GokiteAccount.sol` at `0x93F5...FC21` may have a different interface. The AA SDK docs [Source 1] reference `configureSpendingRules` which uses a `{timeWindow, budget, initialWindowStartTime, targetProviders}` struct — a simpler model without per-tx limits or allowed recipients.

### `/v2/settle` Request [Source 5]

```bash
curl -X POST https://facilitator.pieverse.io/v2/settle \
  -H "Content-Type: application/json" \
  -d '{
    "authorization": { ... },
    "signature": "0x...",
    "network": "kite-testnet"
  }'
```

The `authorization` object and `signature` come from the `X-Payment` header that the buyer's agent sends. The facilitator:
1. Verifies the signature matches the authorization
2. Calls `transferWithAuthorization()` on the stablecoin contract
3. Transfers funds directly from payer → payee on-chain
4. Returns transaction hash

```json
{
  "kinds": [
    {"x402Version": 2, "scheme": "exact", "network": "eip155:2368"},
    {"x402Version": 2, "scheme": "exact", "network": "eip155:2366"}
  ],
  "signers": {
    "eip155:*": [
      "0x12343e649e6b2b2b77649DFAb88f103c02F3C78b",
      "0xfa6b2a1FC2151197cE3242D0Ea64327b798Dbd4a"
    ]

```

Kite Testnet = `eip155:2368`, Kite Mainnet = `eip155:2366`.

### ⚠️ Schema Gap

The facilitator docs at `https://facilitator.pieverse.io/` return only a JSON service description — no detailed request/response schemas for `/v2/verify` or `/v2/settle`. The Service Provider Guide [Source 5] provides the curl example above but doesn't document the full schema of the `authorization` object. For the full x402 protocol spec, refer to [https://docs.x402.org/introduction](https://docs.x402.org/introduction).

## Action Items for NegotiatorGrid

1. **Use `gokite-aa-sdk`** (npm) for AA wallet creation, vault deployment, and spending rule configuration. The official `configureSpendingRules` uses `{timeWindow, budget, targetProviders}` — simpler than `addSessionKeyRule` but still enforceable.

2. **For per-negotiation session keys**, consider deploying the [kite-agentic-settle](https://github.com/bolajahmad/kite-agentic-settle) `KiteAAWallet.sol` which has the full `addSessionKeyRule(valueLimit, dailyLimit, allowedRecipients, metadata)` interface. This is a hackathon-proven implementation.

3. **To update spending cap after negotiation**: Revoke the old session key → create a new one with the negotiated price as `valueLimit`. There's no in-place update.

4. **For x402 settlement**, use the Pieverse facilitator at `https://facilitator.pieverse.io/v2/settle`. The facilitator address `0x12343e649e6b2b2b77649DFAb88f103c02F3C78b` is confirmed live on kite-testnet.

5. **Token for payments**: Use Test USDT (`0x0fF5...`) for x402 settlement. Use PYUSD (`0x8E04...`) only if you need gasless EIP-3009 transfers.

6. **Gasless for UX**: The `gasless.gokite.ai` relayer handles gas-free stablecoin transfers. Consider using this for the demo to avoid requiring judges to hold $KITE for gas.
