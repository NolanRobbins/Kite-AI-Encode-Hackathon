## 1. x402-foundation/x402 — Official SDK (5.9k stars)

### Overview

The official reference implementation. Multi-language (TypeScript, Python, Go, Java), with transport-agnostic client + server + facilitator components. This is the canonical SDK that all other libraries build on top of.

### Install Commands

| Language | Client Install | Server Install |
|----------|---------------|----------------|
| TypeScript | `npm install @x402/fetch @x402/evm` or `npm install @x402/axios @x402/evm` | `npm install @x402/express @x402/core @x402/evm` |
| Python | `pip install x402` (extras: `pip install x402[httpx]` or `x402[requests]`) | `pip install x402[fastapi]` or `x402[flask]` |
| Go | `go get github.com/x402-foundation/x402/go` | Same package |

**Source**: [PyPI x402](https://pypi.org/project/x402/), [x402 buyer quickstart](https://docs.x402.org/getting-started/quickstart-for-buyers)

### Does the Python SDK Handle Full 402→Sign→Retry?

**YES — fully automatic.** The `x402HttpxClient` wraps an httpx `AsyncBaseTransport` that intercepts 402 responses, parses `PaymentRequired`, calls `create_payment_payload()`, injects the `PAYMENT-SIGNATURE` header, and retries — all transparently.

```python
from x402 import x402Client
from x402.mechanisms.evm.exact import ExactEvmScheme
from x402.http.clients.httpx import x402_httpx_transport
from eth_account import Account
import httpx

# 1. Create signer
account = Account.from_key("0xYourPrivateKey")

# 2. Create x402 client and register EVM scheme
client = x402Client()
client.register("eip155:84532", ExactEvmScheme(signer=account))

# 3. Use transport wrapper — 402→sign→retry is AUTOMATIC
async with httpx.AsyncClient(
    transport=x402_httpx_transport(client)
) as http:
    response = await http.get("https://api.example.com/paid-endpoint")
    print(response.json())  # ← Already paid, response is the resource
```

The transport's `handle_async_request()` method:
1. Sends initial request
2. Checks if response is 402
3. Reads body, parses `PaymentRequired` (supports both V1 body and V2 header)
4. Calls `client.create_payment_payload(payment_required)`
5. Encodes payment as header (`PAYMENT-SIGNATURE` for V2 or `X-PAYMENT` for V1)
6. Clones request with payment header + retry flag
7. Returns the retried response

There's also a synchronous `requests` adapter:

```python
from x402.clients.requests import x402_requests

session = x402_requests(account)
response = session.get("https://api.example.com/paid-endpoint")
# Automatic 402→sign→retry
```

**Source**: [x402 Python httpx client](https://github.com/x402-foundation/x402/blob/main/python/x402/http/clients/httpx.py)

### Can I Inject a Custom Price Validator?

**YES — via the Policy and Hook system.** The Python SDK has three injection points:

#### Built-in `max_amount` Policy (simple cap)

```python
from x402 import x402Client, max_amount

client = x402Client()
client.register("eip155:84532", ExactEvmScheme(signer=account))

# Reject any payment above 50000 atomic units ($0.05 USDC)
client.register_policy(max_amount(50000))
```

#### Custom Policy (NegotiatorGrid price validator)

```python
def negotiatorgrid_price_policy(negotiated_deal_price: int):
    """Only allow payments at or below the negotiated price."""
    def policy(version: int, reqs: list) -> list:
        return [r for r in reqs if int(r.get_amount()) <= negotiated_deal_price]
    return policy

# After negotiation agrees on $0.038 (38000 atomic USDC):
client.register_policy(negotiatorgrid_price_policy(38000))
```

The policy system works by:
1. All `PaymentRequirements` from the 402 response pass through registered policies in order
2. Each policy filters the list — removing requirements that don't match criteria
3. The remaining requirements are passed to the selector (default: first match)
4. If all filtered out → `NoMatchingRequirementsError` is raised → payment aborted

**Source**: [x402 Python client_base.py](https://github.com/x402-foundation/x402/blob/main/python/x402/client_base.py)

#### `BeforePaymentCreationHook` (full control)

For more complex validation (e.g., checking deal_hash matches):

```python
from x402.schemas import PaymentCreationContext, AbortResult

async def validate_negotiation(ctx: PaymentCreationContext) -> AbortResult | None:
    """Abort payment if price doesn't match negotiation outcome."""
    requirements = ctx.selected_requirements
    amount = int(requirements.get_amount())
    
    # Check against NegotiatorGrid deal
    deal = get_active_deal(requirements.extra.get("deal_hash"))
    if deal is None:
        return AbortResult(reason="No matching negotiation deal found")
    if amount > deal.agreed_price:
        return AbortResult(reason=f"Price {amount} exceeds negotiated {deal.agreed_price}")
    return None  # Allow payment

client.on_before_payment_creation(validate_negotiation)
```

Hook types available:
- `BeforePaymentCreationHook` — runs before signing, can return `AbortResult` to cancel
- `AfterPaymentCreationHook` — runs after successful signing (logging, analytics)
- `OnPaymentCreationFailureHook` — runs on failure, can return `RecoveredPayloadResult` to retry

All hooks support both sync and async.

**Source**: [x402 Python client.py](https://github.com/x402-foundation/x402/blob/main/python/x402/client.py)

### Kite Compatibility

**Partial.** The official SDK uses CAIP-2 network identifiers (`eip155:84532`) and the `exact` scheme. Kite uses `"kite-testnet"` as the network string and the `gokite-aa` scheme — which is a V1-only custom scheme. To use the official SDK with Kite:
- Register a custom `SchemeNetworkClientV1` for `gokite-aa`
- Use `client.register_v1("kite-testnet", GokiteAAScheme(signer=account))`
- The V1 client path handles `maxAmountRequired` instead of `amount`

### Dynamic Pricing Support

**YES.** The SDK doesn't enforce static pricing. The server generates `PaymentRequirements` dynamically at request time. The client-side policies and hooks let NegotiatorGrid validate that the 402 price matches the negotiated deal.

```python
from fastapi import FastAPI
from fast_x402 import x402_middleware

app = FastAPI()
app.add_middleware(
    x402_middleware,
    wallet_address="0xYourAddress",
```

For NegotiatorGrid: This middleware accepts a `routes` dict with prices. **The price can be set dynamically** by updating the route config before the middleware processes the request, or by using a custom price function.

### x402-langchain — Autonomous Payment Decisions

```python
from x402_langchain import create_x402_agent
from langchain.chat_models import ChatOpenAI

agent = create_x402_agent(
    private_key="0xYourPrivateKey",
```

### Kite Compatibility

**Unlikely out-of-box.** Uses standard EVM x402 (Base, Polygon). Would need modification for `gokite-aa` scheme and `kite-testnet` network.

**Buyer side (x402-langchain)**: The `spending_limit_daily` and `per_transaction` limits serve as caps. NegotiatorGrid could set `per_transaction` to the negotiated price to prevent overpayment.

## 3. Kite-Specific x402 — The "gokite-aa" Scheme

### How gokite-aa Differs from Standard EVM x402

| Feature | Standard EVM x402 (`exact`) | Kite (`gokite-aa`) |
|---------|----------------------------|---------------------|
| x402 Version | V2 (`x402Version: 2`) | V1 (`x402Version: 1`) |
| Network format | CAIP-2: `eip155:84532` | Plain string: `kite-testnet` |
| Amount field | `amount` | `maxAmountRequired` |
| Resource info | Top-level `resource` object | Inside each `accepts` entry |
| Header name | `PAYMENT-SIGNATURE` | `X-PAYMENT` |
| Signing mechanism | EIP-3009 `transferWithAuthorization` | Account Abstraction (AA) - likely ERC-4337 UserOperation |
| Token | USDC (`0x036CbD53842c5426634e7929541eC2318f3dCF7e`) | Test USDT (`0x0fF5393387ad2f9f691FD6Fd28e07E3969e27e63`) |
| Extensions field | Present (`extensions`) | Not present |
| Extra fields | `{ name: "USDC", version: "2" }` | `null` (or custom) |
| Additional fields | — | `merchantName`, `outputSchema` |

**Source**: [Kite Service Provider Guide](https://docs.gokite.ai/kite-agent-passport/service-provider-guide)

### Kite Facilitator: Pieverse (NOT Coinbase)

Kite uses the **Pieverse facilitator** — a third-party facilitator, not the Coinbase CDP free-tier.

| Property | Value |
|----------|-------|
| Facilitator name | x402 Pieverse Facilitator |
| Base URL | `https://facilitator.pieverse.io` |
| Facilitator address | `0x12343e649e6b2b2b77649DFAb88f103c02F3C78b` |
| Supported networks | `bsc`, `bsc-testnet`, `base`, `monad`, `kite-testnet`, `kite` |
| Endpoints | `GET /v2/supported`, `POST /v2/verify`, `POST /v2/settle` |

The same facilitator address (`0x12343e...`) is used across BSC, Base, and Kite chains. The Pieverse facilitator supports **both** Kite and standard EVM chains — meaning NegotiatorGrid can use a single facilitator for both Kite demo and standard x402 deployments.

**Source**: [Pieverse facilitator](https://facilitator.pieverse.io/)

### Kite x402 Fork

Kite provides demo facilitator implementations at `https://github.com/gokite-ai/x402` (referenced in their docs but the repo appears to have restricted access or has been renamed). The Kite developer docs reference it as a "demo facilitator to clarify what is needed to support Kite payment."

### Dynamic Pricing Support

**YES.** The Kite V1 format returns a JSON body with `maxAmountRequired` set by the server. There is no protocol constraint preventing the server from computing this value dynamically based on a negotiation outcome.

## 4. LangChain x402 Integration (xpay.sh)

### Overview

`x402-langchain` is a helper library from the xpay.sh ecosystem that bridges x402 facilitators with LangChain tools. It wraps the 402→sign→retry cycle into LangChain-compatible tools with spending controls.

### Install

```bash
pip install langchain langchain-openai x402-langchain
```

### Usage

```python
from x402_langchain import create_x402_agent
from langchain.chat_models import ChatOpenAI

agent = create_x402_agent(
    private_key=os.getenv('X402_PRIVATE_KEY'),
    llm=ChatOpenAI(model="gpt-4"),
    spending_limits={
        'daily': 10.0,
        'per_transaction': 1.0,
        'hourly': 2.0
    },
    network='polygon'
)

# Agent autonomously decides to pay for data
result = await agent.run("Get the latest price for AAPL and analyze the trend")
```

### Multi-Agent Payment Orchestration

```python
from x402_langchain import AsyncX402Agent

class PaymentOrchestrator:
    def __init__(self):
        self.data_agent = AsyncX402Agent(role="data_purchaser", spending_limit=5.0)
        self.analysis_agent = AsyncX402Agent(role="compute_purchaser", spending_limit=3.0)

    async def execute_workflow(self, query):
        tasks = [
            self.data_agent.purchase_data("https://api.financial-data.com/premium"),
            self.analysis_agent.purchase_compute("https://ml-compute.com/analysis")
        ]
        data, analysis = await asyncio.gather(*tasks)
        return self.synthesize_results(data, analysis)
```

### Facilitator Options

The library is facilitator-agnostic — supports CDP, Mogami, thirdweb, and custom facilitators:

```python
from x402_facilitators import CDPClient      # Enterprise (Coinbase)
from x402_facilitators import MogamiClient   # Zero fees
from x402_facilitators import ThirdwebClient # Developer-friendly
from x402_facilitators import CustomClient   # Custom (e.g., Pieverse)
```

### Kite Compatibility

**Requires custom facilitator setup.** You'd configure `CustomClient` with the Pieverse facilitator URL (`https://facilitator.pieverse.io`). The `gokite-aa` scheme would need a custom tool wrapper.

### Dynamic Pricing Support

**Yes, via spending limits.** Set `per_transaction` to the negotiated price as a cap. The LLM agent can also be prompted to reject offers above a threshold — but this is soft enforcement. For hard enforcement, combine with the official x402 SDK's policy system.

**Source**: [xpay.sh LangChain integration](https://xpay.sh/x402-agent-frameworks/langchain)

## 5. OpenAI Agents SDK + x402 (Laso Finance)

### Overview

Laso Finance provides x402-powered financial tools for the OpenAI Agents SDK. The integration uses `@function_tool` decorators to give agents the ability to order prepaid cards and send payments via x402.

### Install

```bash
pip install openai-agents requests
```

### Usage

```python
from agents import Agent, Runner, function_tool
import requests

@function_tool
def order_card(amount: int) -> str:
    """Order a prepaid card loaded with the specified USD amount."""
    url = f"https://laso.finance/get-card?amount={amount}"
    
    response = requests.get(url)
    if response.status_code == 402:
        payment_requirements = response.json()
        x_payment = sign_x402_payment(payment_requirements)
        response = requests.get(url, headers={"X-PAYMENT": x_payment})
    
    data = response.json()
    return f"Card ordered. Card ID: {data['card']['card_id']}"

agent = Agent(
    name="Payment Agent",
    instructions="You help users order prepaid cards and send payments.",
    tools=[order_card, send_venmo_payment],
)

result = Runner.run_sync(agent, "Order a $25 prepaid card")
```

### Guardrails for Spending Control

```python
from agents import GuardrailFunctionOutput, input_guardrail

@input_guardrail
async def spending_limit(ctx, agent, input) -> GuardrailFunctionOutput:
    """Block requests exceeding spending limit."""
    return GuardrailFunctionOutput(
        output_info={"checked": True},
        tripwire_triggered=False,  # Set True to block
    )

agent = Agent(
    name="Payment Agent",
    tools=[order_card],
    input_guardrails=[spending_limit],
)
```

### Multi-Agent Handoff Pattern

```python
card_agent = Agent(name="Card Agent", tools=[order_card, get_card_data])
payment_agent = Agent(name="Payment Agent", tools=[send_venmo_payment])

triage_agent = Agent(
    name="Triage Agent",
    instructions="Route card requests to Card Agent, payments to Payment Agent.",
    handoffs=[card_agent, payment_agent],
)
```

### Kite Compatibility

**Not directly.** Laso Finance targets Base mainnet. The `sign_x402_payment()` function would need modification for `gokite-aa` scheme.

### Dynamic Pricing Support

**Manual.** The 402→sign→retry is handled explicitly in each tool function (not abstracted). This means NegotiatorGrid has full control: the tool function can validate the price before signing.

**Source**: [Laso Finance OpenAI Agents docs](https://agents.laso.finance/frameworks/openai-agents)

## 8. NegotiatorGrid Recommendation

### Primary Stack

**Buyer Agent (NegotiatorGrid client):**
- **`pip install x402[httpx]`** — the official Python SDK with full 402→sign→retry, policy-based price validation, and lifecycle hooks
- Register a `negotiatorgrid_price_policy` that caps payments at the negotiated deal price
- Register a `BeforePaymentCreationHook` that validates `deal_hash` in `extra` field
- For Kite: implement a custom `SchemeNetworkClientV1` for `gokite-aa`

**Seller Agent (NegotiatorGrid server):**
- **`pip install x402[fastapi]`** — official FastAPI middleware, but bypass the static route config
- Use "Manual Server Integration" pattern from PyPI docs to dynamically set `PaymentRequirements.maxAmountRequired` based on negotiation outcome
- Or use **`pip install fast-x402`** and update route prices dynamically

**AI Agent Layer (optional):**
- **`pip install x402-langchain`** for LangChain-based buyer agents with spending limits
- OR use **OpenAI Agents SDK** with custom `@function_tool` that embeds NegotiatorGrid negotiation before payment

### Facilitator

Use **Pieverse** (`https://facilitator.pieverse.io`) — it supports both Kite and standard EVM chains (Base, BSC, Monad). Single facilitator for both hackathon demo and production deployment.

### Implementation Pattern

```python

    def policy(version, reqs):
        return [r for r in reqs if int(r.get_amount()) <= negotiated_price]
    return policy

# After negotiation: agreed on 38000 atomic units
client.register_policy(deal_price_policy(38000))

async with httpx.AsyncClient(transport=x402_httpx_transport(client)) as http:
    response = await http.get("https://seller.negotiatorgrid.dev/api/data")
    # Automatic: 402 → validate price ≤ 38000 → sign → retry → 200

# === SELLER AGENT ===
from x402.types import PaymentRequirements, PaymentRequiredResponse

# After negotiation concludes with deal:
requirements = PaymentRequirements(
    scheme="exact",
    network="base",
    asset="0x833589fCD6eDb6E08f4c7C32D4f71b54bda02913",
    pay_to="0xSellerAddress",
    max_amount_required=str(deal.agreed_price),  # DYNAMIC from negotiation
```

## Open Questions

1. **`gokite-aa` signing internals**: The Account Abstraction signing flow for Kite is not documented in the x402 reference SDK. Need to inspect `https://github.com/gokite-ai/x402` (or the Kite MCP server) for the exact UserOperation format.

2. **Pieverse fee structure**: The Pieverse facilitator docs don't list fees. Need to clarify if it's free-tier like Coinbase CDP (1000 tx/month free) or has a different model.

3. **`upto` scheme in Python**: The official x402 Python SDK does not yet support the `upto` scheme (only TypeScript and Go). This means NegotiatorGrid's "Option B" pattern (authorize max, settle negotiated) requires TypeScript/Go or a custom Python implementation.

4. **x402-langchain production readiness**: The `x402-langchain` package version is 0.3.13 — check for stability and whether it's actively maintained.
