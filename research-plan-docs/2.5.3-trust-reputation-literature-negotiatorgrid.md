## Paper 1: Inter-Agent Trust Models

**ArXiv ID**: 2511.03434
**Authors**: Botao 'Amber' Hu, Helena Rong
**Date**: November 5, 2025
**URL**: https://arxiv.org/abs/2511.03434
**Core Contribution**: First comprehensive comparative taxonomy of six trust models (Brief, Claim, Proof, Stake, Reputation, Constraint) evaluated across A2A, AP2, ERC-8004, and beyond. Argues that no single mechanism suffices and recommends Proof + Stake as trustless-by-default foundation, with Reputation as an overlay.
**Relevance to NegotiatorGrid**: HIGH

**Key Takeaways for Implementation**:

- **NegotiatorGrid must implement a hybrid trust model**: Proof (deal_hash cryptographic binding) + Stake (implicit via x402 payment authorization) + Reputation (ERC-8004 feedback) + Constraint (session key spending limits). No single layer is sufficient.
- **Reputation alone is brittle for LLM agents**: The paper identifies five LLM-specific fragilities — prompt injection, sycophancy, hallucination, deception, and misalignment — that make purely reputation-based trust dangerous. NegotiatorGrid's price negotiation must not rely solely on reputation scores; the deal_hash cryptographic proof is essential.
- **Sybil resistance requires identity cost**: The paper warns that "even an ideal reputation system only works if honest feedback is plentiful and identities cannot be cheaply faked." NegotiatorGrid's ERC-8004 NFT-based identity (which costs gas to mint) provides some Sybil resistance, but for stronger guarantees, agents should stake collateral proportional to negotiation volume.
- **Collusion resistance is an open problem**: "Weighting schemes, reputation decay, and trust-in-the-reviewer algorithms mitigate but cannot eliminate" collusion. NegotiatorGrid should implement reputation decay and cross-reference feedback with on-chain payment proofs (x402 tx hashes in ERC-8004 feedbackURI).
- **ERC-8004 is most effective for high-impact workflows**: For high-value negotiations, require Proof + Stake validation. For low-stakes micropayments, identity + reputation alone is acceptable.

**Quotable for Demo/Judges**: "No single trust mechanism suffices for autonomous agent markets — Hu & Rong (2025) recommend trustless-by-default architectures anchored in Proof and Stake, which is exactly what NegotiatorGrid implements through cryptographic deal hashes and x402 payment authorization."

**Code Repo**: None found
**Limitations / Gaps**: No formal security proofs. No quantitative model for how reputation scores should influence pricing or negotiation strategy — this is exactly the gap NegotiatorGrid fills.

**ArXiv ID**: 2501.16606
**Authors**: Tomer Jordi Chaffer
**Date**: January 28, 2025 (revised April 2025)
**URL**: https://arxiv.org/abs/2501.16606
**Core Contribution**: Philosophical exploration of governance mechanisms for decentralized agent economies. Introduces Agentbound Tokens — non-transferable identity tokens bound to agents — as a governance primitive for cryptoeconomic oversight.
**Relevance to NegotiatorGrid**: MEDIUM

**Key Takeaways for Implementation**:

- **Agentbound Tokens as non-transferable reputation anchors**: Similar to Soulbound Tokens (SBTs), Agentbound Tokens cannot be traded, preventing reputation laundering. NegotiatorGrid's ERC-8004 agent identity (ERC-721) is transferable — consider adding a non-transferable reputation accumulator that stays with the agent even if the NFT is transferred.
- **Cryptoeconomic governance for agent markets**: The paper argues that human oversight must be embedded at the protocol level, not bolted on after deployment. NegotiatorGrid's deal attestation contract already provides auditability, but governance mechanisms (e.g., who can update negotiation strategy parameters) should be explicit.
- **Agent DAOs for collective negotiation**: The paper envisions agents forming DAOs for collective bargaining — a future extension where multiple buyer agents pool their negotiation power.

**Quotable for Demo/Judges**: "NegotiatorGrid's on-chain deal attestations address Chaffer's (2025) call for 'protocol-level oversight mechanisms that scale with the agent economy,' providing auditability without requiring human intervention in each transaction."

**Code Repo**: None found
**Limitations / Gaps**: Purely philosophical — no formal framework, no implementation, no empirical validation. NegotiatorGrid provides the concrete implementation this paper calls for.

## Paper 3: Insured Agents

**ArXiv ID**: 2512.08737
**Authors**: Botao 'Amber' Hu, Bangdao Chen
**Date**: December 9, 2025
**URL**: https://arxiv.org/abs/2512.08737
**Core Contribution**: Proposes a protocol-native trust insurance mechanism where specialized "insurer agents" post slashable stake on behalf of operational agents, with TEE-based audit access for claims assessment. Creates a hierarchical insurer market that calibrates trust through competitive underwriting.
**Relevance to NegotiatorGrid**: MEDIUM-HIGH

**Key Takeaways for Implementation**:

- **Insurance as a trust primitive for negotiation**: Instead of requiring each agent to post its own collateral, an insurer agent could underwrite NegotiatorGrid deals. If a seller fails to deliver after payment, the insurer covers the loss and slashes the seller's insurance bond.
- **Premium-based risk pricing maps to negotiation**: An insurer's premium for underwriting a deal is itself a signal of the deal's risk level. A high-reputation agent gets lower premiums → lower total deal cost → competitive advantage in negotiations.
- **TEE-based audit for dispute resolution**: When a NegotiatorGrid deal fails (e.g., seller delivers substandard service), the insurer can audit the interaction using TEE-protected logs without exposing proprietary negotiation strategies.
- **Hierarchical insurer market for NegotiatorGrid**: Future extension — multiple insurer agents compete to underwrite deals, creating a meta-market around negotiation trust.

**Quotable for Demo/Judges**: "Hu & Chen's (2025) insured agents model directly addresses NegotiatorGrid's settlement failure risk — the paper shows how competitive insurance markets can provide trustless dispute resolution for autonomous transactions, which is exactly the gap between negotiation agreement and x402 payment settlement."

**Code Repo**: None found
**Limitations / Gaps**: No implementation. Submitted to AAMAS 2026 but not yet published. The TEE requirement adds hardware trust assumptions. NegotiatorGrid can implement a simplified version using the ERC-8004 Validation Registry as the "insurance claim" mechanism.

## Paper 4: Agent Contracts

**ArXiv ID**: 2601.08815
**Authors**: Qing Ye, Jing Tan
**Date**: January 13, 2026 (v3, March 2026, accepted COINE 2026 / AAMAS)
**URL**: https://arxiv.org/abs/2601.08815
**Core Contribution**: Formal framework for resource-bounded agent execution. Defines Agent Contract C = (I, O, S, R, T, Φ, Ψ) with input/output specs, multi-dimensional resource constraints, temporal boundaries, and success criteria. Demonstrates 90% token reduction with 525x lower variance through constraint enforcement. Establishes conservation laws for multi-agent delegation.
**Relevance to NegotiatorGrid**: HIGH

**Key Takeaways for Implementation**:

- **NegotiatorGrid DealContract maps directly to Agent Contract C = (I, O, S, R, T, Φ, Ψ)**:
  - I = negotiation request (resource URI, buyer constraints)
  - O = negotiated deal (agreed price, deal_hash, SLA terms)
  - S = {bilateral_negotiation, x402_payment, attestation_write}
  - R = {r_rounds ≤ max_rounds, r_time ≤ deadline, r_cost ≤ budget}
  - T = (negotiation_start, max_duration)
  - Φ = {deal_agreed ∧ price ≤ budget ∧ x402_settled}
  - Ψ = {timeout ∨ walkaway ∨ budget_exhausted}

- **Conservation laws for parallel negotiations**: When a buyer negotiates with N sellers simultaneously, the total committed budget must satisfy: ∑ committed_price_j ≤ B_total. This is NegotiatorGrid's CommitmentManager constraint.

- **Contract modes map to negotiation strategies**:
  - URGENT → aggressive, fewer rounds, accept quickly
  - ECONOMICAL → conservative, more rounds, optimize price
  - BALANCED → standard concession strategy

- **90% token reduction insight**: Agent Contracts reduce LLM token consumption by 90% through constraint enforcement. NegotiatorGrid can apply this: instead of letting the LLM generate unbounded negotiation reasoning, embed the strategy as structured constraints (reservation price, concession rate, deadline) and let the LLM operate within bounds.

- **Runtime monitoring for negotiation health**: Monitor(C, t) → (c⃗, u⃗, τ_util) translates to: track rounds consumed vs budget, time elapsed vs deadline, price gap vs reservation price. Alert if utilization > 80%.

**Quotable for Demo/Judges**: "NegotiatorGrid formalizes agent-to-agent negotiation as an Agent Contract (Ye & Tan, 2026) — C = (I, O, S, R, T, Φ, Ψ) — where resource constraints bound negotiation rounds, temporal boundaries enforce deadlines, and conservation laws prevent budget violations across parallel deals."

**Code Repo**: None found (paper mentions experiments but no public repo)
**Limitations / Gaps**: No formal security proofs for the conservation laws (empirically validated: zero violations in 50 trials). No integration with payment protocols or on-chain attestation. NegotiatorGrid bridges this gap by connecting Agent Contracts to x402 settlement and ERC-8004 attestation.

## NegotiatorGrid Trust Architecture — Answers to Design Questions

### Q1: How Should Reputation Scores Influence Negotiation Strategy?

**Recommendation: Reputation as a Bayesian prior for opponent modeling, not as a hard constraint.**

Based on the literature synthesis, reputation should influence three aspects of negotiation:

**a) Opening Offer Calibration**

```python
def compute_opening_offer(base_price, seller_reputation, buyer_reservation):
    """Reputation-adjusted opening offer."""
    # reputation_score: 0-100 from ERC-8004 Reputation Registry
    # Higher reputation → agent has proven track record → buyer offers closer to fair value
    # Lower reputation → agent is unknown/unreliable → buyer lowballs more aggressively
    
    reputation_discount = 1.0 - (seller_reputation / 100) * 0.3  # Up to 30% discount for unknown agents
    # High rep seller (90): discount = 0.73 → offer at 73% of base
    # Low rep seller (20): discount = 0.94 → offer at 94% of base (lowball)
    # Wait — this is inverted. High rep should get BETTER offers:
    
    reputation_premium = (seller_reputation / 100) * 0.2  # Up to 20% premium for trusted sellers
    adjusted_offer = base_price * (0.6 + reputation_premium)
    # High rep (90): 0.6 + 0.18 = 0.78 → start at 78% of ask
    # Low rep (20): 0.6 + 0.04 = 0.64 → start at 64% of ask (harder negotiation)
    
    return max(adjusted_offer, buyer_reservation * 0.5)  # Never below half of reservation
```

**b) Concession Rate Adjustment**

```python
def reputation_adjusted_concession_rate(base_rate, opponent_reputation):
    """Concede faster against reputable opponents (they'll likely deliver)."""
    # Trust factor: 0.5 (untrusted) to 1.5 (highly trusted)
    trust_factor = 0.5 + (opponent_reputation / 100)
    return base_rate * trust_factor
```

**c) Walkaway Threshold**

```python
def reputation_adjusted_walkaway(base_threshold, opponent_reputation):
    """More willing to walk away from low-reputation sellers."""
    # Low rep: walk away at 70% of reservation (conservative)
    # High rep: walk away at 95% of reservation (more lenient)
    leniency = 0.7 + (opponent_reputation / 100) * 0.25
    return base_threshold * leniency
```

**Source**: [Hu & Rong (2025)](https://arxiv.org/abs/2511.03434) — reputation as overlay, not foundation; [Zhang et al. (2021)](https://pmc.ncbi.nlm.nih.gov/articles/PMC7971364/) — "multi-issue evaluation function adjusted by rival's reputation"; [Krishnasamy et al. (2025)](https://pmc.ncbi.nlm.nih.gov/articles/PMC11923153/) — "adaptive probabilistic trust management model...dynamically ranks service providers"

### Q2: Should Agents with Higher Reputation Get Better Opening Offers?

**YES — with caveats.**

The academic consensus and the ERC-8004 ecosystem both support reputation-informed pricing:

1. **Forbes on ERC-8004**: "A portable reputation alters the criteria for underwriting. An agent might not be able to offer a house or passport as collateral but can provide a verifiable operational history." ([Forbes, Feb 2026](https://www.forbes.com/sites/digital-assets/2026/02/05/ai-agents-gain-trust-via-ethereum-erc-8004-on-mainnet/))

2. **Reddit on ERC-8004 pricing**: "Reputation can reduce collateral requirements when paired with real enforcement. Reputation informs pricing and access. Enforcement handles loss." ([Reddit, Feb 2026](https://www.reddit.com/r/ethereum/comments/1qwetmu/erc8004_and_agent_reputation_as_a_pricing/))

3. **Hu & Rong (2025)**: Reputation is "adaptive, information-rich evaluation over time; fosters earned trust."

**Implementation for NegotiatorGrid**:

```python
class ReputationAdjustedNegotiator:
    """Adjusts negotiation parameters based on ERC-8004 reputation scores."""
    
    def __init__(self, reputation_registry, identity_registry):
        self.rep_registry = reputation_registry
        self.id_registry = identity_registry
    
    async def get_opponent_trust_profile(self, agent_id: int) -> dict:
        """Build trust profile from ERC-8004 data."""
        # Query on-chain reputation
        summary = await self.rep_registry.getSummary(
            agent_id, 
            clientAddresses=trusted_reviewers,  # Filter by known reviewers
            tag1="deal_completion"
        )
        
        deal_count = summary.count
        avg_score = summary.summaryValue / (10 ** summary.summaryValueDecimals)
        
        # Cold-start handling
        if deal_count < 3:
            return {"trust_level": "unknown", "score": 50, "confidence": "low"}
        
        return {
            "trust_level": "high" if avg_score > 80 else "medium" if avg_score > 50 else "low",
            "score": avg_score,
            "confidence": "high" if deal_count > 20 else "medium",
            "deal_count": deal_count
        }
    
    def adjust_strategy(self, base_strategy, trust_profile):
        """Modify negotiation strategy based on trust profile."""
        score = trust_profile["score"]
        confidence = trust_profile["confidence"]
        
        if confidence == "low":
            # Unknown agent: be conservative, require more proof
            return base_strategy.with_adjustments(
                opening_discount=0.4,     # Lowball: start at 60% of ask
                concession_rate=0.5,      # Concede slowly
                max_rounds=base_strategy.max_rounds,  # Full negotiation
                require_deal_hash=True,   # Always require cryptographic proof
            )
        elif trust_profile["trust_level"] == "high":
            # Trusted agent: offer fair terms, concede faster
            return base_strategy.with_adjustments(
                opening_discount=0.2,     # Start at 80% of ask
                concession_rate=1.2,      # Concede 20% faster
                max_rounds=base_strategy.max_rounds // 2,  # Shorter negotiation
                require_deal_hash=True,   # Still require proof (Proof > Reputation)
            )
        else:
            return base_strategy  # Default strategy
```

### Q3: How to Prevent Collusion Between Repeated Counterparties?

**Threat Model**: Two agents repeatedly negotiate with each other and develop implicit coordination — e.g., the buyer always concedes quickly and the seller always offers the same price, creating a fixed-price cartel that squeezes out competitors.

**Evidence this is real**: [Lechmazur/emergent_collusion (GitHub)](https://github.com/lechmazur/emergent_collusion) demonstrates that "frontier LLMs can coordinate illegally on their own" — turn-taking schemes, price-fixing, and double collusion emerged spontaneously. [Purdue (2025)](https://engineering.purdue.edu/Engr/Research/GilbrethFellowships/ResearchProposals/2025-26/can-ai-agents-learn-to-collude-emergence-detection-and-mitigation-) confirms "repeated interactions may result in tacit collusion."

**NegotiatorGrid Anti-Collusion Measures**:

```python
class CollusionDetector:
    """Detect and prevent collusion between repeated counterparties."""
    
    def __init__(self, deal_record_contract):
        self.deal_record = deal_record_contract
    
    async def check_collusion_risk(self, buyer: str, seller: str) -> dict:
        """Analyze deal history for collusion indicators."""
        buyer_deals = await self.deal_record.getDealsByAgent(buyer)
        
        # 1. Frequency check: How often do these two trade?
        mutual_deals = [d for d in buyer_deals if d.seller == seller]
        total_deals = len(buyer_deals)
        concentration = len(mutual_deals) / max(total_deals, 1)
        
        # 2. Price variance check: Are prices suspiciously stable?
        if len(mutual_deals) > 3:
            prices = [d.finalPrice for d in mutual_deals]
            price_variance = np.var(prices) / np.mean(prices)  # Coefficient of variation
            low_variance = price_variance < 0.01  # Less than 1% variation = suspicious
        else:
            low_variance = False
        
        # 3. Mutual information check (from Bonjour et al., 2022)
        # High mutual information between agents' actions suggests coordination
        rounds_pattern = [d.negotiationRounds for d in mutual_deals]
        if len(rounds_pattern) > 5 and np.var(rounds_pattern) < 0.5:
            # Always same number of rounds = possibly scripted
            pattern_suspicious = True
        else:
            pattern_suspicious = False
        
        # 4. Round-robin check: Do they alternate who "wins"?
        # (Agent A gets better price, then B gets better price, then A...)
        
        risk_level = sum([
            concentration > 0.5,      # More than half of deals with same partner
            low_variance,              # Prices barely change
            pattern_suspicious,        # Negotiation patterns are rigid
        ])
        
        return {
            "risk": "high" if risk_level >= 2 else "medium" if risk_level == 1 else "low",
            "concentration": concentration,
            "price_variance_low": low_variance,
            "pattern_suspicious": pattern_suspicious,
            "recommendation": self.get_recommendation(risk_level)
        }
    
    def get_recommendation(self, risk_level):
        if risk_level >= 2:
            return "DIVERSIFY: Force negotiation with alternative sellers for next 5 deals"
        elif risk_level == 1:
            return "MONITOR: Log all negotiation rounds for audit"
        return "OK: No collusion indicators"
```

**Structural Mitigations**:
1. **Constrained communication**: NegotiatorGrid uses structured DataParts for offers, not free-text — this limits the channel for implicit coordination signals
2. **Reputation decay**: ERC-8004 feedback should decay over time (weight recent interactions more heavily)
3. **Diversification requirement**: If an agent trades with the same counterparty more than 50% of the time, the CommitmentManager should force exploration of alternatives
4. **Noise injection**: Add calibrated randomness to offers (from the information leakage mitigation) — this also disrupts collusion by making implicit coordination harder

**Source**: [Bonjour et al. (2022)](https://proceedings.mlr.press/v180/bonjour22a.html) — mutual information for collusion detection; [Ren et al. (2025)](https://arxiv.org/abs/2502.01971) — bottom-up reputation promotes cooperation; [Hu & Rong (2025)](https://arxiv.org/abs/2511.03434) — "weighting schemes, reputation decay, and trust-in-the-reviewer algorithms mitigate but cannot eliminate"

### Q4: Formal Security Model for Session Key Compromise During Negotiation

**Threat**: An attacker compromises the buyer's AA wallet session key during an active negotiation. The session key has a `valueLimit` set to the negotiated price. The attacker can sign payments up to that limit.

**Security Properties Required**:

1. **Bounded Loss (from Agent Contracts)**: Even if the session key is compromised, the maximum financial loss is bounded by `valueLimit` (the negotiated price). This is enforced on-chain by the AA wallet's `validateUserOp()` function.

2. **Temporal Bounding**: Session keys have `validUntil` timestamps. If the key is compromised after expiry, it's useless. NegotiatorGrid should set `validUntil = negotiation_start + max_duration + settlement_window`.

3. **Target Restriction**: Session keys should be scoped to specific contracts — only the x402 facilitator's `settle()` function and the DealRecord's `recordDeal()` function. An attacker with a compromised key cannot drain the wallet to an arbitrary address.

4. **Nonce Protection**: Each x402 payment uses a unique nonce (bytes32 random). Even with a compromised session key, the attacker cannot replay a payment — the nonce is consumed on-chain after the first use.

**Formal Model**:

```
Session Key SK = (address, valueLimit, validAfter, validUntil, allowedTargets[], allowedSelectors[])

Threat: Adversary A obtains SK at time t_compromise

Safety Properties:
  P1 (Bounded Loss): ∀ txns signed by SK: value(tx) ≤ SK.valueLimit
  P2 (Temporal Safety): t_compromise > SK.validUntil → A cannot execute any tx
  P3 (Target Safety): ∀ txns signed by SK: tx.to ∈ SK.allowedTargets ∧ tx.selector ∈ SK.allowedSelectors
  P4 (Replay Safety): nonce(tx) is unique and consumed on-chain → A cannot replay settled payments
  P5 (Revocation): owner can call revokeSessionKey(SK) → A cannot execute further txns

Compromise Scenarios:
  C1: A compromises SK during negotiation (before payment)
      → A can sign ONE payment up to valueLimit to an allowed target
      → Loss bounded by negotiated price
      → Mitigation: detect via on-chain monitoring; revoke SK immediately

  C2: A compromises SK after payment settled
      → SK's nonce already consumed → A cannot re-use for same deal
      → A could initiate a NEW payment to allowed targets
      → Mitigation: set valueLimit = exact negotiated price (no excess budget)

  C3: A compromises SK and modifies negotiation outcome
      → A could negotiate a higher price, then pay themselves
      → Mitigation: deal_hash verification ensures price matches prior negotiation
      → BeforePaymentCreationHook aborts if deal_hash doesn't match

Maximum Loss = min(SK.valueLimit, wallet_balance, allowedTarget_budget)
```

**NegotiatorGrid Defense-in-Depth**:

| Layer | Mechanism | Protects Against |
|-------|-----------|-----------------|
| 1. Session Key Scoping | `valueLimit = negotiated_price`, `allowedTargets = [facilitator]` | Unbounded drain |
| 2. Temporal Bounding | `validUntil = now + 10min` | Post-expiry attacks |
| 3. Deal Hash Verification | `BeforePaymentCreationHook` checks `deal_hash` | Price manipulation |
| 4. Nonce Uniqueness | EIP-3009 on-chain nonce tracking | Replay attacks |
| 5. On-Chain Monitoring | Watch for unexpected `transferWithAuthorization` events | Real-time detection |
| 6. Key Revocation | `revokeSessionKey(SK)` on detection | Stop ongoing attacks |

**Source**: [ERC-4337 spec](https://eips.ethereum.org/EIPS/eip-4337) — UserOperation validation, session key delegation; [ERC-4337 Session Keys docs](https://docs.erc4337.io/smart-accounts/session-keys-and-delegation.html) — dynamic delegation; [Ye & Tan (2026)](https://arxiv.org/abs/2601.08815) — resource constraint conservation laws bound agent execution

## Open Questions

1. **Reputation cold-start**: How should NegotiatorGrid handle brand-new agents with zero reputation? Current answer: treat as "unknown" with conservative strategy. Better answer from the Insured Agents paper: require a small insurance bond for new agents to participate in high-value negotiations.

2. **Cross-chain reputation portability**: ERC-8004 is deployed per-chain. An agent registered on Kite Testnet has no reputation on Base Mainnet. Future: cross-chain reputation bridging via signed attestations.

3. **LLM strategy leakage**: Even with structured DataParts, the LLM generating negotiation messages could inadvertently leak strategy information through word choice or response timing. The Agent Contracts paper's constraint enforcement (bounding LLM token usage) partially addresses this by limiting what the LLM can express.

4. **Insurance market bootstrapping**: The Insured Agents paper's insurance market requires specialized insurer agents to exist. For the hackathon demo, NegotiatorGrid can simulate this with a single "insurer" that posts a fixed bond.
