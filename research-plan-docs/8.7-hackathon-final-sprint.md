## TL;DR

A buyer agent receives the task *"get a real-time NVDA quote"*, MCP-discovers `surprise_api` (an independent seller process at its own URL), verifies the seller's ERC-8004 identity on Kite testnet, negotiates the price down from $0.04 to $0.025, settles via x402, and displays the live quote in the dashboard. Then the same flow is repeated against a low-reputation seller (buyer opens harder, saves more). Then a malicious seller raises the price at payment time — the buyer refuses before Passport authorizes and the reputation slashes on-chain.

Every deal is bound by two hashes that work together: an **off-chain deal_hash** the buyer carries in the x402 `extra` field so any mutated 402 response is rejected before Passport authorizes, and an **on-chain dealHash** computed by `DealRecord.recordDeal` over `(buyer, seller, finalPrice, resourceUri, timestamp, rounds)` so the attested record is uniquely keyed and recomputable from on-chain data. Both identify the same deal; they don't need to be byte-equal.

Buyer and seller run as **separate processes at separate URLs** — autonomy isn't claimed in slides, it's deployed.

## Glossary lock (resolved)

Three conflicting hash claims were found across docs and code. Reality on disk (verified by reading the actual files via PowerShell — Cursor's Read tool returned stale snapshots that misled an earlier pass):

- `negotiatorgrid/core/negotiation.py` line 384 — computes a **short off-chain fingerprint**: `hashlib.sha256(f"buyer:seller:{agreed_price}:{step}:{start}").hexdigest()[:16]`. This populates `NegotiationResult.deal_hash` and ends up in `x402 extra.deal_hash`. It exists for mutation detection on the wire, not for on-chain keying.
- `negotiatorgrid/core/attestation.py` line 175 — defines a local `_compute_deal_hash(result)` that computes a 32-byte keccak256 over `(buyer_id, seller_id, final_price_atomic, ts, derived_nonce)`. This used to bridge to the on-chain layer but is now superseded by `DealRecord.recordDeal` computing its own hash.
- `contracts/src/DealRecord.sol` lines 101–110 + 242–251 — the canonical **on-chain `dealHash`**: `keccak256(abi.encodePacked(buyer, seller, finalPrice, resourceUri, timestamp, negotiationRounds))`. This is the storage key for the `_deals` mapping and the value emitted in `DealRecorded`.

**Locked narrative for the recording**: the demo refers to "the deal hash" as the on-chain `dealHash` (6 fields, computed by `DealRecord`) because that's what KiteScan shows and what judges can verify. The off-chain fingerprint is described as "the x402 binding tag" if it ever needs to be named on screen.

`8.3-demo-script.md` Act 4 narration was updated to match this (`keccak256(abi.encodePacked(buyer, seller, finalPrice, resourceUri, timestamp, rounds))` replaces the earlier "transcript hash" wording). `CONTEXT.md` glossary entries for `Deal hash` and `deal_bound_at` were rewritten to reflect both hashes truthfully.

### Future cleanup (post-hackathon, do not attempt this sprint)

The two-hash split is a doc-fixing job, not a correctness bug — it doesn't affect the demo. Post-submission, fold both into a single canonical helper module (`negotiatorgrid.core.deal_hash`) that exposes one function per layer (`x402_binding_tag(...)` and `on_chain_deal_hash(...)`) so future readers don't have to reconstruct the relationship from three files.

## Execution order (each step de-risks the next)

1. **P0-1 → P0-3** — fix glossary on paper; cheap.
2. **P0-4 → P0-7** — deploy contracts. Without these, the CLI and dashboard cannot show real on-chain attestation, which the sponsor's site requires explicitly.
3. **P0-8 → P0-14** — rewrite `demo.py` against the deployed contracts. This locally proves the new flow end-to-end before any cloud deploy. If `demo.py` doesn't work locally, the dashboard won't work either.
4. **P0-15 → P0-19** — deploy 3 services. Once `demo.py` works locally, this is config + smoke-test, not new dev.
5. **P0-20 → P0-27** — dashboard polish, wired against the known-working backend.
6. **P0-28 → P0-32** — record, write, submit.

Rationale: the test pyramid is `demo.py (CLI) → dashboard (UI)`. If the CLI tells the right story, the UI is just a presentation layer. If you start with the UI before the CLI works, every dashboard bug is ambiguous (is it backend or frontend?).
