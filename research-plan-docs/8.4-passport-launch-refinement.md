# Passport Launch Refinement Spec

**Last updated:** April 30, 2026

## Objective

Refine NegotiatorGrid for the launched Kite Agent Passport ecosystem. The finished demo should make clear that NegotiatorGrid is not a competing wallet or payment system. It is the negotiation, trust, and procurement policy layer that creates a safe, typed commercial decision before Kite Agent Passport authorizes payment.

## Product Claim

NegotiatorGrid extends Kite Agent Passport from **authorized agent payments** to **authorized agent procurement**.

Passport controls whether an agent is allowed to spend through identity, Sessions, Delegations, x402 payment authorization, and dashboard audit history. NegotiatorGrid decides whether the agent should spend: who to buy from, what terms are acceptable, whether the negotiated price is fair, and whether the final payment request matches the accepted deal.

## Current Kite Passport Model

Based on the current Passport docs:

- **Sessions** are master budgets with spending rules: total spend, time limits, merchant restrictions, and related policy controls.
- **Delegations** are specific signed payment intents linked to a parent Session.
- **MCP** is the agent integration layer for payer address lookup, payment authorization, OAuth, and user prompting.
- **x402** is the standardized payment flow used by paid services and facilitators.

Implication: NegotiatorGrid should not claim it creates Passport authority. It should claim it produces a Passport-compatible payment intent after negotiation and checks that intent against the user's active Session.

## Updated Pipeline

```text
1. Discovery
   Buyer agent discovers candidate service/provider via MCP or cached registry.

2. Identity + Reputation
   Buyer resolves seller identity and reputation before exposing negotiation context.

3. Negotiation
   NegMAS + strategy policies negotiate price, scope, SLA, and delivery terms.

4. Deal Binding
   Accepted terms are hashed and converted into a typed payment intent:
   buyer, seller, amount, asset, merchant/service, terms hash, expiry.

5. Passport Session Fit
   NegotiatorGrid checks whether the payment intent fits the active Passport Session:
   remaining budget, per-payment cap, allowed merchant/payee, asset/token, TTL.

6. Payment Authorization + Settlement
   Kite Passport/MCP authorizes the payment; x402 carries the payment header;
   Kite Facilitator verifies and settles.

7. Attestation + Reputation
   DealRecord stores the negotiated terms hash, accepted price, round count,
   settlement hash, and reputation feedback.
```

## Demo Acceptance Criteria

- The first screen demonstrates procurement, not a generic landing page.
- The dashboard shows a **Passport Session Fit** panel with:
  - negotiated price
  - remaining Session budget
  - per-payment cap
  - merchant/payee
  - asset/token
  - expiration/TTL
  - pass/fail state
- The narration says: "Passport controls whether the agent can spend; NegotiatorGrid decides whether the deal is worth paying for."
- Live infrastructure is labeled honestly:
  - `Passport MCP live`
  - `Passport-compatible mock`
  - `x402 live`
  - `mock facilitator`
- Any overspend or price-manipulation demo fails before payment authorization, with the failure reason tied to either terms-hash mismatch or Passport Session policy mismatch.

## Boundaries

- Always: keep typed deal fields authoritative over LLM text.
- Always: label mock Passport/x402 paths clearly in the UI and demo script.
- Always: keep `.env`, wallet keys, Passport tokens, and reservation prices out of prompts and logs.
- Ask first: replacing current raw x402 settlement with live Passport MCP calls if credentials or account-specific setup are needed.
- Never: claim live Passport settlement unless it was actually run through Passport/MCP.
