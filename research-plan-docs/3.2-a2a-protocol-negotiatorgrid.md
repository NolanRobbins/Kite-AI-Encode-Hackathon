## 1. AgentCard Specification

### 1.1 Full AgentCard Fields

```typescript
interface AgentCard {
  name: string;                    // Human-readable name
  description: string;             // CommonMark-allowed description
  url: string;                     // Base URL for A2A JSON-RPC endpoint (HTTPS for production)
  provider?: AgentProvider;        // { organization: string, url: string }
  version: string;                 // Semver or provider-defined version
  documentationUrl?: string;       // Link to docs
  capabilities: AgentCapabilities; // See below
  securitySchemes?: { [scheme: string]: SecurityScheme }; // OpenAPI-compatible
  security?: { [scheme: string]: string[] }[];
  defaultInputModes: string[];     // MIME types accepted (e.g., ["text", "text/plain"])
  defaultOutputModes: string[];    // MIME types produced
  skills: AgentSkill[];            // Array of capabilities (min 1)
  supportsAuthenticatedExtendedCard?: boolean;
}
```

**Source**: [A2A Spec §5.5](https://google.github.io/A2A/specification/#55-agentcard-object-structure)

### 1.2 AgentCapabilities

```typescript
interface AgentCapabilities {
  streaming?: boolean;             // SSE support for message/stream
  pushNotifications?: boolean;     // Webhook-based async updates
  stateTransitionHistory?: boolean; // Future: detailed state change history
  extensions?: AgentExtension[];   // ← KEY FOR NEGOTIATORGRID
}
```

### 1.3 AgentExtension (how x402 and NegotiatorGrid declare themselves)

```typescript
interface AgentExtension {
  uri: string;          // Unique URI identifying the extension
  description: string;  // Human-readable description
  required: boolean;    // Whether client MUST support this extension
}
```

**Example — x402 extension declaration in AgentCard:**
```json
{
  "capabilities": {
    "streaming": true,
    "extensions": [
      {
        "uri": "https://github.com/google-a2a/a2a-x402/v0.1",
        "description": "Supports payments using the x402 protocol for on-chain settlement.",
        "required": true
      }
    ]
  }
}
```

**Source**: [a2a-x402 spec §3](https://github.com/google-agentic-commerce/a2a-x402/blob/main/spec/v0.1/spec.md)

### 1.4 AgentSkill

```typescript
interface AgentSkill {
  id: string;              // Unique ID within this agent
  name: string;            // Human-readable name
  description: string;     // What the skill does
  tags?: string[];         // Categorization tags
  examples?: string[];     // Example prompts/queries
  inputModes?: string[];   // Override agent-level input modes
  outputModes?: string[];  // Override agent-level output modes
}
```

### 1.5 Discovery Mechanisms

| Method | How it works |
|--------|-------------|
| Well-Known URI | `GET https://{domain}/.well-known/agent.json` (RFC 8615) |
| Registries/Catalogs | Query curated catalogs (enterprise, public, or domain-specific) |
| Direct Configuration | Pre-configured Agent Card URL or embedded card content |
| x402 Bazaar | Discovery layer via `GET /discovery/resources` on facilitators |

**Blockchain/IPFS storage**: Not currently part of the A2A spec. The spec envisions Registries/Catalogs as the extensible mechanism. NegotiatorGrid could store AgentCard hashes on-chain as attestations, but this is our own addition, not in the base protocol.

**Source**: [A2A Spec §5.2](https://google.github.io/A2A/specification/#52-discovery-mechanisms)

## 2. JSON-RPC 2.0 Message Format

### 2.1 Transport

- All communication over **HTTP(S)**
- Payload format: **JSON-RPC 2.0**
- Content-Type: `application/json`
- Default port: `41241`

### 2.2 Request Format

```json
{
  "jsonrpc": "2.0",
  "id": "req-001",
  "method": "message/send",
  "params": {
    "message": {
      "kind": "message",
      "role": "user",
      "messageId": "msg-uuid-001",
      "contextId": "session-uuid",
      "parts": [
        { "kind": "text", "text": "Generate an image of a sunset" }
      ],
      "metadata": {}
    }
  }
}
```

### 2.3 Response Format

```json
{
  "jsonrpc": "2.0",
  "id": "req-001",
  "result": {
    "kind": "task",
    "id": "task-123",
    "contextId": "session-uuid",
    "status": {
      "state": "completed",
      "message": {
        "kind": "message",
        "role": "agent",
        "messageId": "msg-resp-001",
        "parts": [{ "kind": "text", "text": "Here is your sunset image." }],
        "metadata": {}
      },
      "timestamp": "2026-04-09T05:00:00Z"
    },
    "artifacts": [
      {
        "parts": [{ "kind": "file", "file": { "uri": "https://...", "mimeType": "image/png" } }],
        "name": "sunset.png"
      }
    ]
  }
}
```

### 2.4 Core JSON-RPC Methods

| Method | Purpose | Response |
|--------|---------|----------|
| `message/send` | Send a message, get synchronous Task response | `Task` object |
| `message/stream` | Send message + subscribe to SSE updates | SSE stream of `TaskStatusUpdateEvent` / `TaskArtifactUpdateEvent` |
| `tasks/get` | Query current state of a task by ID | `Task` object |
| `tasks/cancel` | Cancel a running task | Updated `Task` |
| `tasks/resubscribe` | Reconnect to a broken SSE stream | SSE stream |
| `tasks/pushNotificationConfig/set` | Register webhook for push notifications | Confirmation |
| `tasks/pushNotificationConfig/get` | Get current push notification config | Config |

**Source**: [A2A Spec §3, §7](https://google.github.io/A2A/specification/)

## 3. Task Lifecycle: State Machine

### 3.1 TaskState Enum

```
                                   ┌──────────────┐
                                   │  submitted   │ (received, not yet started)
                                   └──────┬───────┘
                                          │
                                          ▼
                                   ┌──────────────┐
                               ┌──►│   working    │◄───────────────┐
                               │   └──────┬───────┘                │
                               │          │                        │
                               │     ┌────┴────┐                   │
                               │     ▼         ▼                   │
                          ┌────────────┐ ┌──────────────┐ ┌────────────────┐
                          │ input-     │ │ auth-        │ │                │
                          │ required   │ │ required     │ │  completed     │
                          │ (paused)   │ │ (paused)     │ │  (terminal)    │
                          └─────┬──────┘ └──────┬───────┘ └────────────────┘
                                │               │
                                └──────┬────────┘
                                       │ (client provides input/auth)
                                       ▼
                                   ┌──────────────┐
                                   │   working    │
                                   └──────┬───────┘
                                          │
                            ┌─────────────┼─────────────┐
                            ▼             ▼             ▼
                     ┌──────────┐  ┌──────────┐  ┌──────────┐
                     │ completed│  │  failed  │  │ canceled │
                     │(terminal)│  │(terminal)│  │(terminal)│
                     └──────────┘  └──────────┘  └──────────┘
```

| State | Terminal? | Description |
|-------|-----------|-------------|
| `submitted` | No | Task received, acknowledged, not yet started |
| `working` | No | Actively being processed |
| `input-required` | No (pause) | Agent needs more input from client |
| `auth-required` | No (pause) | Agent needs authentication from client |
| `completed` | Yes | Finished successfully |
| `failed` | Yes | Terminated due to error |
| `canceled` | Yes | Canceled by client or server |
| `rejected` | Yes | Rejected by remote agent |
| `unknown` | Yes | Task ID invalid or expired |

**Key for NegotiatorGrid**: The `input-required` state is what the x402 extension uses for `payment-required`. We can similarly use it for `negotiation-required` — the agent pauses and requests negotiation input.

**Source**: [A2A Spec §6.3](https://google.github.io/A2A/specification/#63-taskstate-enum)

## 4. SSE Streaming — Real-Time Negotiation Updates

### 4.1 How SSE Works in A2A

1. Client calls `message/stream` (JSON-RPC method)
2. Server responds with `HTTP 200 OK`, `Content-Type: text/event-stream`
3. Server pushes SSE events with `data` field containing JSON-RPC Response objects

### 4.2 Event Types

| Event Type | Purpose | Content |
|-----------|---------|---------|
| `TaskStatusUpdateEvent` | State changes | `{ kind: "status-update", taskId, contextId, status: TaskStatus, final: boolean }` |
| `TaskArtifactUpdateEvent` | Partial/final results | `{ kind: "artifact-update", taskId, contextId, artifact: Artifact }` |

### 4.3 SSE for NegotiatorGrid Negotiation Rounds

For streaming negotiation round updates in real-time:

```
Client calls: message/stream with initial negotiation request
Server streams:
  data: {"jsonrpc":"2.0","id":"req-001","result":{"kind":"status-update","taskId":"task-nego-1","status":{"state":"working","message":{"role":"agent","parts":[{"kind":"data","data":{"negotiation_round":1,"offer":0.05,"counter":0.03}}],"metadata":{"x402.negotiation.status":"counter-offer"}}},"final":false}}

  data: {"jsonrpc":"2.0","id":"req-001","result":{"kind":"status-update","taskId":"task-nego-1","status":{"state":"working","message":{"role":"agent","parts":[{"kind":"data","data":{"negotiation_round":2,"offer":0.04,"counter":0.035}}],"metadata":{"x402.negotiation.status":"counter-offer"}}},"final":false}}

  data: {"jsonrpc":"2.0","id":"req-001","result":{"kind":"status-update","taskId":"task-nego-1","status":{"state":"input-required","message":{"role":"agent","parts":[{"kind":"data","data":{"negotiation_round":3,"agreed_price":0.038,"deal_hash":"0xabc..."}}],"metadata":{"x402.negotiation.status":"deal-agreed","x402.payment.status":"payment-required","x402.payment.required":{...}}}},"final":false}}
```

The SSE connection stays open across negotiation rounds. Each round is a `TaskStatusUpdateEvent` with `state: "working"`. When negotiation concludes, the server transitions to `input-required` with the payment requirements.

**Source**: [A2A Streaming & Async docs](https://a2a-protocol.org/latest/topics/streaming-and-async/)

## 5. Custom Message Types — NegotiatorGrid Extensibility

### 5.1 Can A2A Carry Custom Message Types?

**YES — via three mechanisms:**

#### Mechanism 1: Message `metadata` (recommended for NegotiatorGrid)

Every `Message` object has a `metadata?: Record<string, any>` field. The x402 extension already uses this pattern:

```json
{
  "metadata": {
    "x402.payment.status": "payment-required",
    "x402.payment.required": { ... }
  }
}
```

**NegotiatorGrid extension metadata keys:**

```json
{
  "metadata": {
    "negotiatorgrid.status": "negotiate-request",
    "negotiatorgrid.offer": {
      "price": "35000",
      "asset": "0x...",
      "deadline_rounds": 10,
      "strategy_hint": "time_dependent",
      "deal_hash": null
    }
  }
}
```

| Status Value | Direction | Description |
|-------------|-----------|-------------|
| `negotiate-request` | Client → Seller | Initial price inquiry |
| `counter-offer` | Either direction | Counter-proposal with new price |
| `deal-agreed` | Either direction | Both parties accepted |
| `deal-rejected` | Either direction | Walkaway — no deal |
| `deal-contract` | Seller → Client | Final terms + deal_hash, transitions to payment |

#### Mechanism 2: `DataPart` in Message Parts

The `DataPart` type (`kind: "data"`) carries structured JSON. NegotiatorGrid negotiation messages can be encoded as DataParts:

```json
{
  "kind": "data",
  "data": {
    "type": "NEGOTIATE_REQUEST",
    "buyer_id": "0xBuyerAddress",
    "resource": "/api/premium-data",
    "initial_offer": "25000",
    "max_rounds": 10,
    "reservation_price": "50000",
    "strategy": "time_dependent_concession"
  },
  "metadata": {
    "schema": "negotiatorgrid://schemas/negotiate-request/v1"
  }
}
```

#### Mechanism 3: A2A Extensions (formal declaration)

NegotiatorGrid registers as a proper A2A extension with its own URI:

```json
{
  "capabilities": {
    "extensions": [
      {
        "uri": "https://negotiatorgrid.dev/extension/v1",
        "description": "Agent-to-agent price negotiation protocol with game-theoretic strategies",
        "required": true
      },
      {
        "uri": "https://github.com/google-a2a/a2a-x402/v0.1",
        "description": "x402 payment settlement",
        "required": true
      }
    ]
  }
}
```

Extension activation is requested via HTTP header:
```
X-A2A-Extensions: https://negotiatorgrid.dev/extension/v1, https://github.com/google-a2a/a2a-x402/v0.1
```

**Source**: [A2A Extensions Blog](https://developers.googleblog.com/en/a2a-extensions-empowering-custom-agent-functionality/), [A2A Spec §6.4 Message metadata](https://google.github.io/A2A/specification/#64-message-object)

## 6. a2a-x402: Payment Flow (payment-required → payment-submitted → payment-completed)

### 6.1 The Three-Step Payment Protocol

The a2a-x402 extension defines a state machine layered on top of A2A Task states:

```
[*] ──► PAYMENT_REQUIRED ──► PAYMENT_SUBMITTED ──► PAYMENT_VERIFIED ──► PAYMENT_COMPLETED ──► [*]
                │                                       │
                ├──► PAYMENT_REJECTED ──► [*]           ├──► PAYMENT_FAILED ──► [*]
```

### 6.2 Step-by-Step with Exact JSON-RPC Messages

**Step 1: Client requests service**
```json
{
  "jsonrpc": "2.0",
  "method": "message/send",
  "id": "req-001",
  "params": {
    "message": {
      "kind": "message",
      "role": "user",
      "messageId": "msg-001",
      "parts": [{ "kind": "text", "text": "Generate an image of a sunset" }]
    }
  }
}
```

**Step 2: Merchant responds with payment-required (Task state: `input-required`)**
```json
{
  "jsonrpc": "2.0",
  "id": "req-001",
  "result": {
    "kind": "task",
    "id": "task-123",
    "status": {
      "state": "input-required",
      "message": {
        "kind": "message",
        "role": "agent",
        "messageId": "msg-002",
        "parts": [{ "kind": "text", "text": "Payment is required to generate the image." }],
        "metadata": {
          "x402.payment.status": "payment-required",
          "x402.payment.required": {
            "x402Version": 1,
            "accepts": [{
              "scheme": "exact",
              "network": "base",
              "resource": "https://api.example.com/generate-image",
              "asset": "0x833589fCD6eDb6E08f4c7C32D4f71b54bda02913",
              "payTo": "0xServerWalletAddress",
              "maxAmountRequired": "48240000",
              "maxTimeoutSeconds": 600,
              "extra": { "name": "USD Coin", "version": 2 }
            }]
          }
        }
      }
    }
  }
}
```

**Step 3: Client signs payment and submits (payment-submitted)**
```json
{
  "jsonrpc": "2.0",
  "method": "message/send",
  "id": "req-003",
  "params": {
    "message": {
      "kind": "message",
      "taskId": "task-123",
      "role": "user",
      "messageId": "msg-003",
      "parts": [{ "kind": "text", "text": "Here is the payment authorization." }],
      "metadata": {
        "x402.payment.status": "payment-submitted",
        "x402.payment.payload": {
          "x402Version": 1,
          "scheme": "exact",
          "network": "base",
          "payload": {
            "signature": "0x...",
            "authorization": {
              "from": "0xBuyerAddress",
              "to": "0xServerWalletAddress",
              "value": "48240000",
              "validAfter": "0",
              "validBefore": "1712700000",
              "nonce": "0x..."
            }
          }
        }
      }
    }
  }
}
```

**Step 4: Merchant verifies, settles, and returns result**
```json
{
  "jsonrpc": "2.0",
  "id": "req-003",
  "result": {
    "kind": "task",
    "id": "task-123",
    "status": {
      "state": "completed",
      "message": {
        "kind": "message",
        "role": "agent",
        "messageId": "msg-004",
        "parts": [{ "kind": "text", "text": "Payment successful. Your image is ready." }],
        "metadata": {
          "x402.payment.status": "payment-completed",
          "x402.payment.receipts": [{
            "success": true,
            "transaction": "0xabc123...",
            "network": "base",
            "payer": "0xBuyerAddress"
          }]
        }
      }
    },
    "artifacts": [
      {
        "parts": [{ "kind": "file", "file": { "uri": "https://...", "mimeType": "image/png" } }],
        "name": "sunset.png"
      }
    ]
  }
}
```

### 6.3 x402.payment.status Values

| Value | Direction | A2A Task State | Description |
|-------|-----------|----------------|-------------|
| `payment-required` | Merchant → Client | `input-required` | Payment requirements sent |
| `payment-submitted` | Client → Merchant | (message) | Signed payload submitted |
| `payment-rejected` | Client → Merchant | (message) | Client rejects all payment options |
| `payment-verified` | Merchant internal | `working` | Facilitator verified signature |
| `payment-completed` | Merchant → Client | `working` or `completed` | Settlement confirmed on-chain |
| `payment-failed` | Merchant → Client | `failed` | Verification or settlement failed |

**Source**: [a2a-x402 spec §4–§6](https://github.com/google-agentic-commerce/a2a-x402/blob/main/spec/v0.1/spec.md)

## 7. x402_a2a Python Library — How It Bridges A2A with x402

### 7.1 Library Architecture

```
python/x402_a2a/src/x402_a2a/
├── __init__.py
├── core/
│   ├── agent.py       # create_x402_agent_card() — builds AgentCards with x402 extension
│   ├── helpers.py     # Helper utilities
│   ├── merchant.py    # create_payment_requirements() — converts prices to PaymentRequirements
│   ├── protocol.py    # verify_payment() + settle_payment() — facilitator bridge
│   └── utils.py       # Utility functions
```

### 7.2 Key Functions

**`create_x402_agent_card()`** — Creates an AgentCard with x402 extension declared:

```python
from x402_a2a.core.agent import create_x402_agent_card

card = create_x402_agent_card(
    name="NegotiatorGrid Seller",
    description="AI service with negotiated pricing",
    url="https://seller.negotiatorgrid.dev",
    version="1.0.0",
    streaming=True,
)
# Automatically adds AgentExtension with uri="https://github.com/google-a2a/a2a-x402/v0.1"
```

**`create_payment_requirements()`** — Converts human-readable prices to x402 PaymentRequirements:

```python
from x402_a2a.core.merchant import create_payment_requirements

requirements = create_payment_requirements(
    price="$0.05",                    # USD amount → converts to atomic USDC units
    pay_to_address="0xSellerAddress",
    resource="/api/premium-data",
    network="base",
    description="Premium data access",
    scheme="exact",
    max_timeout_seconds=600,
)
# Returns PaymentRequirements with maxAmountRequired="50000", asset=USDC address, etc.
```

**`verify_payment()` and `settle_payment()`** — Bridge to x402 facilitator:

```python
from x402_a2a.core.protocol import verify_payment, settle_payment

# Verify
verify_result = await verify_payment(payment_payload, payment_requirements, facilitator_client)
# → VerifyResponse { is_valid: bool, invalid_reason?: str, payer?: str }

# Settle
settle_result = await settle_payment(payment_payload, payment_requirements, facilitator_client)
# → SettleResponse { success: bool, transaction: str, network: str, payer?: str }
```

**Source**: [a2a-x402 Python library](https://github.com/google-agentic-commerce/a2a-x402/tree/main/python/x402_a2a/src/x402_a2a/core)

## 8. Google Codelabs — Multi-Seller Agent Pattern

### 8.1 Architecture

The codelab deploys a **purchasing concierge** (A2A Client) that communicates with multiple seller agents (A2A Servers):

```
User → [Purchasing Concierge (ADK, Agent Engine)]
            ├──► [Burger Seller Agent (CrewAI, Cloud Run)] ← A2A Server
            └──► [Pizza Seller Agent (Langgraph, Cloud Run)] ← A2A Server
```

Key properties:
- **Each seller is a separate service** deployed on Cloud Run
- **Each uses a different agent framework** (CrewAI, Langgraph, ADK) — A2A abstracts this away
- **Discovery**: Client fetches `/.well-known/agent.json` from each seller at startup
- **Orchestration**: Concierge agent has `send_task` tool that routes to the right seller based on skill matching

### 8.2 Multi-Seller Orchestration Pattern

```python
# Concierge agent prompt includes remote agent info:
"""
Agents:
{self.agents}   # ← JSON of all discovered AgentCards

Current active seller agent: {current_agent["active_agent"]}
"""

# send_task tool routes to correct seller:
async def send_task(self, agent_name: str, task: str, tool_context: ToolContext):
    client = self.remote_agent_connections[agent_name]
    payload = {
        "message": {
            "role": "user",
            "parts": [{"type": "text", "text": task}],
            "messageId": message_id,
            "contextId": session_id,
        }
    }
    message_request = SendMessageRequest(
        id=message_id,
        params=MessageSendParams.model_validate(payload)
    )
    send_response = await client.send_message(message_request=message_request)
```

### 8.3 Key Takeaways for NegotiatorGrid

1. **Multiple seller agents can coexist** — the concierge discovers them all via AgentCards
2. **Agent framework doesn't matter** — A2A normalizes the interface
3. **Session continuity** — `contextId` maintains conversation state across multiple `message/send` calls
4. **Tool-based routing** — the concierge LLM decides which seller to contact based on the user's request and agent skills

**Source**: [Google Codelabs A2A Purchasing Concierge](https://codelabs.developers.google.com/intro-a2a-purchasing-concierge)

## 9. NegotiatorGrid Injection Point — Where Negotiation Enters the a2a-x402 Flow

### 9.1 The Standard a2a-x402 Flow (without negotiation)

```
1. Client → Merchant: "Generate an image" (message/send)
2. Merchant → Client: Task{state: input-required, metadata: {x402.payment.status: "payment-required"}}
3. Client signs payment
4. Client → Merchant: Message{metadata: {x402.payment.status: "payment-submitted", x402.payment.payload: ...}}
5. Merchant verifies + settles
6. Merchant → Client: Task{state: completed, artifacts: [...], metadata: {x402.payment.status: "payment-completed"}}
```

### 9.2 The NegotiatorGrid-Modified Flow (with negotiation)

**Negotiation inserts between Steps 1 and 2.** The Merchant doesn't immediately return `payment-required` — instead, it enters a negotiation loop:

```
1.  Client → Merchant: "Generate an image" (message/send)

    ┌─── NEGOTIATION PHASE (NegotiatorGrid Extension) ───┐
    │                                                     │
2a. │ Merchant → Client: Task{state: input-required,      │
    │   metadata: {                                       │
    │     negotiatorgrid.status: "negotiate-request",     │
    │     negotiatorgrid.offer: {                         │
    │       price: "50000",   // Opening ask: $0.05       │
    │       resource: "/generate-image",                  │
    │       max_rounds: 10,                               │
    │       deadline: "2026-04-09T05:10:00Z"              │
    │     }                                               │
    │   }                                                 │
    │ }                                                   │
    │                                                     │
```

### 9.4 How Task States Map

| NegotiatorGrid Phase | A2A Task State | x402 Payment Status | NegotiatorGrid Status |
|---------------------|----------------|--------------------|-----------------------|
| Service request | `submitted` | — | — |
| Negotiation opening | `input-required` | — | `negotiate-request` |
| Counter-offer rounds | `input-required` | — | `counter-offer` |
| Deal agreed → payment | `input-required` | `payment-required` | `deal-agreed` |
| Payment submitted | `working` | `payment-submitted` | — |
| Payment verified | `working` | `payment-verified` | — |
| Payment completed + delivery | `completed` | `payment-completed` | — |
| Negotiation walkaway | `rejected` or `failed` | — | `deal-rejected` |
| Payment failed | `failed` | `payment-failed` | — |

### 9.5 Extension Coexistence

NegotiatorGrid and x402 are independent A2A extensions that compose cleanly:

```json
{
  "capabilities": {
    "streaming": true,
    "extensions": [
      {
        "uri": "https://negotiatorgrid.dev/extension/v1",
        "description": "Agent-to-agent price negotiation with game-theoretic strategies",
        "required": true
      },
      {
        "uri": "https://github.com/google-a2a/a2a-x402/v0.1",
        "description": "x402 on-chain payment settlement",
        "required": true
      }
    ]
  }
}
```

Both use `Message.metadata` with namespaced keys (`negotiatorgrid.*` and `x402.payment.*`). They don't conflict because they operate in different phases of the Task lifecycle.

## Open Questions

1. **SSE during negotiation**: Should negotiation rounds use `message/stream` (persistent SSE) or sequential `message/send` calls? SSE is more efficient for rapid back-and-forth, but the A2A spec models `message/stream` as primarily server→client streaming. For true bilateral negotiation, sequential `message/send` calls (one per round) may be cleaner, using `taskId` to link rounds.

2. **Negotiation timeout**: A2A's `maxTimeoutSeconds` in PaymentRequirements is for payment validity. NegotiatorGrid needs its own `negotiation_deadline` in the extension metadata to bound negotiation rounds.

3. **Multi-seller negotiation**: The purchasing concierge pattern supports multiple sellers. NegotiatorGrid could run parallel negotiations with N sellers simultaneously, choosing the best deal. This maps to parallel `message/send` calls to different A2A servers, each maintaining its own `taskId`.

4. **AgentCard storage on-chain**: The A2A spec doesn't specify blockchain/IPFS storage for AgentCards. NegotiatorGrid could post AgentCard hashes on Kite L1 as on-chain attestations (e.g., via EAS or a custom registry contract), enabling trustless discovery. This is an extension beyond the A2A spec.

5. **Kite MCP integration**: Kite's MCP server (`https://mcp.prod.gokite.ai/`) could be used for agent tool discovery, while A2A handles agent-to-agent negotiation. The two protocols are complementary per the A2A spec's own guidance.
