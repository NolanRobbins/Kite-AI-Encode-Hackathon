## Key Findings

- The x402 protocol defines a 402-Payment-Required HTTP flow where payment is embedded as an `X-PAYMENT` header containing a base64-encoded EIP-3009 `TransferWithAuthorization` signature, enabling autonomous agent payment without a human approval step.
- ERC-8004 extends ERC-721: each registered agent is a non-fungible token whose `tokenURI` points to a JSON AgentCard containing endpoint, pricing, SLA parameters, and wallet address.
- NegMAS `SAOMechanism` supports time-limited alternating-offers with arbitrary utility functions over typed issue spaces; the `AspirationNegotiator` base class provides a tuneable Boulware–Zeuthen concession curve controllable via `aspiration_type` and `max_aspiration`.
- The Kite L1 facilitator contract (`0x12343e649e6b2b2b77649DFAb88f103c02F3C78b`) acts as the payment escrow; the buyer's AA wallet session key is scoped to exactly the agreed price and expiry, preventing overpayment.
- On-chain attestation via the `NegotiationRecorded` event provides a complete, tamper-evident audit trail: `(negotiation_id, tool_metadata_hash, agreed_price, payment_hash, output_hash, transcript_uri)`.
- IPFS transcript upload gives the on-chain event a human-readable counterpart; the `transcript_uri` links the blockchain record to the full negotiation history and opponent model snapshot.
- Opponent model cross-session memory allows the buyer agent to classify sellers as "tough", "moderate", or "soft" based on historical concession deltas, improving negotiation efficiency over time.

## Step-by-Step Reference Tables

### Step 1 — DISCOVER

| Attribute | Details |
|-----------|---------|
| Function signature | `async def discover(self, service_query: str) -> List[SellerCandidate]` |
| Key library | `web3.py` (AsyncWeb3 + AsyncHTTPProvider), `mcp` Python SDK |
| On-chain call | `registry.functions.totalSupply().call()` then `tokenURI(i).call()` for each token |
| Expected latency | ~500 ms on-chain (parallel gather); ~200 ms MCP fallback |
| Failure mode | Registry contract unreachable (RPC down, wrong address) |
| Fallback | `_discover_via_mcp()` — connects to x402Scout MCP server, calls `list_tools`, filters by service_query |
| On-chain attestation | None (read-only) |
| Output | `List[SellerCandidate]` with `agent_id`, `token_uri` populated |
| Demo visualization | Table of discovered agents: `agent_id`, `token_uri`, `name` |

### Step 2 — EVALUATE

| Attribute | Details |
|-----------|---------|
| Function signature | `async def evaluate(self, candidates: List[SellerCandidate]) -> List[SellerCandidate]` |
| Key library | `httpx` (AgentCard HTTP/IPFS fetch), `web3.py` (Reputation Registry) |
| Off-chain call | `GET {token_uri}` → JSON AgentCard with `endpoint`, `asking_price`, `min_price`, `sla_*` |
| On-chain call | `reputationRegistry.functions.getReputation(wallet_address).call()` → `(score, totalDeals, successfulDeals)` |

| On-chain attestation | None (read-only) |
| Output | Candidates with `agent_card`, `reputation_score`, `asking_price`, `sla_terms` populated |
| Demo visualization | Reputation leaderboard with score bars |

---

### Step 3 — RANK

| Attribute | Details |
|-----------|---------|
| Function signature | `def rank(self, candidates: List[SellerCandidate]) -> List[SellerCandidate]` |
| Key library | Pure Python (no external dependency; numpy optional for larger candidate sets) |
| Algorithm | `utility = 0.40*price_score + 0.30*rep_score + 0.20*sla_score + 0.10*history_score` |
| Price score | `1 - (asking_price / max_price)` — inverted so lower price = higher score |
| SLA score | `min_sla_latency / candidate_sla_latency` — normalised, lower latency = higher score |
| History score | `successful_deals / total_deals`; defaults to 0.5 (neutral) for agents with no history |
| Expected latency | <10 ms (local computation) |
| Failure mode | All candidates have identical scores → deterministic tie-break by reputation |
| On-chain attestation | None (local) |
| Output | Candidates sorted descending by `utility_score` |
| Demo visualization | Ranked leaderboard with utility breakdown per dimension |

**Weight rationale**: Price dominates (0.40) since this is a payment flow; reputation second (0.30) to avoid rogue sellers; SLA third (0.20) for quality assurance; history last (0.10) because many agents will be new.

---

### Step 4 — NEGOTIATE

| Attribute | Details |
|-----------|---------|
| Function signature | `async def negotiate(self, seller: SellerCandidate) -> Optional[DealContract]` |
| Key library | `negmas` — `SAOMechanism`, `make_issue`, `LinearAdditiveUtilityFunction`, `AspirationNegotiator` |
| Negotiation type | Alternating-offers protocol (SAO) with time limit 30 s, max 10 rounds |
| Issues | `price` (int, micro-USDT), `sla_latency_ms` (int, 500–5000), `sla_uptime_pct` (float, 95–99.9) |
| Buyer strategy | `NegGridBuyerNegotiator(AspirationNegotiator)` — Boulware aspiration curve, exponent tuned by opponent stance |
| Opponent model | `NegGridOpponentModel` — records offer history, computes concession deltas, classifies stance as "tough" / "moderate" / "soft", Bayesian reservation estimate |
| Seller side (demo) | Stub `AspirationNegotiator` (soft/moderate). In production: seller's remote agent via x402 negotiation endpoint |
| Expected latency | ~100–500 ms for 5–10 rounds (blocking `session.run()` in executor) |
| Failure mode | No agreement in 10 rounds / 30 s timeout → returns `None`, buyer retries with next-ranked seller |
| Fallback | Try up to 3 sellers from ranked list |
| On-chain attestation | `negotiation_id` (UUID), `tool_metadata_hash` (SHA-256 of seller metadata + issue space) |
| Output | `DealContract` with `negotiation_id`, `agreed_price`, `sla_terms`, `expiry` |
| Demo visualization | Live offer/counter-offer feed; convergence chart showing bid curves |

**Aspiration function**:
```
aspiration(t) = 1 - t^exponent
  where exponent = 0.3 (tough seller), 0.5 (moderate), 0.8 (soft seller)
```
A smaller exponent means slower concession (Boulware behaviour) when facing a tough opponent.

## Opponent Model Design

The `NegGridOpponentModel` is a lightweight cross-session memory that persists between `run()` calls via the `_opponent_models` dict keyed by seller wallet address.

```
Offer history:   [1000, 850, 780, 720]
Concession Δs:  [150, 70, 60]         ← shrinking → tough stance
Avg Δ:          93.3  → stance = "moderate" (threshold: <500 tough, <2000 moderate)

Bayesian reservation estimate:
  reservation ≈ last_offer − (avg_Δ × remaining_rounds × 0.5)
              ≈ 720 − (93.3 × 1.5 × 0.5) ≈ 650
```

Aspiration exponent mapping:

| Stance | Exponent | Concession rate | Behaviour |
|--------|----------|-----------------|-----------|
| tough | 0.3 | Very slow | Hold near max willingness-to-pay |
| moderate | 0.5 | Medium | Standard Boulware curve |
| soft | 0.8 | Faster | Concede earlier to close deal |

## Latency Budget

End-to-end latency for a single successful 8-step loop:

| Step | Description | Min | Typical | Max |
|------|-------------|-----|---------|-----|
| 1 DISCOVER | ERC-8004 registry scan | 200 ms | 500 ms | 1,500 ms |
| 2 EVALUATE | AgentCard fetch + reputation | 400 ms | 800 ms | 2,000 ms |
| 3 RANK | Local utility computation | <1 ms | 5 ms | 20 ms |
| 4 NEGOTIATE | 5–10 round SAO | 100 ms | 300 ms | 500 ms |
| 5 COMMIT | EIP-712 sign + session key tx | 500 ms | 1,200 ms | 3,000 ms |
| 6 EXECUTE | x402 HTTP + on-chain settle | 500 ms | 1,200 ms | 4,000 ms |
| 7 VERIFY | Local SLA check | <1 ms | 5 ms | 50 ms |
| 8 LEARN | IPFS upload + attestation tx | 1,000 ms | 2,500 ms | 5,000 ms |
| **TOTAL** | | **~2.7 s** | **~6.5 s** | **~16 s** |

Steps 1 and 2 are parallelised internally (asyncio.gather). Steps 5, 6, and 8 are the on-chain bottlenecks. In demo mode with the Kite testnet, block times of ~2 s mean step 8 typically dominates.
