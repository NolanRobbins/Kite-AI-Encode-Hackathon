## Contract 1: DealRecord Attestation Contract

### Purpose

Stores on-chain attestations for completed negotiations, linking the negotiation outcome to the x402 payment settlement. This creates a permanent, auditable record that both agents can reference for dispute resolution and reputation building.

### Solidity Interface

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.26;

/// @title IDealRecord
/// @notice On-chain attestation of NegotiatorGrid negotiation outcomes
/// @dev Stores deal terms and links to x402 settlement transactions
interface IDealRecord {

    // ========================================================================
    // STRUCTS
    // ========================================================================

    struct SLATerms {
        uint64 responseTimeMs;      // Max response time promised (ms)
        uint64 availabilityBps;     // Uptime guarantee in basis points (9900 = 99%)
        uint64 validityPeriodSecs;  // How long the deal terms are valid
    }

    struct DealAttestation {
        bytes32 dealHash;           // keccak256(buyer, seller, price, resource, ts, nonce)
        address buyer;              // Buyer agent wallet address
        address seller;             // Seller agent wallet address
        uint256 buyerAgentId;       // ERC-8004 agentId of buyer (0 if not registered)
        uint256 sellerAgentId;      // ERC-8004 agentId of seller (0 if not registered)
        string resourceUri;         // Resource being purchased
        uint256 openingBuyerPrice;  // Buyer's opening offer (atomic units)
        uint256 openingSellerPrice; // Seller's opening ask (atomic units)
        uint256 finalPrice;         // Agreed price (atomic units)
        uint8 negotiationRounds;    // Number of rounds to agreement
        SLATerms sla;              // Service-level agreement terms
        bytes32 x402TxHash;         // x402 settlement transaction hash (0x0 if pending)
        uint64 timestamp;           // Block timestamp of attestation
        bool settled;               // Whether x402 payment has settled
    }

    // ========================================================================
    // EVENTS
    // ========================================================================

    event DealRecorded(
        bytes32 indexed dealHash,
        address indexed buyer,
        address indexed seller,
        uint256 finalPrice,
        uint8 negotiationRounds
    );

    event DealSettled(
        bytes32 indexed dealHash,
        bytes32 x402TxHash
    );

    event ReputationUpdated(
        bytes32 indexed dealHash,
        address indexed agent,
        int128 score,
        string tag
    );

    // ========================================================================
    // WRITE FUNCTIONS
    // ========================================================================

    /// @notice Record a completed negotiation deal
    /// @param attestation The deal attestation data
    /// @return dealHash The unique identifier for this deal
    function recordDeal(DealAttestation calldata attestation) external returns (bytes32 dealHash);

    /// @notice Mark a deal as settled with the x402 transaction hash
    /// @param dealHash The deal to update
    /// @param x402TxHash The on-chain settlement transaction hash
    function settleDeal(bytes32 dealHash, bytes32 x402TxHash) external;

    /// @notice Update reputation scores for both agents after deal completion
    /// @param dealHash The deal to update reputation for
    /// @param buyerScore Buyer's performance score (-128 to 127)
    /// @param sellerScore Seller's performance score (-128 to 127)
    /// @param tag Reputation category (e.g., "pricing_fairness", "delivery_speed")
    function updateReputation(
        bytes32 dealHash,
        int128 buyerScore,
        int128 sellerScore,
        string calldata tag
    ) external;

    // ========================================================================
    // READ FUNCTIONS
    // ========================================================================

    /// @notice Get a deal attestation by hash
    function getDeal(bytes32 dealHash) external view returns (DealAttestation memory);

    /// @notice Get all deals for an agent address
    function getDealsByAgent(address agent) external view returns (bytes32[] memory dealHashes);

    /// @notice Get deal count for an agent
    function getDealCount(address agent) external view returns (uint256);

    /// @notice Get average negotiation rounds for an agent
    function getAvgRounds(address agent) external view returns (uint256);

    /// @notice Get total volume traded by an agent
    function getTotalVolume(address agent) external view returns (uint256);

    /// @notice Verify a deal hash matches the stored attestation
    function verifyDealHash(bytes32 dealHash, DealAttestation calldata attestation) external pure returns (bool);
}
```

### Implementation Notes

- `dealHash` is computed off-chain as `keccak256(abi.encodePacked(buyer, seller, finalPrice, resourceUri, timestamp, nonce))` and verified on-chain
- Only the `buyer` or `seller` of a deal can call `settleDeal()` and `updateReputation()`
- Gas optimization: `resourceUri` is stored as `bytes32` hash on-chain, full URI emitted in event
- The `SLATerms` struct is packed into a single storage slot (64+64+64 = 192 bits < 256 bits)

## Contract 2: ERC-8004 Agent Identity Registration

### ERC-8004 Overview

ERC-8004 defines three registries deployed as per-chain singletons:

| Registry | Purpose | Base |
|----------|---------|------|
| **Identity Registry** | Agent registration as ERC-721 NFTs | ERC-721 + URIStorage |
| **Reputation Registry** | Structured feedback (score + tags + URI) | Custom |
| **Validation Registry** | Independent verification requests/responses | Custom |

## Contract 3: AA Wallet with Dynamic Spending Rules

### Architecture

Kite Agent Passport uses **Privy AA wallets** (ERC-4337). Session keys control spending limits. NegotiatorGrid needs to update these limits after each negotiation.

### Session Key Pattern

Session keys are **temporary, scoped permissions** granted to an app or agent. They're implemented via wallet-specific modules (not standardized — each AA wallet has its own approach).

```solidity
/// @title ISessionKeyManager
/// @notice Interface for managing session keys with dynamic spending rules
/// @dev Not a standard — modeled after common AA session key implementations
interface ISessionKeyManager {

    struct SessionKeyRule {
        address sessionKey;          // The key authorized to sign on behalf of the wallet
        uint256 valueLimit;          // Max value per transaction (atomic units)
        uint256 dailyLimit;          // Max total value per day
        uint256 validAfter;          // Unix timestamp — key not valid before
        uint256 validUntil;          // Unix timestamp — key expires after
        address[] allowedTargets;    // Contract addresses the key can interact with
        bytes4[] allowedSelectors;   // Function selectors allowed
    }

    event SessionKeyAdded(address indexed wallet, address indexed sessionKey, uint256 valueLimit);
    event SessionKeyUpdated(address indexed wallet, address indexed sessionKey, uint256 newValueLimit);
    event SessionKeyRevoked(address indexed wallet, address indexed sessionKey);

    /// @notice Add a new session key with spending rules
    function addSessionKeyRule(SessionKeyRule calldata rule) external;

    /// @notice Update an existing session key's value limit
    /// @dev Called after each negotiation to set limit = negotiated_price
    function updateSessionKeyLimit(address sessionKey, uint256 newValueLimit) external;

    /// @notice Revoke a session key
    function revokeSessionKey(address sessionKey) external;

    /// @notice Get current rules for a session key
    function getSessionKeyRule(address sessionKey) external view returns (SessionKeyRule memory);

    /// @notice Check if a session key is valid and within limits
    function validateSessionKey(address sessionKey, uint256 value, address target, bytes4 selector)
        external view returns (bool);
}
```

### NegotiatorGrid Usage Pattern

```python
# After negotiation concludes with agreed_price:

async def update_wallet_for_deal(wallet_contract, session_key, deal):
    """Update AA wallet spending limit to match negotiated price."""
    
    # Build the session key update transaction
    tx = wallet_contract.functions.updateSessionKeyLimit(
        sessionKey=session_key,
        newValueLimit=deal.agreed_price  # e.g., 38000 atomic USDC
    ).build_transaction({
        "from": wallet_owner,
        "nonce": await w3.eth.get_transaction_count(wallet_owner),
    })
    
    # Sign and send (or package as UserOperation for ERC-4337)
    signed = w3.eth.account.sign_transaction(tx, private_key)
    tx_hash = await w3.eth.send_raw_transaction(signed.rawTransaction)
    
    return tx_hash

# Flow:
# 1. Before negotiation: session key has high limit (max budget)
# 2. Negotiation concludes at $0.038
# 3. updateSessionKeyLimit(sessionKey, 38000)
# 4. Now the session key can only sign payments up to 38000
# 5. x402 payment proceeds with this constrained key
# 6. After deal: optionally revoke or update for next negotiation
```

### Kite-Specific Considerations

Kite Agent Passport uses **Privy AA wallets** with the following constraints:
- Wallet support: Privy AA wallet only (as of testnet)
- Session types: Long-term and one-time
- The session key management may be handled by Privy's SDK rather than a direct smart contract call

For the hackathon demo, a simplified approach:
1. Use a standard EOA for the buyer agent (simpler)
2. Implement the `SessionKeyManager` as a standalone contract that wraps spending authorization
3. The x402 `BeforePaymentCreationHook` checks the session key's `valueLimit` before signing

**Source**: [ERC-4337 Session Keys](https://docs.erc4337.io/smart-accounts/session-keys-and-delegation.html), [Kite Testnet Notice](https://docs.gokite.ai/kite-agent-passport/testnet-notice)

## Deployment Plan

### Deployment Order

```
1. IdentityRegistry (ERC-721)        → agents register here first
2. ReputationRegistry                 → initialized with IdentityRegistry address
3. DealRecord                         → initialized with IdentityRegistry + ReputationRegistry
4. SessionKeyManager (optional)       → standalone or integrated with AA wallet
```

### Deployment Script (Hardhat Ignition)

```typescript
// ignition/modules/NegotiatorGrid.ts
import { buildModule } from "@nomicfoundation/hardhat-ignition/modules";

const NegotiatorGridModule = buildModule("NegotiatorGrid", (m) => {
  // 1. Deploy Identity Registry
  const identityRegistry = m.contract("IdentityRegistry", []);
  
  // 2. Deploy Reputation Registry
  const reputationRegistry = m.contract("ReputationRegistry", []);
  
  // 3. Initialize Reputation Registry with Identity Registry address
  m.call(reputationRegistry, "initialize", [identityRegistry]);
  
  // 4. Deploy DealRecord
  const dealRecord = m.contract("DealRecord", [identityRegistry, reputationRegistry]);
  
  // 5. Deploy SessionKeyManager (optional)
  const sessionKeyManager = m.contract("SessionKeyManager", []);
  
  return { identityRegistry, reputationRegistry, dealRecord, sessionKeyManager };
});

export default NegotiatorGridModule;
```

## Open Questions

1. **ERC-8004 on Kite**: The Identity Registry is deployed on ETH Sepolia, Base Sepolia, and SKALE — but not on Kite Testnet. NegotiatorGrid needs to deploy its own instance. The canonical address `0x8004A818BFB912233c491871b3d84c89A494BD9e` is CREATE2-deployed — we could try to match it on Kite if the factory contract exists.

2. **Privy AA wallet SDK**: Kite Agent Passport uses Privy for AA wallets. Need to investigate whether Privy exposes session key management APIs that NegotiatorGrid can call programmatically, or if we need to build a custom `SessionKeyManager` contract.

3. **Gas sponsorship**: Kite testnet mentions "Gas costs: Covered by testnet." Unclear if this means a paymaster is available or just that gas is cheap enough to ignore. For the demo, 0.5 KITE from faucet should cover many transactions.

4. **Validation Registry for deal verification**: ERC-8004's Validation Registry could be used for independent deal verification — a third party re-validates that the negotiation was fair. This is a stretch goal for the hackathon but powerful for the narrative.
