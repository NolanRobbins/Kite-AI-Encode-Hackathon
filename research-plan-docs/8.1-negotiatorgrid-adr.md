# ADR-001: NegotiatorGrid Architecture

**Status**: Accepted  
**Date**: April 9, 2026  
**Author**: Nolan Robbins  
**Context**: Kite AI × Encode Club Hackathon — Novel Track ($10K prize)  
**Constraints**: 2-week build, 1 builder, demo + codebase submission

---

## 1. Decision

Build **NegotiatorGrid** — a pre-x402 bilateral negotiation layer for agent-to-agent price bargaining on Kite Chain. Agents negotiate price, scope, and terms through multi-round dialogue before any payment is authorized, then atomically bind the agreed price to an x402 settlement with on-chain attestation.

The system is implemented as a fork of [`google-agentic-commerce/a2a-x402`](https://github.com/google-agentic-commerce/a2a-x402) (488 stars, Python, Apache 2.0), extended with a NegMAS-powered negotiation engine, ERC-8004 agent identity, and a DealRecord attestation contract on Kite testnet.

## 2. Context

### The Open Problem

The [SoK: Blockchain Agent-to-Agent Payments](https://arxiv.org/abs/2604.03733) (Zhang et al., April 2026) — the most comprehensive systematization of A2A payments — explicitly identifies multi-round price negotiation as an open future direction:

> "Agent-mediated interactions can involve iterative or multi-round negotiation over price, volume, or service scope, as reflected in evolving x402-style pricing models such as 'up-to' pricing and negotiated schemes. Therefore, lifecycle models should account for how payable conditions are formed across interactions, rather than assuming they are fully specified prior to authorization and execution."  
> — Section 5.6, Future Directions

### The Hackathon

- **Event**: [Kite AI × Encode Club Global Hackathon](https://www.encode.club/kite-hackathon) (March 27 – April 26, 2026)
- **Track**: Novel — "innovative implementations beyond the defined tracks" ($10K first prize)

### The Gap

No existing system combines: (1) bilateral agent negotiation, (2) x402 payment settlement, (3) on-chain deal attestation, and (4) MCP dynamic discovery. This was validated against the full academic landscape — see [Novel Contributions document](./negotiatorgrid-novel-contributions.md).

### Data Flow: A Complete Negotiation Cycle

```
1. Discovery    Agent A queries MCP server → finds Agent B's capabilities + AgentCard
2. Identity     Agent A resolves Agent B's ERC-8004 identity → reads reputation from
                Reputation Registry (getSummary) → injects reputation score into
                negotiation strategy parameters
3. Negotiation  A2A Task created → NegMAS SAOMechanism runs multi-round bilateral
                negotiation:
                  Round 1: Agent A proposes $0.08 (LLM generates NL offer)
                  Round 2: Agent B counters $0.12 (opponent model updates)
                  Round 3: Agent A concedes to $0.10 (gambit validates Nash)
                  Round 4: Agent B accepts (acceptance criteria met)
4. Binding      Agreed price ($0.10) → x402 PaymentRequirements constructed →
                ERC-4337 session key created with spending limit = $0.10
5. Settlement   x402 payment flow: 402 → X-PAYMENT header → Kite Facilitator
                verifies → settles on Kite testnet
6. Attestation  DealRecord.recordDeal() called with negotiation metadata →
                on-chain event emitted → reputation updated
```

## 4. Key Libraries

### NegMAS — Negotiation Protocol Engine

- **Install**: `pip install negmas`
- **Repo**: [yasserfarouk/negmas](https://github.com/yasserfarouk/negmas) (85 stars, actively maintained)
- **Docs**: [negmas.readthedocs.io](https://negmas.readthedocs.io/en/latest/)
- **Role**: Provides the `SAOMechanism` (Stacked Alternating Offers) for bilateral negotiation, plus built-in negotiators (`AspirationNegotiator`, `SimpleTitForTatNegotiator`) and an opponent modeling module ([negmas overview](https://negmas.readthedocs.io/en/latest/overview.html))
- **BOA Integration**: NegMAS's architecture separates Bidding strategy, Opponent modeling, and Acceptance criteria — the three BOA components. We extend `SAONegotiator` with LLM-augmented bidding (natural language offer generation) and reputation-conditioned acceptance thresholds
- **Why NegMAS**: Battle-tested through all ANAC (Automated Negotiating Agents Competition) competitions; includes winners/finalists from past years. The `modeling` subpackage provides opponent utility estimation, strategy recognition, and offer prediction ([academic: NegoSim/EUBOA](https://www.mdpi.com/2076-3417/13/1/642), [ASTRA negotiation agent](https://arxiv.org/abs/2503.07129))

```python
from negmas.sao import SAOMechanism, AspirationNegotiator
from negmas.preferences import LinearAdditiveUtilityFunction

# Create bilateral negotiation session
mechanism = SAOMechanism(issues=[price_issue, scope_issue], n_steps=10)
mechanism.add(BuyerNegotiator(name="buyer", ufun=buyer_utility))
mechanism.add(SellerNegotiator(name="seller", ufun=seller_utility))
state = mechanism.run()
agreed_price = state.agreement  # → feeds into x402 PaymentRequirements
```

### x402 SDK — Payment Settlement

- **Install**: `pip install x402`
- **Repo**: [x402-foundation/x402](https://github.com/x402-foundation/x402) (5,915 stars)
- **Docs**: [docs.x402.org](https://docs.x402.org), [Coinbase x402 docs](https://docs.cdp.coinbase.com/x402/quickstart-for-sellers)
- **PyPI**: [pypi.org/project/x402](https://pypi.org/project/x402/)
- **Role**: Handles the 402 Payment Required → verify → settle flow after negotiation completes
- **Flow**: (1) Seller returns 402 with `PaymentRequirements` derived from negotiated price, (2) buyer signs `PaymentPayload`, (3) Kite Facilitator at `0x12343e649e6b2b2b77649DFAb88f103c02F3C78b` verifies + settles on-chain

```python
from x402.types import PaymentRequirements
from x402.client import FacilitatorClient

# After negotiation concludes with agreed price
requirements = PaymentRequirements(
    scheme="exact",
    network="eip155:2368",  # Kite testnet
    price=str(agreed_price),
    pay_to=seller_wallet,
    asset="0x0fF5393387ad2f9f691FD6Fd28e07E3969e27e63",  # Test USDT
)
facilitator = FacilitatorClient("https://x402.dev.gokite.ai")
```

### google-agentic-commerce/a2a-x402 — FORK BASE

- **Repo**: [google-agentic-commerce/a2a-x402](https://github.com/google-agentic-commerce/a2a-x402) (488 stars, Python, Apache 2.0)
- **Role**: The base fork providing A2A protocol transport + x402 payment extension. NegotiatorGrid adds a negotiation phase between `payment-required` and `payment-submitted`
- **Architecture**: Functional core (`core/protocol.py` — verify/settle), imperative shell (`executors/` — middleware). Spec v0.2 supports Standalone and Embedded flows with atomic signing, delegated signing, and smart contract escrow patterns ([spec v0.2](https://github.com/google-agentic-commerce/a2a-x402/blob/main/spec/v0.2/spec.md))
- **What we add to the fork**:
  1. New A2A message types: `negotiation-offer`, `negotiation-counteroffer`, `negotiation-accept`, `negotiation-reject`
  2. `NegotiationExecutor` that wraps `SAOMechanism` and bridges NegMAS rounds to A2A messages
  3. `DealAttestationModule` that writes `DealRecord` on-chain after settlement
  4. ERC-8004 identity resolution in AgentCard discovery

### Gambit — Nash Equilibrium Validation

- **Install**: `pip install pygambit`
- **Repo**: [gambitproject/gambit](https://github.com/gambitproject/gambit) (537 stars, C++ core with Python bindings)
- **Docs**: [gambitproject.readthedocs.io](https://gambitproject.readthedocs.io/en/latest/)
- **Role**: Game-theoretic validation of negotiation outcomes. After each round, computes whether the current offer profile is near a Nash equilibrium. Used as a guardrail to prevent LLM agents from accepting exploitative deals
- **Integration**: `pygambit` Python API constructs a 2-player strategic-form game from the negotiation's utility space, then runs equilibrium-finding algorithms

```python
import pygambit as gbt

# Construct bilateral bargaining game from negotiation state
game = gbt.Game.new_table([n_buyer_strategies, n_seller_strategies])
# ... populate payoff matrix from utility functions ...
equilibria = gbt.nash.lcp_solve(game)  # Lemke-Howson for 2-player
```

### fast-x402 — Seller-Side FastAPI Middleware

- **Repo**: [jordo1138/fastapi-x402](https://github.com/jordo1138/fastapi-x402/)
- **Role**: One-line decorator to paywall any FastAPI endpoint via x402. Seller agents expose their services behind `@pay("$0.10")` decorators, where the price is dynamically set from the negotiation outcome ([GitHub](https://github.com/jordo1138/fastapi-x402/))

```python
from fastapi import FastAPI

app = FastAPI()
init_x402(app, pay_to="0x...", facilitator_url="https://x402.dev.gokite.ai")

@app.get("/ai-service")
@pay(negotiated_price)  # Dynamic price from negotiation outcome
async def ai_service():
    return {"result": "..."}
```

## 5. Alternatives Considered

### Option A: Raw OpenAI Agents SDK

- **What it is**: OpenAI's minimal 4-primitive SDK (Agents, Handoffs, Guardrails, Tracing) for building agent chains ([OpenAI](https://openai.com/index/new-tools-for-building-agents/))
- **Pros**: Lowest friction to first agent (~minutes), built-in tracing
- **Cons**: No native A2A protocol support, no MCP integration (must wrap as function tools), no built-in state persistence, OpenAI-only models by default, no negotiation primitives ([techsy.io comparison](https://techsy.io/blog/langgraph-vs-crewai-vs-openai-agents-sdk), [Particula comparison](https://particula.tech/blog/langgraph-vs-crewai-vs-openai-agents-sdk-2026))
- **Why rejected**: Would require building A2A transport from scratch. No extension mechanism for x402 payment flow. The a2a-x402 fork gives us the payment transport for free

### Option B: CrewAI

- **What it is**: Role-based multi-agent framework (46.3K GitHub stars), first-class MCP support ([crewai.com](https://crewai.com))
- **Pros**: Fast prototyping, MCP integration, role metaphor fits buyer/seller, strong community
- **Cons**: No native A2A protocol support (roadmap only), no x402 payment integration, role-based model doesn't map cleanly to bilateral negotiation protocol, no game-theoretic primitives ([Particula comparison](https://particula.tech/blog/langgraph-vs-crewai-vs-openai-agents-sdk-2026))
- **Why rejected**: We'd still need to build the A2A+x402 bridge. CrewAI's task-based paradigm doesn't naturally model multi-round negotiation state. Starting from a2a-x402 is closer to our final architecture

### Option C: LangGraph

- **What it is**: Directed graph framework for stateful agent workflows (26.6K stars), production-grade checkpointing ([langchain-ai/langgraph](https://github.com/langchain-ai/langgraph))
- **Pros**: Best state management (SQLite/Postgres checkpointing), graph model fits negotiation state machine, production-ready, model-agnostic ([techsy.io comparison](https://techsy.io/blog/langgraph-vs-crewai-vs-openai-agents-sdk))
- **Cons**: Steep learning curve (1-2 weeks), MCP only via LangChain tools (manual wiring), no native A2A, no x402 integration, heavy dependency chain
- **Why rejected**: Learning curve too steep for a 2-week hackathon. The graph abstraction adds complexity but doesn't help with the core problem (bilateral negotiation protocol). a2a-x402 already solves the transport + payment layer

### Decision: Fork a2a-x402

| Criterion | OpenAI SDK | CrewAI | LangGraph | **a2a-x402 Fork** |
|-----------|:----------:|:------:|:---------:|:------------------:|
| A2A protocol | ❌ | ❌ (roadmap) | ❌ | ✅ Built-in |
| x402 payments | ❌ | ❌ | ❌ | ✅ Built-in |
| MCP discovery | ❌ | ✅ | Via LangChain | Add via Kite MCP |
| Negotiation | ❌ | ❌ | ❌ | Add via NegMAS |
| Time to MVP | 2 weeks | 1.5 weeks | 2+ weeks | **1 week** |
| Hackathon fit | Low | Medium | Low | **High** |

The a2a-x402 fork starts with ~70% of our architecture already built (A2A transport + x402 settlement). We add the negotiation layer (NegMAS), identity layer (ERC-8004), and attestation layer (DealRecord contract). Every alternative would require building the payment transport from scratch.

## 6. Risks

### Risk 1: NegMAS ↔ LLM Integration Complexity
- **Impact**: HIGH — The BOA framework expects structured utility functions; LLM reasoning is freeform
- **Likelihood**: MEDIUM
- **Mitigation**: Use NegMAS `SAOMechanism` for protocol orchestration only. LLM generates natural language offers, but the actual bid values come from a `LinearAdditiveUtilityFunction`. LLM enriches the communication layer; NegMAS enforces the game theory. Fallback: hardcoded aspiration strategies if LLM integration stalls

### Risk 2: Kite Testnet Instability
- **Impact**: HIGH — Demo depends on live on-chain transactions
- **Likelihood**: MEDIUM — Testnet may have downtime, gas issues, or RPC rate limits
- **Mitigation**: (1) Pre-record critical demo paths as backup video. (2) Implement a mock facilitator (a2a-x402 already has one at `server/agents/mock_facilitator.py`). (3) Cache recent on-chain attestations in local DB for dashboard display even if RPC is down

### Risk 3: x402 SDK Python Maturity
- **Impact**: MEDIUM — Python SDK is newer than TypeScript; may have edge cases
- **Likelihood**: MEDIUM — The [PyPI package](https://pypi.org/project/x402/) exists but the TypeScript SDK has more production usage
- **Mitigation**: (1) Use the x402 test facilitator at `https://x402.org/facilitator` for development. (2) Kite's own facilitator at `https://x402.dev.gokite.ai` for demo. (3) If Python SDK fails, fall back to raw HTTP 402 protocol implementation (verify/settle are just REST calls)

### Risk 4: Scope Creep — Too Many Novel Contributions
- **Impact**: MEDIUM — Trying to demonstrate all 5 gaps (atomicity, reputation, MCP transport, ERC-4337, anti-collusion) in 2 weeks could result in nothing working well
- **Likelihood**: HIGH
- **Mitigation**: Prioritize ruthlessly:
  - **P0 (must ship)**: Bilateral negotiation via A2A → x402 settlement → on-chain attestation (Gaps A, C)
  - **P1 (demo-worthy)**: Reputation-conditioned strategy (Gap B), Next.js dashboard
  - **P2 (mention in video)**: ERC-4337 session keys (Gap D), anti-collusion detection (Gap E)
  - If P0 isn't solid by day 10, drop P1/P2 entirely

### Risk 5: ERC-8004 Is Draft Status
- **Impact**: LOW — The EIP may change, but for a hackathon demo, the interface is stable enough
- **Likelihood**: LOW — Draft EIPs are stable for months; we only need the Identity Registry + Reputation Registry interfaces
- **Mitigation**: Deploy our own simplified version of the ERC-8004 registries on Kite testnet. If the full spec is too complex, implement just `register()`, `giveFeedback()`, and `getSummary()` — the three functions NegotiatorGrid actually needs

## 7. Open Questions

### Architecture

1. **SAOMechanism round limit**: How many negotiation rounds before timeout? ANAC competitions typically use 10-20 rounds. For a demo, 5-7 rounds is visually interesting without being tedious. Need to calibrate against LLM latency (~1-2s per round).

2. **LLM provider for negotiation reasoning**: OpenAI GPT-4o for quality, or a cheaper model for faster iteration? Budget consideration: each negotiation round = 1 LLM call per agent = 2 calls per round × ~$0.01 = ~$0.10 per full negotiation. Acceptable for demo.

3. **MCP tool schema for negotiation**: Should negotiation be exposed as an MCP tool (`negotiate_price`) or as an A2A extension? Current lean: A2A extension for agent-to-agent negotiation, MCP tool for human-in-the-loop price queries.

### Implementation

4. **Gambit integration depth**: Full Nash equilibrium computation per round, or simplified dominance checking? `pygambit`'s `lcp_solve` works for 2-player games but may be slow for large strategy spaces. Simplification: discretize the price range into ~10 buckets, compute Nash on the resulting 10×10 bimatrix.

5. **DealRecord contract storage costs**: Storing full negotiation transcripts on-chain is expensive. Store only: `(buyer, seller, agreedPrice, rounds, termsHash, x402TxHash)` on-chain. Full transcript goes to IPFS or off-chain storage with content hash anchored on-chain.

6. **fast-x402 Kite network support**: The [fastapi-x402](https://github.com/jordo1138/fastapi-x402/) library supports Base and Avalanche out of the box. Need to verify it works with Kite testnet (Chain ID 2368) or add custom network config. Worst case: use raw x402 Python SDK instead of the FastAPI wrapper.

### Strategy

7. **Demo narrative**: Lead with the negotiation visualization (most visually compelling) or the technical architecture (most novel)? The [DX audit](./kite-winners-dx-audit.md) found that ETHDenver winners led with live demos, not architecture diagrams. Lean: 30s context → 2min live negotiation demo → 1min architecture → 30s impact.

8. **Judge audience**: Encode judges may not have deep game theory background. How much to explain BOA/Nash vs. just showing agents haggling in natural language? Lean: show the haggling, mention game theory as the "engine under the hood," don't deep-dive formulas.
