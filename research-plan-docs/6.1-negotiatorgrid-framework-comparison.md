## 1. OpenAI Agents SDK + x402 Tool

**Stars**: 20.7k | **Language**: Python | **Last updated**: 2026-04-09

**Sources**: [GitHub](https://github.com/openai/openai-agents-python), [Laso Finance x402 integration](https://agents.laso.finance/frameworks/openai-agents), [DigitalOcean MCP guide](https://www.digitalocean.com/community/tutorials/how-to-use-mcp-with-openai-agents), [Composio MCP guide](https://composio.dev/content/building-mcp-agents-with-openai-agents-sdk)

### Key Findings

**x402 integration**: Laso Finance provides a [working pattern](https://agents.laso.finance/frameworks/openai-agents) wrapping x402 as `@function_tool`. The pattern is straightforward — intercept HTTP 402, parse payment requirements, sign with wallet, retry with `X-PAYMENT` header. The `sign_x402_payment()` function needs adaptation for Kite L1 (Base → Kite chain ID 2368).

```python
@function_tool
def negotiate_and_pay(service_url: str, max_price: float) -> str:
    response = requests.get(service_url)
    if response.status_code == 402:
        payment_req = response.json()
        # NegotiatorGrid: negotiate price before signing
        agreed_price = negotiation_engine.negotiate(payment_req)
        x_payment = sign_x402_payment(payment_req, amount=agreed_price)
        response = requests.get(url, headers={"X-PAYMENT": x_payment})
    return response.json()
```

**Multi-agent handoffs**: Native `handoffs` parameter maps directly to NegotiatorGrid's architecture:

```python
buyer_agent = Agent(name="Buyer", tools=[discover_tools, negotiate_price])
seller_agent = Agent(name="Seller", tools=[set_price, deliver_service])
mediator_agent = Agent(name="Mediator", tools=[evaluate_fairness, suggest_compromise])

triage = Agent(name="Triage", handoffs=[buyer_agent, seller_agent, mediator_agent])
```

Handoffs support `on_handoff` callbacks (for logging negotiation state), `input_type` (Pydantic models for structured offer/counter-offer), and `input_filter` (to control what context transfers between agents). [Source](https://github.com/openai/openai-agents-python/blob/main/docs/handoffs.md).

**MCP support**: Built-in via `agents.mcp` — supports `MCPServerStdio`, `MCPServerSse`, and Streamable HTTP. Multiple MCP servers can attach to a single agent. Tools are auto-discovered. [Source](https://www.digitalocean.com/community/tutorials/how-to-use-mcp-with-openai-agents).

**Guardrails**: Native `input_guardrails` for spending limit enforcement — directly maps to our AA wallet constraint:

```python
@input_guardrail
async def spending_limit(ctx, agent, input):
    return GuardrailFunctionOutput(tripwire_triggered=(amount > MAX_TX))
```

### Evaluation

| Criterion | Rating | Notes |
|-----------|--------|-------|
| **Setup complexity** | ★★★★★ Low | `pip install openai-agents requests`. 2 files to get a working multi-agent system with x402. Laso Finance pattern is copy-paste-adapt. |
| **x402/Kite compatibility** | ★★★★☆ Good | x402 pattern proven (Laso Finance uses Base chain). Requires custom `sign_x402_payment()` for Kite L1 (chain ID 2368, test USDT). No native Kite support — ~1 day to adapt. |
| **NegMAS integration** | ★★★★☆ Easy | NegMAS runs as a pure Python library. Wrap `SAOMechanism` inside a `@function_tool`. The negotiation engine is orthogonal to the agent framework. |
| **Demo impressiveness** | ★★★★☆ High | OpenAI tracing dashboard shows real-time agent handoffs. Can add Streamlit UI. Handoff visualization is built-in. |
| **Risk level** | ★★★★☆ Low | Depends on OpenAI API (well-tested, 99.9% uptime). SDK is open-source. x402 signing is local (no external dependency). |

### Risks
- Requires OpenAI API key and credits for LLM calls
- `sign_x402_payment()` needs to be built for Kite chain (no SDK exists)
- Handoffs are LLM-routed, meaning token cost per routing decision

## 2. LangGraph + Custom Negotiation Nodes

**Stars**: 28.7k | **Language**: Python | **Last updated**: 2026-04-09

**Sources**: [GitHub](https://github.com/langchain-ai/langgraph), [AWS multi-agent guide](https://aws.amazon.com/blogs/machine-learning/build-multi-agent-systems-with-langgraph-and-amazon-bedrock/), [LangChain Blog](https://blog.langchain.com/langgraph-multi-agent-workflows/), [xpay.sh](https://www.xpay.sh/x402-agent-frameworks/), [Zhao et al. 2025 (supply chain)](http://iglc.net/Papers/Details/2306)

### Key Findings

**Graph-based architecture**: LangGraph models agent workflows as state machines with nodes (Python functions) and edges (conditional transitions). This maps naturally to a negotiation protocol:

```
[Discover] → [Trust Gate] → [Initial Offer] → [Counter-Offer] ←→ [Evaluate] → [Accept/Reject] → [Pay via x402]
```

Each node is a Python function. Edges are conditional (e.g., "if counter-offer within ZOPA, proceed; else loop back"). State is a shared TypedDict that persists across the graph.

**Supply chain validation**: [Zhao et al. (2025)](http://iglc.net/Papers/Details/2306) built a LangChain+LangGraph multi-agent system for supply chain coordination with Supplier Agents and General Contractor Agents. The agents engage in natural language interactions to coordinate material deliveries — validating the bilateral coordination pattern. However, they did not implement a formal negotiation protocol (no SAOP, no utility functions).

**x402 integration**: [xpay.sh rates LangGraph as "Advanced" complexity](https://www.xpay.sh/x402-agent-frameworks/) for x402 integration. LangGraph's state management enables multi-step validation and approval processes, but requires more boilerplate than simpler frameworks. No off-the-shelf x402 node exists.

**Dynamic node creation**: LangGraph supports `add_node()` at graph construction time. For multi-round negotiation, you'd predefine a configurable number of offer/counter-offer cycles rather than truly dynamic node creation. This is a constraint for open-ended negotiation.

### Evaluation

| Criterion | Rating | Notes |
|-----------|--------|-------|
| **Setup complexity** | ★★★☆☆ Medium-High | `pip install langgraph langchain`. Must define State schema, node functions, edge conditions, and graph compilation. ~3-5 days for the negotiation graph alone. |
| **x402/Kite compatibility** | ★★★☆☆ Custom | No native x402 integration. Must build a custom node that handles 402 → sign → retry. Same Kite adaptation needed as Option 1, plus graph plumbing. |
| **NegMAS integration** | ★★★★☆ Easy | Same as OpenAI SDK — NegMAS is a library call. Wrap it in a graph node. |
| **Demo impressiveness** | ★★★★★ Highest | Graph visualization (LangSmith) shows the negotiation state machine in real-time. Judges can see the offer/counter-offer cycles as graph traversals. This is the most visually impressive option. |
| **Risk level** | ★★★☆☆ Medium | Depends on LangChain ecosystem (frequent breaking changes historically). LangGraph itself is more stable. More moving parts = more debugging. |

### Risks
- LangChain ecosystem has a history of API churn — lock your versions
- Graph definition is verbose; the 2-week timeline is tight
- Supervisor pattern adds latency (extra LLM call per routing decision)
- Debugging graph state transitions is harder than linear agent flows

## 3. Google A2A + NegMAS Hybrid

**Stars**: A2A (488 on a2a-x402) | NegMAS (85) | **Language**: Python

**Sources**: [a2a-x402 GitHub](https://github.com/google-agentic-commerce/a2a-x402), [A2A announcement](https://developers.googleblog.com/en/a2a-a-new-era-of-agent-interoperability/), [NegMAS docs](https://negmas.readthedocs.io), [NegMAS PyPI](https://pypi.org/project/negmas/), [AP2 + x402 docs](https://ap2-protocol.org/topics/ap2-and-x402/), [NegoLog IJCAI 2024](https://www.ijcai.org/proceedings/2024/0998.pdf)

### Key Findings

**A2A transport**: Google's A2A protocol provides agent-to-agent communication via JSON Agent Cards (capability advertisement), SSE streaming, and task lifecycle management. The [a2a-x402 extension](https://github.com/google-agentic-commerce/a2a-x402) implements the exact payment flow NegotiatorGrid needs: `payment-required` → `payment-submitted` → `payment-completed`. It's Python-only, uses a "functional core, imperative shell" architecture.

**Architecturally ideal**: A2A handles transport (how agents find and talk to each other), while NegMAS handles negotiation logic (SAOMechanism, AspirationNegotiator, utility functions). This is the cleanest separation of concerns. NegMAS v0.15.4 supports:
- SAOMechanism (Stacked Alternating Offers Protocol) — exactly the bilateral negotiation protocol we need
- AspirationNegotiator, NaiveTitForTatNegotiator — built-in strategies
- MappingUtilityFunction — define utility over outcomes
- Multi-session support — concurrent negotiations

**Integration challenge**: Neither A2A nor NegMAS knows about the other. You'd need to:
1. Build an A2A server that wraps NegMAS's `SAOMechanism`
2. Map A2A messages to NegMAS `propose()`/`respond()` calls
3. Map NegMAS outcomes to x402 payment amounts
4. Handle the A2A task lifecycle (created → working → completed)

The [a2a-x402 repo](https://github.com/google-agentic-commerce/a2a-x402) has examples (`adk-demo`, `ap2-demo`) but no negotiation logic — it only handles fixed-price payment flows. Adding negotiation is the entire point of NegotiatorGrid but requires significant glue code.

**NegMAS strengths for judges**: NegMAS is used in [ANAC (Automated Negotiating Agents Competition)](https://www.ijcai.org/proceedings/2024/0998.pdf), giving academic credibility. It generates "Negotiation Dance" plots showing offer dynamics over time — great for demo visualization.

### Evaluation

| Criterion | Rating | Notes |
|-----------|--------|-------|
| **Setup complexity** | ★★☆☆☆ High | A2A server setup + NegMAS integration + x402 extension wiring. Estimate 5-7 days just for the integration layer. Most novel code, most risky timeline. |
| **x402/Kite compatibility** | ★★★★★ Native | a2a-x402 implements x402 payment flow natively. Payment Required/Submitted/Completed maps to A2A message types. Still need Kite chain adaptation. |
| **NegMAS integration** | ★★★★★ Native | NegMAS IS the negotiation engine. No wrapping needed — just connect it to A2A's message transport. SAOMechanism, utility functions, strategies all built-in. |
| **Demo impressiveness** | ★★★★☆ High | NegMAS Negotiation Dance plots + A2A task lifecycle = compelling narrative. But no built-in real-time visualization; you'd build it yourself. |
| **Risk level** | ★★☆☆☆ High | a2a-x402 has only 488 stars and is early-stage. NegMAS has 85 stars and niche docs. If either has a bug, you're debugging unfamiliar code under hackathon pressure. 50+ partners announced A2A but few production implementations exist yet. |

### Risks
- a2a-x402 is very new (last updated 2026-04-08) — potential undiscovered bugs
- NegMAS docs are academic-oriented, not tutorial-oriented
- No existing example combining A2A + NegMAS + x402 — you're blazing trail
- A2A TypeScript port just [launched Oct 2025](https://x.com/dabit3/status/1976038551352639540) — ecosystem still maturing

## 4. CrewAI + x402 Tool

**Stars**: 48.4k | **Language**: Python | **Last updated**: 2026-04-09

**Sources**: [GitHub](https://github.com/crewAIInc/crewAI), [CrewAI MCP docs](https://docs.crewai.com/en/mcp/overview), [MoltsPay + CrewAI x402](https://dev.to/yaqing2023/give-your-ai-agents-a-wallet-moltspay-crewai-in-10-lines-1hg9), [xpay.sh](https://www.xpay.sh/x402-agent-frameworks/), [Digital Applied comparison](https://www.digitalapplied.com/blog/mcp-vs-langchain-vs-crewai-agent-framework-comparison)

### Key Findings

**Multi-agent patterns**: CrewAI's role-based architecture maps naturally to NegotiatorGrid:

```python
buyer = Agent(role="Buyer Agent", goal="Get the lowest price for the service",
              tools=[MoltsPayTool()])
seller = Agent(role="Seller Agent", goal="Maximize revenue while retaining clients")
mediator = Agent(role="Mediator", goal="Ensure fair pricing for both parties")

crew = Crew(agents=[buyer, seller, mediator], tasks=[negotiate_task])
```

**x402 integration**: [MoltsPay demonstrates a working 10-line CrewAI + x402 integration](https://dev.to/yaqing2023/give-your-ai-agents-a-wallet-moltspay-crewai-in-10-lines-1hg9). The `BaseTool` subclass wraps x402 payment flow. [xpay.sh rates CrewAI as "Medium" complexity](https://www.xpay.sh/x402-agent-frameworks/) for x402 — easier than LangGraph.

**MCP support**: CrewAI has [first-class MCP integration](https://docs.crewai.com/en/mcp/overview) via the `mcps` DSL field on agents. Supports Stdio, HTTP/Streamable HTTP, and SSE transports. Tool discovery is automatic. This means NegotiatorGrid's dynamic MCP discovery could use CrewAI's built-in MCP client.

**Limitation for negotiation**: CrewAI's task execution model is **sequential or hierarchical** — agents complete tasks in order or under a manager. It does NOT natively support the **back-and-forth message exchange** that bilateral negotiation requires. You'd need to hack the task flow: either (a) have a single "negotiation task" that internally runs a loop, or (b) create a chain of tasks (offer → counter-offer → evaluate → ...) with a fixed number of rounds. Neither is elegant.

### Evaluation

| Criterion | Rating | Notes |
|-----------|--------|-------|
| **Setup complexity** | ★★★★☆ Low-Medium | `pip install crewai crewai-tools[mcp]`. Agent/Task/Crew pattern is intuitive. ~2-3 days for working negotiation demo. But the negotiation loop hack adds complexity. |
| **x402/Kite compatibility** | ★★★★☆ Good | MoltsPay pattern works. Same Kite chain adaptation needed. CrewAI's MCP integration helps with tool discovery. |
| **NegMAS integration** | ★★★☆☆ Medium | NegMAS can run inside a CrewAI `BaseTool`, but CrewAI's sequential task model fights against NegMAS's turn-based negotiation. You'd wrap the entire SAOMechanism run inside a single tool call. |
| **Demo impressiveness** | ★★★☆☆ Medium | CrewAI has `verbose=True` logging but no graph visualization. No built-in real-time negotiation UI. The "crew" narrative is compelling but the demo is mostly terminal output. |
| **Risk level** | ★★★★☆ Low | Most popular framework (48k stars), active development, good docs. Low risk of abandonment or breaking changes during hackathon. |

### Risks
- Sequential task model doesn't fit bilateral negotiation naturally
- CrewAI abstracts away control flow — harder to implement custom negotiation protocols
- `verbose=True` output is noisy and hard to parse for demo purposes
- CrewAI crews are designed for collaborative tasks, not adversarial negotiation

## 5. Raw Python + a2a-x402 Fork

**Stars**: 488 (a2a-x402) | **Language**: Python

**Sources**: [a2a-x402 GitHub](https://github.com/google-agentic-commerce/a2a-x402), [NegMAS docs](https://negmas.readthedocs.io), [Laso Finance x402 flow](https://agents.laso.finance/guides/how-x402-works)

### Key Findings

**What you get by forking**: The a2a-x402 repo gives you:
- `x402_a2a/` core library — payment-required/submitted/completed message types
- `spec/v0.1/` — formal x402 extension specification
- `examples/adk-demo/` and `examples/ap2-demo/` — working demonstrations
- "Functional core, imperative shell" — clean architecture for extension

**What you need to add**:
1. NegMAS `SAOMechanism` as the negotiation engine between payment-required and payment-submitted
2. MCP client (use `mcp` Python SDK directly — `pip install mcp`)
3. ERC-8004 trust gate (on-chain calls via `web3.py`)
4. ERC-4337 wallet (via `eth-account` + custom `validateUserOp`)
5. A simple web UI (FastAPI + WebSockets for real-time updates)

**Maximum control**: No framework opinions. You decide exactly how the negotiation loop works, how agents communicate, and how x402 payments flow. Every line of code is yours to explain to judges.

**No LLM dependency (optional)**: You could run the negotiation engine entirely with NegMAS strategies (AspirationNegotiator, TimeDependentNegotiator) and only use an LLM for the demo narrative/explanation layer. This eliminates the OpenAI API dependency and makes the system more deterministic — a plus for security-conscious judges.

### Evaluation

| Criterion | Rating | Notes |
|-----------|--------|-------|
| **Setup complexity** | ★★★☆☆ Medium | Fork + add NegMAS + add MCP client + add web3.py + add FastAPI. No framework magic means more boilerplate, but also no framework-fighting. Estimate 4-5 days for core. |
| **x402/Kite compatibility** | ★★★★★ Native | a2a-x402 IS the x402 implementation. Kite chain adaptation still needed but you have full control over the signing code. |
| **NegMAS integration** | ★★★★★ Native | Direct Python import. No framework wrapper needed. NegMAS's SAOMechanism runs natively in your event loop. |
| **Demo impressiveness** | ★★★☆☆ Medium | No built-in visualization — you build everything from scratch. But you can create a custom WebSocket-driven UI that shows exactly what you want. Higher ceiling, lower floor. |
| **Risk level** | ★★★☆☆ Medium | a2a-x402 is early-stage (488 stars). No framework safety net. But also no framework bugs to work around. Your bugs are your bugs. |

### Risks
- No framework means more boilerplate code to write
- a2a-x402 may have undocumented edge cases
- You're the framework — if you architect poorly, there's no guardrail
- Demo visualization requires building a custom UI from scratch

## 7. Recommendation: Why OpenAI Agents SDK Wins

### Primary: OpenAI Agents SDK + x402 Tool

**The calculus is simple**: In a 2-week hackathon, velocity beats elegance.

1. **Day 1-2**: Working multi-agent skeleton with buyer/seller/mediator handoffs. Copy the [Laso Finance pattern](https://agents.laso.finance/frameworks/openai-agents), adapt `sign_x402_payment()` for Kite chain.

2. **Day 3-5**: Integrate NegMAS as a `@function_tool`. The buyer agent calls `negotiate_price(service_url, max_budget)` which internally runs `SAOMechanism` with an `AspirationNegotiator`.

3. **Day 6-8**: Add ERC-8004 trust gate and AA wallet constraint (from security model). These are `@function_tool` wrappers around `web3.py` calls.

4. **Day 9-11**: MCP dynamic discovery (`MCPServerSse` for x402Scout, custom `mcp-find`). Wire the "wow moment": discover → verify → negotiate → pay → use.

5. **Day 12-14**: Demo polish, Streamlit UI, documentation, video.

**Why not LangGraph?** Better visualization but 2-3x more setup time. The graph definition is verbose and the negotiation loop mapping is over-engineered for a hackathon. Save LangGraph for the "after hackathon" productionization.

**Why not A2A + NegMAS?** Architecturally ideal but the integration glue is 5-7 days of novel code. Too risky for a hackathon where the demo is everything.

**Why not CrewAI?** Popular but the sequential task model actively fights bilateral negotiation. You'd spend time fighting the framework instead of building the product.

### Fallback: Raw Python + a2a-x402 Fork

If OpenAI Agents SDK introduces unexpected friction (e.g., OpenAI API downtime, Kite chain signing incompatibility, handoff latency issues), drop to raw Python:

- Fork a2a-x402 for the payment flow
- Import NegMAS directly for negotiation
- Use `mcp` Python SDK for tool discovery
- Build a FastAPI + WebSocket server for the demo UI
- No LLM dependency means 100% deterministic negotiation — actually a selling point

**The trade-off**: More code, more control, no framework safety net. But you can explain every line to a judge.

## 8. Open Questions

1. **OpenAI API cost**: Multi-agent handoffs consume tokens per routing decision. For the demo, is the token cost acceptable, or should we pre-script the routing for the live demo?
2. **Kite chain `sign_x402_payment()`**: No Python x402 SDK exists for Kite. We need to build EIP-3009 `transferWithAuthorization` signing for Kite's test USDT. How long will this take?
3. **NegMAS version compatibility**: NegMAS 0.15.4 requires Python 3.10+. Is this compatible with the OpenAI Agents SDK's dependencies?
4. **Demo architecture**: Should the buyer and seller be separate processes (true A2A) or separate agents within a single process (simpler, less impressive)?
5. **LLM-driven vs. algorithmic negotiation**: Should the negotiation strategies be LLM-generated (more impressive, less predictable) or NegMAS algorithmic (more reliable, less flashy)? Can we do both and let the judge choose?
