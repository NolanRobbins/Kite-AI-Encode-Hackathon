## 1. GPT-Bargaining — What NegotiatorGrid Can Take

### Architecture: Buyer → Seller → Critic

The three-agent pattern maps directly to NegotiatorGrid:
- **Buyer agent**: minimize price (NegotiatorGrid buyer)
- **Seller agent**: maximize price (NegotiatorGrid seller)
- **Critic agent**: reviews negotiation history, generates 3 improvement suggestions

The critic never speaks to both sides — it coaches one player asymmetrically. The improvement comes from **ICL-AIF** (In-Context Learning from AI Feedback): accumulated negotiation history + critic suggestions become few-shot demonstrations in the coached agent's context window.

### What to adopt
- The **critic pattern** — after each negotiation session, an LLM reviews the transcript and generates strategy improvements for the next session. This maps to NegotiatorGrid's cross-session learning.
- The **self-play loop** — run multiple negotiation rounds where the agent accumulates experience as in-context demonstrations. No gradient updates needed.

### What to avoid
- **Free-form NL bids with regex extraction** — fragile. GPT-Bargaining needs a Moderator LLM just to handle parse failures. This won't work for on-chain settlement where the price must be exact.

## 2. AgenticPay — What NegotiatorGrid Can Take

### The Structured Action Extraction Pattern

AgenticPay's three-priority regex cascade is the state of the art for extracting structured data from LLM responses:

```
Priority 1: ### BUYER_PRICE($8,750) ###    ← enforced by system prompt
Priority 2: ### $100.50 ###                ← backward compat
Priority 3: $100 / "100 dollars" / "100 USD"  ← fallback
```

Agreement detection: `|buyer_price - seller_price| ≤ 1.0` OR `seller_price ≤ buyer_price` OR explicit `MAKE_DEAL`.

### LLM Performance Rankings (verified from Table 1)

| Model | GlobalScore | Deal Rate | Timeout Rate | Avg Rounds |
|-------|-----------|-----------|-------------|-----------|
| Claude Opus 4.5 | **86.9** | 100% | 0% | **3.7** |
| GPT-5.2 | 81.7 | 100% | 0% | 3.8 |
| Gemini-3-Flash | 82.2 | 100% | 0% | 4.8 |
| Qwen3-14B | 63.9 | 79.3% | 20.7% | 7.8 |
| Llama-3.1-8B | 32.5 | 51.4% | **48.6%** | 15.0 |

Key insight: **All proprietary models achieve 100% deal rate.** The failure cliff is sharp between Qwen3-14B (79.3% deal rate) and Llama-3.1-8B (51.4%). For NegotiatorGrid, using a frontier model (Claude/GPT-5) as the negotiation engine is non-negotiable for reliability.

### Welfare Metrics → On-Chain Attestation

AgenticPay's `GlobalScore = γ^(t-1) × (D + 4·rb·rs·W + E)` where:
- `rb = (pmax - p) / Z` — buyer's share of surplus
- `rs = (p - pmin) / Z` — seller's share of surplus  
- `4·rb·rs` — Nash product proxy, peaks at 1.0 for equal split

**On-chain mapping**: The tuple `(p, pmax, pmin, t)` is all that's needed. Reservation prices can stay private via ZK proofs while the contract verifies `p ∈ [pmin, pmax]` and computes the welfare score.

### What to adopt
- The **`### PRICE($X) ###` structured token format** — reliable, simple, and keeps the LLM's reasoning in NL while the action is structured
- The **`<mental_model>` chain-of-thought block** — forces the LLM to reason about opponent strategy before bidding
- The **welfare metric formula** — adoptable as NegotiatorGrid's on-chain quality attestation

## 3. PACT — What NegotiatorGrid Can Take

### Composite Model Score (CMS)

```
CMS = α × OBS + (1-α) × SurplusShare
```

Where α is chosen by bootstrap to maximize ranking stability. OBS (Opponent-Balanced Share) corrects for opponent quality — prevents score inflation from playing weak opponents.

### JSONL Log Schema

PACT's 8 event types (`init`, `conversation`, `bid_ask`, `trade`, `payoff_change`, `round_end`, `propensity_snapshot`) provide a complete, typed logging format. Directly adoptable for NegotiatorGrid session logging.

### Leaderboard Insight

30 models tested. **Reasoning models dominate** (GPT-5 CMS 72%, o3 64%, o4-mini 60%). This confirms the pattern from AgenticPay: negotiation benefits enormously from extended inference-time computation.

### What to adopt
- **CMS as a KPI** for NegotiatorGrid agent evaluation, with α re-estimated for your agent population
- **PACT's JSONL schema** as the logging format for negotiation sessions
- **The insight that reasoning models >> standard models** — prioritize models with chain-of-thought or extended thinking

## 4. ASTRA — What NegotiatorGrid Can Take

### The Hybrid Architecture: LLM → LP → LLM

This is the most sophisticated approach and the most relevant to NegotiatorGrid:

```
Stage 1: LLM reads dialogue → infers partner preferences (IPP)
         Rule engine classifies Fairness × Stance → λ
         
Stage 2: LP solver maximizes Sa + (1-λ)·Sp subject to Sa ≤ Smax
         Solves N times with λ ± 0.3 perturbations
         Returns N Pareto-efficient offer candidates

Stage 3: LLM (VPA) scores each candidate for acceptance probability
         LLM selects tactic (9 options) + ranks offers
         LLM generates natural language response with winning offer
```

**The key insight**: LLMs cannot reliably optimize. The LP solver generates provably Pareto-optimal offers; the LLM handles preference inference (where it excels) and natural language generation (where it's needed). The 3.59-point improvement over pure LLM (24.34 vs 20.75, p < 0.001) is statistically definitive.

### Stance Classification → Opponent Modeling

The Fairness × Stance grid maps directly to NegotiatorGrid's aspiration curve parameter:

| Opponent Behavior | ASTRA λ | NegotiatorGrid Mapping |
|-------------------|---------|----------------------|
| Greedy + Unfair | 0.9 | Boulware (exponent=4.0) — hold firm |
| Neutral + Unfair | 0.9 | Boulware |
| Neutral + Fair | 0.8 | Moderate (exponent=2.0) |
| Generous + Fair | 0.3 | Conceder (exponent=0.25) — reciprocate |
| Unknown | 0.5 | Linear (exponent=1.0) |

### What to adopt
- The **LLM → Optimizer → LLM** pipeline — use NegMAS's aspiration curve or a custom LP as the optimizer, with an LLM for preference inference and response generation
- **Stance classification** as the opponent modeling signal that controls concession speed
- **The VPA (Virtual Partner Agent)** pattern — use an LLM to simulate the opponent and predict acceptance probability of candidate offers

## 5. The Key Question: Structured vs Natural Language vs Hybrid

### Option A: Pure Natural Language (GPT-Bargaining style)

```
Agent says: "I'll sell the API access for $0.05 per request with 99.9% SLA"
Parse with regex → extract price, SLA terms
```

**Pros**: Most natural for LLM demo, judges understand it immediately
**Cons**: Fragile parsing, can't guarantee exact prices, no on-chain verifiability

### Option B: Pure Structured Protocol (NegMAS/NegoLog style)

```json
{"type": "offer", "price": 0.05, "latency_ms": 100, "uptime_pct": 99.9}
```

**Pros**: Exact, parseable, directly maps to session key `valueLimit`, on-chain attestable
**Cons**: No natural language reasoning, loses the "AI negotiation" narrative

### Option C: Hybrid — LLM Reasons, Outputs Structured Actions (RECOMMENDED)

This is what both AgenticPay and ASTRA converge on independently:

```
LLM thinks in natural language:
  <mental_model>
  The seller started at $0.10/request. They've conceded to $0.07 over 3 rounds.
  Their stance is Neutral+Fair (λ=0.8). My aspiration at t=0.6 with boulware 
  curve is u(0.6) = 1.0 × (1 - 0.6^4) = 0.87. Target utility = 0.87.
  LP solver suggests: price=$0.04, latency=150ms, uptime=99.5%
  This gives estimated opponent utility of 0.72 — likely acceptable.
  </mental_model>

LLM outputs structured action:
  ### OFFER(price=0.04, latency_ms=150, uptime_pct=99.5) ###
  
  "I appreciate your flexibility on pricing. Given the volume we're discussing, 
   I'd like to propose $0.04 per request with a 150ms latency guarantee and 
   99.5% uptime SLA. This gives us both room to work with."
```

### Why Hybrid Wins for NegotiatorGrid

| Requirement | Pure NL | Pure Structured | Hybrid |
|-------------|---------|----------------|--------|
| On-chain settlement (exact price) | ❌ Regex fragile | ✅ | ✅ Structured action |
| Judge "wow factor" (AI reasoning visible) | ✅ | ❌ | ✅ `<mental_model>` block |
| Kite x402 compatibility (price for `approve_payment`) | ❌ | ✅ | ✅ Parse structured token |
| NegMAS/NegoLog interop (tuple-based offers) | ❌ | ✅ | ✅ Structured → tuple |
| Opponent modeling (LLM inference) | ✅ | ❌ | ✅ LLM reasons about opponent |
| Pareto optimality (LP/aspiration optimization) | ❌ | ✅ | ✅ LP generates candidates |
| A2A message transport | ❌ NL is ambiguous | ✅ JSON is clean | ✅ Structured payload + NL explanation |

```
│                    NegotiatorGrid Agent                       │
│                                                               │
│  ┌─────────────────────────────────────────────────────────┐ │
│  │ Stage 1: Opponent Modeling (LLM + NegoLog)               │ │
│  │   - FrequencyLinearUFunModel from received offers        │ │
│  │   - ASTRA-style Stance classification (Generous/Neutral/ │ │
│  │     Greedy) from utility deltas                          │ │
│  │   - On-chain reputation score from Kite agent profile    │ │
│  │   → Outputs: estimated opponent ufun + λ parameter       │ │
│  └─────────────────────────────────────────────────────────┘ │
│                          ↓                                    │
│  ┌─────────────────────────────────────────────────────────┐ │
│  │ Stage 2: Offer Optimization (NegMAS + aspiration curve)  │ │
│  │   - PolyAspiration(exponent=f(λ)) sets target utility    │ │
│  │   - InverseUtilityFunction finds offers at target level  │ │
│  │   - Or: LP solver for multi-issue Pareto candidates      │ │
│  │   → Outputs: N candidate offers as tuples                │ │
│  └─────────────────────────────────────────────────────────┘ │
│                          ↓                                    │
│  ┌─────────────────────────────────────────────────────────┐ │
│  │ Stage 3: LLM Selection + Expression                      │ │
│  │   - LLM (Claude/GPT-5) scores candidates for acceptance  │ │
│  │   - Selects best offer + generates NL explanation         │ │
│  │   - Outputs structured action token:                      │ │
│  │     ### OFFER(price=X, latency=Y, uptime=Z) ###          │ │
│  │   - Plus natural language reasoning for the counterparty  │ │
│  └─────────────────────────────────────────────────────────┘ │
│                          ↓                                    │
│  ┌─────────────────────────────────────────────────────────┐ │
│  │ Stage 4: Settlement (Kite x402 + MCP)                    │ │
│  │   - On agreement: extract price from structured token     │ │
│  │   - Call approve_payment(amount=price)                    │ │
│  │   - Attest welfare score: GlobalScore = γ^(t-1) × (...)  │ │
│  └─────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────┘
```

### Message Format for A2A Transport

```json
{
  "type": "negotiate/offer",
  "round": 5,
  "relative_time": 0.6,
  "structured_action": {
    "action": "OFFER",
    "terms": {"price": 0.04, "latency_ms": 150, "uptime_pct": 99.5}
  },
  "natural_language": "Given our discussion, I propose $0.04/request with 150ms latency and 99.5% uptime.",
  "mental_model_hash": "0xabc123...",
  "sender_did": "did:kite:buyer.eth/negotiator-v1"
}
```

The `structured_action` is what the protocol parses and enforces. The `natural_language` is what the demo shows to judges. The `mental_model_hash` is attestable on-chain without revealing reasoning.
