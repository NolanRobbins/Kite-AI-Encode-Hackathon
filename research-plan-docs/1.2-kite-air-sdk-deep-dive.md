## 2. KiteClient Initialization

**Doc Section**: Getting Started > "Authentication"; Source code: `kite_client.py` [Sources 1, 3]

```python
from gokite import KiteClient

client = KiteClient(
    api_key: str = None,       # KitePass API key. Falls back to env var KITE_API_KEY
    base_url: str = None,      # API base URL. Default: "https://neo.prod.gokite.ai"
    verbose: bool = False       # Enable detailed HTTP request/response logging
)
```

### What Happens on Init

1. Reads `api_key` from param or `KITE_API_KEY` env var. Raises `KiteAuthenticationError` if missing.
2. Creates a `requests.Session` with headers:
   ```
   X-API-KEY: {api_key}
   Content-Type: application/json
   ```
3. Initializes an in-memory service details cache (`_service_details` dict)
4. If `verbose=True`, configures DEBUG logging with masked credentials

### Base URL

```
https://neo.prod.gokite.ai
```

This is the Kite AIR platform backend (not the chain RPC). All SDK methods hit REST endpoints under this base.

## 3. Full Method Inventory

**Doc Section**: Source code inspection of `kite_client.py` [Source 3]

### Public Methods

| Method | Signature | What It Does |
|--------|-----------|-------------|
| `get_service_info()` | `get_service_info(service_id: str) -> str` | Returns a human-readable description of a service including endpoints, pricing, request/response format. Parses the OpenAPI schema. |
| `call_service()` | `call_service(service_id: str, payload: dict, headers: dict = {}) -> dict` | Calls a service with payload validation against its OpenAPI schema. Handles payment authorization via KitePass API key. |
| `load_service_description()` | `load_service_description(service_id: str) -> str` | Returns just the description text for a service. |
| `load_service_input_fields()` | `load_service_input_fields(service_id: str) -> Dict[str, str]` | Extracts input field names and types from the service's OpenAPI schema. Returns `{}` for GET endpoints. |
| `load_service_response_fields()` | `load_service_response_fields(service_id: str) -> Dict[str, str]` | Extracts response field names and types from the OpenAPI schema. |
| `make_payment()` | `make_payment(to_address: str, amount: float) -> str` | **NOT IMPLEMENTED** — raises `NotImplementedError("MakePayment is not implemented yet")` |
| `enable_verbose_logging()` | `@classmethod enable_verbose_logging()` | Enables DEBUG logging globally for all KiteClient instances |
| `disable_verbose_logging()` | `@classmethod disable_verbose_logging()` | Disables verbose logging globally |

### Internal Methods

| Method | What It Does |
|--------|-------------|
| `_get_service_details(service_id)` | Fetches service metadata from `GET /v1/asset?id={service_id}` with caching. Supports service IDs prefixed with `agent_`, `tool_`, or `dataset_`. Falls back to name-based lookup. |
| `_handle_response(response)` | Uniform HTTP response handler. Raises typed exceptions for 401/403/404/4xx/5xx. |
| `_handle_service_response(response)` | Service-specific response handler (less strict — returns text if JSON parsing fails). |
| `_log_method_call(...)` | Verbose logging for method calls (masks sensitive params) |
| `_log_http_request(...)` | Verbose logging for HTTP requests (masks auth headers) |
| `_log_http_response(...)` | Verbose logging for HTTP responses |

### LangChain Integration

```python
from gokite.langchain_tools import KitePaymentTool

# Auto-creates KiteClient from env
tool = KitePaymentTool.from_env()

# Use as a LangChain BaseTool
# NOTE: Calls make_payment() which is NOT IMPLEMENTED
```

The `KitePaymentTool` wraps `make_payment()`, which is currently a stub. This LangChain tool is non-functional in v0.0.15.

### What's NOT in the SDK

The SDK is a **thin service-calling client**. It does NOT have:
- `list_services()` — no catalog listing endpoint
- Agent registration/management (that's the REST API, see Section 6)
- Wallet operations
- Session key management
- DID resolution
- Reputation queries
- Agent-to-agent discovery (that's the REST API, see Section 7)
- On-chain payment execution

### API Endpoints Used by SDK

| SDK Method | HTTP Call |
|-----------|----------|
| `_get_service_details()` | `GET {base_url}/v1/asset?id={service_id}` or `?name={service_id}` |
| `call_service()` | `POST {base_url}/v1/service/{service_id}` with body `{"data": payload}` |

That's it — only two HTTP endpoints are used by the entire SDK.

## 4. KitePass Claim Flow

**Doc Section**: Getting Started > "Step1: [As an agent user] Claim KitePass" [Source 1]

### Step-by-Step

1. **Visit** [https://app.gokite.ai/](https://app.gokite.ai/)
2. **Authentication**: Create account via Particle Network. Each login requires email verification code sent by `verify@particle.network`. [Source 1, "Account Authentication"]
3. **Navigate**: Click "Go ->" on "Register your Agent for a KitePass" or use top-right menu → "Claim KitePass"
4. **Name your pass**: Enter passport name and description. **Passport name is immutable once set.** [Source 1]
5. **Configure spending rules**:
   - **Frequency**: Time window for budget (e.g., daily, weekly)
   - **Budget**: Payment amount allowed per frequency window
   - **Target Provider**: Which types of providers the budget applies to
6. **Copy API key**: The portal generates an API key (prefixed `api_key_`). This is what you pass to `KiteClient(api_key=...)`.

### What KitePass Actually Is

From the Agent Passport architecture [Source 7]:

| Layer | What It Provides |
|-------|-----------------|
| **Passport** | Identity + auth + delegation: User/Agent IDs, Sessions (budgets + spending rules), Delegations (signed payment intents) |
| **Payment** | On-chain value transfer on Kite L1, x402 facilitator integration |
| **MCP Tool** | Integration for AI agents: Kite Payment, session/delegation handling |

The KitePass is essentially a **Session** object: a master budget with spending rules, time limits, and merchant restrictions, created by user signature [Source 7].

### Current Access Status

Kite AIR is in **limited access / invite-only** mode. Agent builders get invited, and the KitePass portal is at [https://x402-portal-eight.vercel.app/](https://x402-portal-eight.vercel.app/) [Source 8].

## 5. API Key → On-Chain Identity Mapping

**Doc Section**: Getting Started [Source 1]; API References [Source 5]; Workflow: Agent Builders [Source 6]

### How It Works

```
User (human) ─── Particle Network OAuth ───> Kite Account
     │                                            │
     └── creates KitePass ──> API Key             │
              │                                   │
              ├── User ID (attached automatically) │
              ├── Agent ID (attached automatically)│
              ├── Spending Rules (user-configured) │
              └── Session (master budget)          │
                                                   │
                            On-Chain Identity ◄────┘
```

The API key is **not** a raw private key or wallet address. It's a **session credential** that maps to:

1. **User ID** — the authenticated human's identity on Kite
2. **Agent ID** — the specific agent instance this key authorizes
3. **Session** — the spending rules and budget constraints

When `KiteClient` sends `X-API-KEY: {api_key}` with requests, the Kite backend (`neo.prod.gokite.ai`) resolves this to the user→agent→session chain and enforces spending rules before proxying the call to the target service [Sources 5, 6].

### Two-Staged Delegation Model

From the Agent Builder Guide [Source 4]:

1. **Authentication at MCP connection**: End users authenticate and approve the agent during connection to Kite MCP. This establishes a trusted session.
2. **Signature for delegation proof**: When a specific purchase is initiated, the agent generates a delegation proof for the end user to sign. Merchants verify this proof before executing payment.

The API key handles stage 1 (session authentication). Stage 2 (delegation proof) happens through the MCP tools at transaction time.

### Security Architecture

From the API References [Source 5]:

> "Kite does NOT store user credentials to manage users' financial resources. All user authentication flows through trusted third-party OAuth providers."

| Actor | Authentication Method |
|-------|---------------------|
| End-users | Third-party OAuth (Particle Network) |
| AI Agents | MCP + User OAuth |
| Agent Builders | Developer API key |
| Merchants | Proof Verification |

## 6. Service Discovery — Browsing the App Store Programmatically

### Current State: SDK Has NO Catalog Listing

The `gokite` SDK (v0.0.15) has **no** `list_services()` or `search_services()` method. The only way to look up a service is by its **known ID**:

```python
# You must already know the service_id
service_info = client.get_service_info(service_id="agent_LpzYVzWGzjGiZBI3HTm4ZCKj")
```

### How You're Supposed to Find Services Today

From the Getting Started guide [Source 1]:

> "Visit https://app.gokite.ai/ to browse service, on service detail page, copy service ID"

This is a **manual, browser-based** discovery flow. There's no programmatic catalog API exposed in the SDK.

### The Backend Endpoint Exists But Requires Auth

The SDK hits `GET /v1/asset?id={service_id}` for individual lookups. Testing shows:
- `GET /v1/assets` → returns `400` (likely needs auth or params)
- `GET /v1/asset` without params → returns `500`
- The endpoint exists but requires proper authentication

## 7. Agent-to-Agent Discovery — Critical for NegotiatorGrid

**Doc Section**: Agent Builder Guide > "Agent Discovery" [Source 4]

### Answer: YES — via the REST API (not the Python SDK)

The Agent Builder Guide [Source 4] documents a full A2A-compatible agent discovery system that is **not** exposed in the `gokite` Python SDK but is available as REST API endpoints.

### Agent Registration

#### `POST /v1/agents/register`

Register a NegotiatorGrid agent with an A2A Agent Card:

```json
{
  "agentCard": {
    "name": "NegotiatorGrid Price Negotiator",
    "description": "Agent-to-agent price negotiation for service procurement",
    "url": "https://negotiatorgrid.example.com/a2a",
    "version": "1.0.0",
    "provider": {
      "name": "NegotiatorGrid",
      "url": "https://negotiatorgrid.example.com"
    },
    "capabilities": {
      "streaming": true,
      "pushNotifications": false
    },
    "skills": [
      {
        "name": "price_negotiation",
        "description": "Bilateral price negotiation with counter-offers and deadline pressure",
        "tags": ["negotiation", "pricing", "bilateral"]
      },
      {
        "name": "sla_enforcement",
        "description": "Encodes negotiated terms as on-chain SLA contracts",
        "tags": ["sla", "enforcement", "smart-contract"]
      }
    ]
  }
}
```

**Response:**
```json
{
  "agent_id": "agent_abc123",
  "agent_card_url": "https://negotiatorgrid.example.com/a2a",
  "status": "active",
  "created_at": "2026-04-08T..."
}
```

### Agent Discovery (Search)

#### `GET /v1/agents/search`

**Query Parameters:**
| Param | Description | NegotiatorGrid Use |
|-------|------------|-------------------|
| `skill` | Filter by skill name | `"price_negotiation"` to find other negotiators |
| `tag` | Filter by skill tag | `"negotiation"`, `"pricing"` |
| `capability` | Filter by capability | `"streaming"` for real-time negotiation |
| `provider` | Filter by provider name | Find agents from specific organizations |
| `limit` | Results per page (max 100) | Pagination |
| `offset` | Pagination offset | |

**Response:**
```json
{
  "agents": [
    {
      "agent_id": "agent_abc123",
      "name": "Shopping Assistant Bot",
      "description": "...",
      "agent_card_url": "https://...",
      "reputation_score": 85,
      "total_transactions": 1250,
      "skills": ["product_search", "price_comparison", "payment_processing"],
      "capabilities": { "streaming": true }
    }
  ],
  "total": 15,
  "has_more": false
}
```

### Agent Profile Lookup

#### `GET /v1/agents/{agent_id}`

Returns full profile including reputation score, total transactions, and cached A2A Agent Card.

### Transaction History

#### `GET /v1/agents/{agent_id}/transactions`

Search transaction history with filters: `from_address`, `to_address`, `user_id`, `status`, `date_from`, `date_to`.

### MCP Tools (Payment Operations)

Available via Kite's MCP server at `https://mcp.prod.gokite.ai/{api_key_value}/mcp`:

| Tool | Description |
|------|------------|
| `check_session_config` | Check spending rules, expiration |
| `get_user_id` | Get authenticated user ID |
| `get_agent_id` | Get authenticated agent ID |
| `get_merchant_info` | Fetch verified merchant identity and policy metadata |
| `check_wallet_balance` | Check available funds |
| `generate_payment_delegation` | Create delegation request within session limits |
| `get_payment_delegation` | Retrieve signed proof authorizing payment |
| `revoke_payment_delegation` | Revoke a previously issued delegation |
| `get_payment_history` | Retrieve payment history |
| `get_payment_status` | Check status of specific payment |
| `terminate_session` | End active session |

### Recommended Architecture for NegotiatorGrid

```
NegotiatorGrid Agent
├── gokite (Python SDK)
│   ├── KiteClient → service discovery + service calling
│   └── API key auth via KitePass
│
├── REST API calls (requests library)
│   ├── POST /v1/agents/register → register as negotiator
│   ├── GET /v1/agents/search?tag=negotiation → find counterparties
│   └── GET /v1/agents/{id} → get opponent reputation_score
│
├── MCP Server (https://mcp.prod.gokite.ai/{key}/mcp)
│   ├── generate_payment_delegation → commit to negotiated price
│   ├── check_wallet_balance → verify counterparty can pay
│   └── get_merchant_info → verify counterparty identity
│
├── A2A Protocol (direct agent-to-agent)
│   ├── Opponent's agent_card_url → establish negotiation channel
│   └── JSON-RPC over HTTPS → exchange offers/counter-offers
│
└── gokite-aa-sdk (Node.js, for on-chain settlement)
    ├── configureSpendingRules({budget: negotiatedPrice})
    └── Deploy ClientAgentVault with deal terms
```

### Critical Finding: Agent Discovery IS Possible

The `GET /v1/agents/search` endpoint with skill/tag filtering means NegotiatorGrid agents **can** discover each other programmatically. The flow:

1. Both NegotiatorGrid buyer and seller register with skill tag `"negotiation"`
2. Buyer searches `GET /v1/agents/search?tag=negotiation` to find sellers
3. Buyer reads seller's `agent_card_url` to get A2A endpoint
4. Buyer initiates negotiation via A2A JSON-RPC to seller's endpoint
5. After deal, buyer uses MCP `generate_payment_delegation` to commit
6. Seller verifies delegation proof and delivers service

This is the peer discovery loop NegotiatorGrid needs. The REST API exists in the docs [Source 4] even though the Python SDK doesn't wrap it yet.
