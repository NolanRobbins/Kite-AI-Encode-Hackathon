## Part I: ANEX Protocol Extraction

### 1. The Six FIPA-Contract-Net Phases in ANEX

ANEX defines six sequential phases, mapped to FIPA interaction protocols [Source 1]:

```
Phase 1: SELF-IDENTIFICATION          Protocol: ANEX-Handshaking
  Agent A → Agent B: REQUEST
  Content: "Hi, I'm [Owner]'s AI assistant [PA*]"
  Purpose: Declare ANEX compliance, introduce identity
  
Phase 2: INITIATION OF ENGAGEMENT     Protocol: ANEX-Handshaking
  Agent A → Agent B: REQUEST
  Content: {request: "Set up time for meeting. Ok to continue?"}
  Purpose: Propose interaction scope

Phase 3: RESPONSE HANDLING            Protocol: ANEX-Handshaking
  Agent B → Agent A: AGREE | REFUSE | PROPOSE
  - AGREE: proceed
  - REFUSE: end interaction
  - PROPOSE: request modification (e.g., "provide email for verification")

Phase 4: NEGOTIATION OF TERMS         Protocol: FIPA-Contract-Net
  Agent A → Agent B: CFP (Call for Proposal)
  Content: {identity, owner, relation, request_type, access[], promise[]}
  Agent B → Agent A: PROPOSE (counter-terms)
  Agent A → Agent B: ACCEPT-PROPOSAL | REJECT-PROPOSAL
  Purpose: Agree on data access permissions, promises, conditions

Phase 5: DATA EXCHANGE                Protocol: ANEX-Data-Exchange
  Agent A ↔ Agent B: INFORM
  Content: actual data (e.g., meeting_times[])
  Transport: Secure WebSocket (wss://)

Phase 6: SESSION TERMINATION          Protocol: ANEX-Termination
  Agent A → Agent B: INFORM
  Content: {message: "Session terminated."}
```

### 2. ACL Message Structure

Every ANEX message uses this envelope [Source 1, §4.2]:

```json
{
  "performative": "CFP",                    // Action type
  "sender": "AgentA",                       // Initiating agent ID
  "receiver": "AgentB",                     // Target agent ID
  "content": { ... },                       // Payload (JSON)
  "language": "JSON",                       // Content encoding
  "ontology": "ANEX-Ontology",             // Shared vocabulary reference
  "protocol": "FIPA-Contract-Net"           // Which interaction protocol
}
```

### 3. Performative Vocabulary

ANEX uses a subset of the [FIPA Communicative Act Library](https://jade.tilab.com/papers/JADETutorialIEEE/JADETutorial_FIPA.pdf) [Sources 1, 2, 6]:

| Performative | Direction | When Used | ANEX Phase |
|-------------|-----------|-----------|-----------|
| `REQUEST` | Initiator → Participant | Self-identification, engagement initiation | 1, 2 |
| `AGREE` | Participant → Initiator | Accept engagement | 3 |
| `REFUSE` | Participant → Initiator | Decline engagement | 3 |
| `CFP` | Initiator → Participant | Call for proposal — request terms | 4 |
| `PROPOSE` | Participant → Initiator | Submit or modify terms | 3, 4 |
| `ACCEPT-PROPOSAL` | Initiator → Participant | Accept proposed terms | 4 |
| `REJECT-PROPOSAL` | Initiator → Participant | Reject proposed terms | 4 |
| `INFORM` | Either → Either | Data exchange, session termination | 5, 6 |
| `FAILURE` | Either → Either | Error notification | Any |
| `NOT-UNDERSTOOD` | Either → Either | Unrecognized message | Any |
| `CANCEL` | Either → Either | Cancel a pending request | Any |

### 4. FIPA-CNP → A2A Protocol Message Mapping

A2A uses JSON-RPC 2.0 over HTTP(S) with methods like `message/send` and `message/stream` [Sources 3, 4, 7]. The mapping:

| FIPA-CNP Concept | A2A JSON-RPC Equivalent |
|-----------------|----------------------|
| Performative | JSON-RPC `method` field (custom namespace) |
| Sender | `params.message.contextId` + agent card URL |
| Receiver | HTTP endpoint URL (from agent card discovery) |
| Content | `params.message.parts[].text` (or `.data` for structured) |
| Ontology | Agent card `skills[].tags` + custom extension headers |
| Protocol | A2A task lifecycle (SUBMITTED → WORKING → DONE/FAILED) |
| CFP | `method: "negotiate/cfp"` — custom A2A extension |
| PROPOSE | `method: "negotiate/propose"` |
| ACCEPT-PROPOSAL | `method: "negotiate/accept"` |
| REJECT-PROPOSAL | `method: "negotiate/reject"` |
| INFORM (data) | `method: "message/send"` with artifact |
| Session ID | `params.message.contextId` (A2A session tracking) |

## Part II: NegotiatorGrid Wire Format Design

### Design Principles

1. **FIPA-CNP semantics** for negotiation formalism (the performative vocabulary is proven)
2. **A2A JSON-RPC 2.0 transport** for network interoperability (Kite's agent registry uses A2A)
3. **x402-compatible settlement fields** for payment execution after agreement
4. **Kite DID-based identity** for on-chain verifiability
5. **Structured action tokens** (from AgenticPay research) for reliable LLM → protocol bridge

### Message Envelope (Shared by All Message Types)

Every NegotiatorGrid message is a valid A2A JSON-RPC 2.0 request with a FIPA-inspired extension:

```json
{
  "jsonrpc": "2.0",
  "id": "msg-uuid-v4",
  "method": "negotiate/{performative}",
  "params": {
    "negotiation_id": "neg-uuid-v4",
```

### Additional Message Types

#### REJECT (REJECT-PROPOSAL)

```json
{
  "method": "negotiate/reject",
  "params": {
    "content": {
      "rejected_offer_id": "propose-007",
      "reason": "price_too_high",
      "counter_hint": "I can accept up to $0.02/request",
      "natural_language": "The price is above my budget ceiling. Can you do $0.02?"
```

```json
{
```

## Part III: Complete Protocol Flow

```
┌──────────────────────────────────────────────────────────────────┐
│           NegotiatorGrid Bilateral Negotiation Protocol           │
│                                                                    │
│  Phase 1: DISCOVERY (Kite A2A)                                    │
│    Buyer: GET /v1/agents/search?tag=negotiation                   │
│    → Finds seller's agent_card_url                                │
│    Buyer: GET seller/.well-known/agent.json                       │
│    → Gets seller's capabilities, DID, skills                      │
│                                                                    │
│  Phase 2: CFP (negotiate/cfp)                                     │
│    Buyer → Seller: "I need weather data, budget $0.001-$0.05"    │
│    Seller evaluates: can I meet this? is buyer reputable?         │
│                                                                    │
│  Phase 3: NEGOTIATION LOOP (negotiate/propose × N)                │
│    Seller → Buyer: PROPOSE(price=$0.05, latency=100ms)           │
│    Buyer → Seller: PROPOSE(price=$0.01, latency=200ms)           │
│    Seller → Buyer: PROPOSE(price=$0.04, latency=120ms)           │
│    Buyer → Seller: PROPOSE(price=$0.02, latency=180ms)           │
│    ... aspiration curves converge ...                              │
│    Seller → Buyer: PROPOSE(price=$0.03, latency=150ms)           │
│                                                                    │
│  Phase 4: ACCEPTANCE (negotiate/accept)                           │
│    Buyer → Seller: ACCEPT(price=$0.03, deal_hash, signatures)    │
│    Buyer computes welfare attestation (GlobalScore, utilities)    │
│                                                                    │
│  Phase 5: SETTLEMENT (x402 + Kite MCP)                           │
│    Buyer: MCP approve_payment(amount=$0.03, payee=seller_wallet)  │
│    Buyer → Seller service: GET /api/weather + X-Payment header    │
│    Seller: facilitator /v2/settle → on-chain transfer             │
│    Session key created: valueLimit=$0.03, recipient=seller_only   │
│                                                                    │
│  Phase 6: TERMINATION (negotiate/end)                             │
│    Both agents: INFORM("Session complete")                         │
│    Welfare attestation stored on-chain                             │
└──────────────────────────────────────────────────────────────────┘
```

## Part IV: FIPA-CNP → A2A → x402 Bridge Reference

| FIPA-CNP Phase | NegotiatorGrid Method | A2A Lifecycle | Kite x402 Action |
|---------------|---------------------|---------------|-----------------|
| CFP | `negotiate/cfp` | Task SUBMITTED | — |
| PROPOSE | `negotiate/propose` | Task WORKING | — |
| PROPOSE (counter) | `negotiate/propose` | Task WORKING | — |
| ACCEPT-PROPOSAL | `negotiate/accept` | Task DONE | `approve_payment()` → `X-Payment` header |
| REJECT-PROPOSAL | `negotiate/reject` | Task WORKING (continue) | — |
| REFUSE | `negotiate/end` | Task FAILED | — |
| INFORM (data) | `message/send` | Artifact delivery | Service response with data |
| FAILURE | `negotiate/end` | Task FAILED | Escrow reclaim |

### x402 Integration Points

The `DEAL_CONTRACT` message's `settlement` block maps directly to x402:

```
DEAL_CONTRACT.settlement.method = "x402-gokite-aa"
  → Use Kite AA wallet + Pieverse facilitator
  
DEAL_CONTRACT.settlement.escrow_amount = agreed_price × volume_commitment
  → addSessionKeyRule(valueLimit=escrow_amount)
  
DEAL_CONTRACT.settlement.facilitator = "0x12343e..."
  → POST facilitator.pieverse.io/v2/settle

DEAL_CONTRACT.settlement.session_key_config
  → Direct input to gokite-aa-sdk configureSpendingRules()
```

## Action Items

1. **Publish this schema as a JSON Schema** at `https://negotiatorgrid.example.com/schemas/v1/` for agent discovery. Reference it in the agent card's `skills[].tags`.

2. **Implement the `negotiate/` method namespace** as an A2A extension. Register NegotiatorGrid agents with skill `"price_negotiation"` and tag `"negotiatorgrid-v1"` so counterparties discover the protocol support.

3. **The `deal_hash` is the cryptographic anchor.** Compute `keccak256(canonical_json(agreed_terms))` — both parties sign this, and it goes on-chain as the `metadata` parameter in `addSessionKeyRule()`.

4. **The `welfare_attestation` block is optional but powerful for demo.** Computing `GlobalScore = γ^(t-1) × (D + 4·rb·rs·W + E)` at deal time and including it in the contract gives judges a quantitative measure of deal quality.

5. **The `natural_language` field in PROPOSE messages is the LLM output.** The structured `offer` fields are what the protocol enforces. This implements the hybrid pattern recommended in the LLM negotiation synthesis.
