## 1. tools/list — Request/Response Format

**Sources**: [MCP Spec (2025-03-26)](https://github.com/modelcontextprotocol/specification/blob/main/docs/specification/2025-03-26/server/tools.mdx), [MCP Spec (2025-11-25)](https://github.com/modelcontextprotocol/specification/blob/main/docs/specification/2025-11-25/server/tools.mdx)  
**Confidence**: HIGH

### Server Capability Declaration

```json
{
  "capabilities": {
    "tools": {
      "listChanged": true
    }
  }
}
```

`listChanged: true` means the server will emit `notifications/tools/list_changed` when tools are added/removed at runtime — critical for dynamic discovery.

### Request (JSON-RPC)

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list",
  "params": {
    "cursor": "optional-cursor-value"
  }
}
```

Supports pagination via `cursor`/`nextCursor`.

### Response

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "tools": [
      {
        "name": "get_weather",
        "title": "Weather Information Provider",
        "description": "Get current weather information for a location",
        "inputSchema": {
          "type": "object",
          "properties": {
            "location": {
              "type": "string",
              "description": "City name or zip code"
            }
          },
          "required": ["location"]
        },
        "outputSchema": {
          "type": "object",
          "properties": {
            "temperature": { "type": "number" },
            "condition": { "type": "string" }
          }
        },
        "icons": [
          {
            "src": "https://example.com/weather-icon.png",
            "mimeType": "image/png",
            "sizes": ["48x48"]
          }
        ],
        "execution": {
          "taskSupport": "optional"
        },
        "annotations": {}
      }
    ],
    "nextCursor": "next-page-cursor"
  }
}
```

### Tool Definition Fields (2025-11-25 spec)

| Field | Required | Description |
|-------|----------|-------------|
| `name` | Yes | Unique identifier (1-128 chars, `[A-Za-z0-9_\-\.]`) |
| `title` | No | Human-readable display name (added in 2025-11-25) |
| `description` | Yes | What the tool does |
| `inputSchema` | Yes | JSON Schema for parameters |
| `outputSchema` | No | JSON Schema for structured output (added 2025-06-18) |
| `icons` | No | Array of icon objects (added 2025-11-25) |
| `execution` | No | Task support: `"forbidden"`, `"optional"`, `"required"` |
| `annotations` | No | Untrusted metadata about behavior |

### Key Finding for NegotiatorGrid
The `annotations` field is the extension point. We can inject negotiation metadata here: `x402_price_range`, `payment_network`, `erc8004_agent_id`. Clients MUST treat annotations as untrusted unless from trusted servers — this is exactly why we need ERC-8004 verification.

## 2. tools/call — Request/Response Format

**Sources**: [MCP Spec](https://github.com/modelcontextprotocol/specification/blob/main/docs/specification/2025-03-26/server/tools.mdx)  
**Confidence**: HIGH

### Request

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": {
      "location": "New York"
    }
  }
}
```

### Response (Unstructured)

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "Current weather in New York:\nTemperature: 72°F"
      }
    ],
    "isError": false
  }
}
```

### Response (Structured — spec 2025-06-18+)

When the tool defines an `outputSchema`, the response includes `structuredContent`:

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "content": [
      { "type": "text", "text": "Temperature: 22.5°C, partly cloudy" }
    ],
    "structuredContent": {
      "temperature": 22.5,
      "condition": "partly cloudy",
      "humidity": 65,
      "city": "New York"
    },
    "isError": false
  }
}
```

### Content Types Supported
- `text` — plain text
- `image` — base64-encoded with mimeType
- `audio` — base64-encoded audio
- `resource` — embedded resource with URI (can be subscribed to later)

### Error Handling
Two layers:
1. **Protocol errors** — JSON-RPC error codes (e.g., `-32602` for unknown tool)
2. **Tool execution errors** — `isError: true` in result (API failures, business logic)

### Key Finding for NegotiatorGrid
The `tools/call` response with `isError: true` is our hook for x402. When a tool call fails with a payment-required condition, we return `isError: true` with payment instructions in the text content. The agent then negotiates price and retries with x402 headers at the HTTP transport layer.

## 3. Transport Options: stdio vs SSE vs Streamable HTTP

**Sources**: [MCP Spec Transports](https://github.com/modelcontextprotocol/specification/blob/main/docs/specification/2025-03-26/basic/transports.mdx)  
**Confidence**: HIGH

### stdio

- Client launches server as a **subprocess**
- Communication via stdin/stdout, newline-delimited JSON-RPC
- Server MAY write logs to stderr
- **Use case**: Local tools, development, Claude Desktop integrations
- **Limitation**: Can't work for remote/networked services

### Streamable HTTP (replaces SSE in spec 2025-03-26+)

- Server is an **independent process** handling multiple clients
- Single HTTP endpoint (e.g., `https://example.com/mcp`)
- Supports both POST and GET methods
- **POST**: Client sends JSON-RPC messages; server responds with either:
  - `Content-Type: application/json` (single response)
  - `Content-Type: text/event-stream` (SSE stream for multiple messages)
- **GET**: Opens SSE stream for server-initiated messages (notifications, requests)
- **Session management**: `Mcp-Session-Id` header for stateful sessions
- **Resumability**: SSE event IDs + `Last-Event-ID` header for reconnection

### Key Protocol Details

```
Client → POST /mcp
  Headers: Accept: application/json, text/event-stream
  Body: {"jsonrpc":"2.0","id":1,"method":"tools/list"}

Server → 200 OK
  Content-Type: application/json  (or text/event-stream)
  Mcp-Session-Id: 1868a90c...
```

### Legacy SSE Transport (2024-11-05, deprecated)

- Two endpoints: GET /sse (stream) + POST /messages (send)
- Server sends `endpoint` event first with POST URL
- Still supported via backwards-compat negotiation

### Backwards Compatibility Handshake

Clients wanting to support both:
1. POST `InitializeRequest` to server URL
2. If 200 → Streamable HTTP
3. If 4xx → GET same URL, expect SSE stream with `endpoint` event → Legacy SSE

### Key Finding for NegotiatorGrid
**Streamable HTTP is our transport.** It's the only option for remote MCP servers, which is what x402-gated services will be. The HTTP layer gives us the natural place to intercept 402 responses. The `Mcp-Session-Id` header enables stateful negotiation sessions.

## 4. notifications/tools/list_changed

**Sources**: [MCP Spec](https://github.com/modelcontextprotocol/specification/blob/main/docs/specification/2025-03-26/server/tools.mdx)  
**Confidence**: HIGH

### Server Push Notification

```json
{
  "jsonrpc": "2.0",
  "method": "notifications/tools/list_changed"
}
```

- Sent by servers with `"listChanged": true` capability
- No params, no id (it's a notification, not a request)
- Client should respond by re-calling `tools/list` to get updated tool set

### Message Flow

```
Server → Client: {"jsonrpc":"2.0","method":"notifications/tools/list_changed"}
Client → Server: {"jsonrpc":"2.0","id":3,"method":"tools/list"}
Server → Client: {"jsonrpc":"2.0","id":3,"result":{"tools":[...updated list...]}}
```

### Key Finding for NegotiatorGrid
This is the mechanism that enables **runtime tool discovery**. When our negotiation middleware adds a new x402-gated service to the MCP session, it fires `list_changed` to tell the agent "new tools are available." The agent re-lists, sees the negotiation/payment tools, and can use them. This is the MCP-native equivalent of Docker's `mcp-add`.

### stdio Client

import asyncio
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

server_params = StdioServerParameters(
    command="python",
    args=["server.py"],
)

async def run():
    async with stdio_client(server_params) as (read, write):
        async with ClientSession(read, write) as session:
            await session.initialize()

            # List tools
            tools = await session.list_tools()
            print([t.name for t in tools.tools])

            # Call a tool
            result = await session.call_tool("add", arguments={"a": 5, "b": 3})

            print(result.structuredContent)  # If outputSchema defined

asyncio.run(run())

## 7. Docker Dynamic MCP: mcp-find / mcp-add / mcp-exec

**Sources**: [Docker Blog](https://www.docker.com/blog/dynamic-mcps-stop-hardcoding-your-agents-world/), [Docker Dynamic MCP Docs](https://docs.docker.com/ai/mcp-catalog-and-toolkit/dynamic-mcp/)  
**Confidence**: HIGH

### Primordial Tools

The Docker MCP Gateway injects these "primordial" tools into every agent session:

| Tool | Description |
|------|-------------|
| `mcp-find` | Search for MCP servers in the catalog by name or description |
| `mcp-add` | Add a new MCP server to the current session |
| `mcp-exec` | Execute a tool by name that exists in the current session |
| `mcp-config-set` | Configure settings for an MCP server |
| `mcp-remove` | Remove an MCP server from the session |
| `code-mode` | Create a JavaScript sandbox combining multiple MCP server tools |

### Dynamic Discovery Flow

```
1. Agent calls mcp-find("SQL databases")
2. Gateway searches Docker MCP Catalog (300+ servers) by name/description
3. Returns matching servers with details
4. Agent calls mcp-add("postgres")
5. Gateway pulls Docker image from trusted registry
6. Spins up MCP server container locally
7. New tools from postgres server appear in agent's session
8. Agent calls mcp-exec or direct tool call
```

### The Docker MCP Catalog

- 300+ curated, verified MCP servers
- Packaged as Docker images on Docker Hub
- Registry repo: [github.com/docker/mcp-registry](https://github.com/docker/mcp-registry)
- **Custom catalogs** supported: curate a subset for your org
  - When using custom catalog, `mcp-find` searches only that catalog
  - Can include private MCP servers alongside public ones

### code-mode Tool (Experimental)

```
1. Agent calls code-mode with server names + tool name
2. Gateway creates JavaScript sandbox with access to those servers' tools
3. New composite tool registered in session
4. Agent calls the composite tool
5. Code executes in sandbox, can only interact through MCP tools
```

### Key Finding for NegotiatorGrid
Docker's pattern is our **architectural template**, but we need to replace the catalog with an on-chain registry. Where Docker uses `mcp-find` → Docker Hub catalog, we use `negotiate-find` → ERC-8004 Identity Registry + x402 pricing metadata. The flow becomes:

```
negotiate-find("weather API")
  → Query ERC-8004 registry for agents with matching capabilities
  → Filter by x402 support
  → Return candidates with reputation scores

negotiate-add("agent_id_42")
  → Verify ERC-8004 identity on-chain
  → Fetch agent-card.json for MCP endpoint
  → Connect via streamablehttp_client
  → List tools, inject into session

negotiate-price("get_weather", max_budget=0.10)
  → Run bilateral negotiation with opponent modeling
  → Agree on price
  → Sign x402 payment

negotiate-exec("get_weather", {"location": "NYC"})
  → Call tool with x402 payment header
  → Verify result
  → Submit reputation feedback to ERC-8004
```

## 8. How mcp-find Searches a Registry

**Sources**: [Docker Docs](https://docs.docker.com/ai/mcp-catalog-and-toolkit/catalog/), [Docker Blog](https://www.docker.com/blog/dynamic-mcps-stop-hardcoding-your-agents-world/)  
**Confidence**: MEDIUM

### Current Behavior

- `mcp-find` does **text search** by name and description against the Docker MCP Catalog
- No structured filtering (no filter by protocol, payment method, etc.)
- The catalog is a curated list — servers are added via PR to [github.com/docker/mcp-registry](https://github.com/docker/mcp-registry)
- No public REST API for programmatic catalog search documented
- Custom catalogs can restrict the search space but don't add filter dimensions

### Can It Filter by Payment Protocol (x402)?

**No.** The Docker MCP Catalog has no concept of payment protocols. It's a package registry (like npm) not a marketplace. Servers are free — there's no pricing metadata.

### Open Questions
- The catalog metadata schema is not publicly documented
- No evidence of structured tags or attributes beyond name/description
- The gateway source is not open (runs inside Docker Desktop)
- The `mcp-registry` repo defines server configs but not searchable metadata schemas

### Agent Identifier Format (CAIP-10)

### x402 Payment Flow at MCP Transport Layer

Based on [mcp-go-x402](https://github.com/mark3labs/mcp-go-x402) and [Coinbase x402 MCP docs](https://docs.cdp.coinbase.com/x402/mcp-server):

```
1. Client → POST /mcp (tools/call)
2. Server → 402 Payment Required
   Headers: PAYMENT-REQUIRED: base64({
     "scheme": "exact",
     "network": "kite-testnet",
     "asset": "0x0fF539...USDT",
     "payTo": "0xServerWallet",
     "maxAmountRequired": "50000",
     "description": "Weather data query",
     "maxTimeoutSeconds": 60
   })
3. Client parses requirements, runs negotiation engine
4. Client signs payment (EIP-3009 transferWithAuthorization for USDC, 
   or Permit2 for other ERC-20)
5. Client → POST /mcp (same request)
   Headers: PAYMENT-SIGNATURE: base64(signed_payment_payload)
6. Server → Facilitator: verify + settle on-chain
7. Server → 200 OK with tool result + PAYMENT-RESPONSE header
```

### Implementation Architecture for negotiate-find

```python
from web3 import Web3
from mcp import ClientSession
from mcp.client.streamable_http import streamablehttp_client
import httpx

KITE_RPC = "https://rpc-testnet.gokite.ai/"
IDENTITY_REGISTRY = "0x..."  # Deploy on Kite testnet

w3 = Web3(Web3.HTTPProvider(KITE_RPC))

async def negotiate_find(query: str, max_price_usdt: int = None) -> list[dict]:
    """Custom mcp-find that searches ERC-8004 + filters by x402."""
    
    # Step 1: Query ERC-8004 Identity Registry events
    registry = w3.eth.contract(
        address=IDENTITY_REGISTRY, 
        abi=IDENTITY_REGISTRY_ABI
    )
    
    # Get all registered agents
    events = registry.events.Registered.get_logs(fromBlock=0)
    
    candidates = []
    for event in events:
        agent_id = event.args.agentId
        agent_uri = event.args.agentURI
        
        # Step 2: Fetch agent-card.json
        async with httpx.AsyncClient() as client:
            card = await client.get(agent_uri)
            card_data = card.json()
        
        # Step 3: Filter by x402 support
        if "x402Support" not in card_data:
            continue
        
        # Step 4: Filter by price range
        if max_price_usdt:
            min_price = int(card_data["x402Support"].get("priceRange", {}).get("min", 0))
            if min_price > max_price_usdt:
                continue
        
        # Step 5: Check text match against query
        name = card_data.get("name", "").lower()
        desc = card_data.get("description", "").lower()
        if query.lower() not in name and query.lower() not in desc:
            continue
        
        # Step 6: Get reputation score
        reputation = w3.eth.contract(
            address=REPUTATION_REGISTRY, 
            abi=REPUTATION_REGISTRY_ABI
        )
        summary = reputation.functions.getSummary(
            agent_id, [], "", ""
        ).call()
        
        candidates.append({
            "agent_id": agent_id,
            "name": card_data["name"],
            "description": card_data["description"],
            "mcp_endpoint": next(
                s["endpoint"] for s in card_data["services"] 
                if s["name"] == "MCP"
            ),
            "price_range": card_data["x402Support"]["priceRange"],
            "networks": card_data["x402Support"]["networks"],
            "reputation_score": summary[1] / (10 ** summary[2]),
            "feedback_count": summary[0],
        })
    
    # Rank by reputation
    return sorted(candidates, key=lambda c: c["reputation_score"], reverse=True)
```

## Open Questions

1. **ERC-8004 on Kite**: The standard is live on Ethereum mainnet (Jan 2026) but are the registry contracts deployed on Kite testnet (chain 2368)? If not, we deploy our own.

2. **Agent-card.json schema**: The EIP doesn't formalize the `x402Support` field — we'd be extending it. Is there a community convention forming?

3. **Discovery at scale**: Scanning all `Registered` events on-chain is O(n). For a hackathon demo this is fine, but production needs an indexer (The Graph / QuickNode Streams).

4. **Facilitator on Kite**: The Kite facilitator is at `0x12343e649e6b2b2b77649DFAb88f103c02F3C78b`. Does it support the same x402 payment verification as Coinbase's facilitator?

5. **MCP Python SDK x402 integration**: [mcp-go-x402](https://github.com/mark3labs/mcp-go-x402) exists for Go but there's no Python equivalent. We need to build x402 handling into the `streamablehttp_client` transport layer.

6. **Dynamic tool injection**: When `negotiate-add` connects to a new remote server, how do we inject its tools into the calling agent's tool list? We need to fire `notifications/tools/list_changed` and proxy the remote tools.
