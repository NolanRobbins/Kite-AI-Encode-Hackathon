## 1. AbstractOpponentModel — Interface

**Source**: `nenv/OpponentModel/AbstractOpponentModel.py` [Source 1]

```python
class AbstractOpponentModel(ABC):
    _pref: EstimatedPreference  # The mutable predicted preference object

    def __init__(self, reference: Preference):
        """
        Constructor. Takes the agent's OWN preference as a reference 
        (to get domain info — issues, values). Initializes EstimatedPreference 
        with inverted weights (1 - agent_weight) as a starting heuristic.
        """
        self._pref = EstimatedPreference(reference)

    @property
    @abstractmethod
    def name(self) -> str:
        """Unique name for logging."""

    @abstractmethod
    def update(self, bid: Bid, t: float):
        """Called when a bid is received from the opponent.
        
        Args:
            bid: The received bid (with utility calculated from OUR perspective)
            t: Normalized negotiation time [0.0, 1.0]
        """

    @property
    def preference(self) -> EstimatedPreference:
        """Returns the current estimated opponent preference profile."""
        return self._pref

    def calculate_error(self, org_pref: Preference, 
                        return_rmse=True, return_spearman=True, 
                        return_kendall_tau=True) -> (float, float, float):
        """Evaluates estimation accuracy against the real opponent preference.
        
        Returns: (RMSE, Spearman correlation, Kendall-Tau correlation)
        
        - RMSE: sqrt(mean((real_utility - estimated_utility)^2)) over all bids
        - Spearman: Rank correlation between real and estimated bid orderings
        - Kendall-Tau: Rank correlation (different formula) between orderings
        """
```

### Key Design Insight for NegotiatorGrid

The opponent model is **completely decoupled from the agent**. The `Session` class calls `estimator.update(bid, t)` for ALL registered estimators on every received bid — even estimators not used by the agent's strategy. This allows **independent benchmarking** of opponent models.

### Built-in Opponent Models

| Model | File | Algorithm |
|-------|------|-----------|
| `ClassicFrequencyOpponentModel` | `ClassicFrequencyOpponentModel.py` | Frequency analysis: tracks how often each value appears in opponent offers. If opponent doesn't change a value between consecutive offers, that issue's weight increases (scaled by `α × (1-t)`). |
| `BayesianOpponentModel` | `BayesianOpponentModel.py` | Bayesian belief updating over possible preference profiles. |
| `ConflictBasedOpponentModel` | `ConflictBasedOpponentModel.py` | Models opponent based on conflict patterns (from Keskin et al. 2023). |
| `WindowedFrequencyOpponentModel` | `WindowedFrequencyOpponentModel.py` | Frequency analysis with a sliding window (only recent N offers). |

## 2. EstimatedPreference — Mutable Opponent Preference Representation

**Source**: `nenv/OpponentModel/EstimatedPreference.py` [Source 1]

`EstimatedPreference` extends `Preference` and makes it **mutable** — opponent models can update issue weights and value weights during negotiation.

### Structure

```python
class EstimatedPreference(Preference):
    """A mutable Preference where issue and value weights can be changed."""

    # Inherited from Preference:
    _issue_weights: Dict[Issue, float]              # issue → weight (sum to 1.0)
    _value_weights: Dict[Issue, Dict[str, float]]   # issue → {value → weight [0,1]}
    
    # LinearAdditive utility model:
    # U(bid) = Σ_issue (issue_weight × value_weight[issue][bid[issue]])
```

### Initialization Heuristic

When created from the agent's own preference as `reference`, the initial estimate inverts weights:

```python
for issue in self._issue_weights:
    self._issue_weights[issue] = 1.0 - reference.issue_weights[issue]
    for value in issue.values:
        self._value_weights[issue][value] = 1.0 - reference.value_weights[issue][value]
self.normalize()
```

This "assume the opponent is our inverse" is a reasonable zero-information starting point.

### Getters/Setters

```python
# Read weights
weight = estimated_pref["price"]                    # Issue weight
weight = estimated_pref["price", "valueA"]          # Value weight

# Write weights (mutable!)
estimated_pref["price"] = 0.4                       # Set issue weight
estimated_pref["price", "valueA"] = 0.8             # Set value weight

# Normalize after changes
estimated_pref.normalize()

# Calculate utility of any bid
utility = estimated_pref.get_utility(bid)
```

### NegotiatorGrid Mapping

`EstimatedPreference` represents what we think the counterparty values. In NegotiatorGrid:
- After each negotiation round, update the opponent model from their latest offer
- Use `estimated_pref.get_utility(our_offer)` to predict how much the counterparty likes our proposal
- Target offers that are high-utility for us AND acceptable-utility for the estimated opponent

## 3. The `receive_offer` → `act` Loop

**Source**: `nenv/Agent.py` and `nenv/Session.py` [Source 1]

### Session Main Loop (`Session.start()`)

```python
def start(self) -> LogRow:
    # Initialize both agents
    agentA.initiate(opponent_name=agentB.name)
    agentB.initiate(opponent_name=agentA.name)
    
    t = 0.0
    round = 0
    
    while t < 1.0:
        # ── AgentA's turn ──
        if round > 0:
            agentA.receive_bid(last_action.bid, t)  # Internal: updates estimators + calls receive_offer
        action = agentA.act(t)                       # Returns Offer(bid) or Accept(bid)
        
        if isinstance(action, Accept):
            return on_acceptance("A", action, t)
        else:
            on_offer(action, "A", t)                 # Fires logger callbacks
        
        t = get_time()
        if t >= 1.0:
            return on_fail(t)                        # Deadline reached
        
        # ── AgentB's turn ──
        agentB.receive_bid(action.bid, t)
        action = agentB.act(t)
        
        if isinstance(action, Accept):
            return on_acceptance("B", action, t)
        else:
            on_offer(action, "B", t)
        
        round += 1
        t = get_time()
    
    return on_fail(t)
```

### Agent Method Signatures

```python
class AbstractAgent(ABC):
    preference: Preference              # Agent's own preference
    last_received_bids: List[Bid]       # History of all opponent bids
    estimators: List[AbstractOpponentModel]  # All registered opponent models
    session_time: int                   # Max negotiation time (seconds)

    def initiate(self, opponent_name: Optional[str]):
        """Called before negotiation starts. Initialize your state here."""

    def receive_bid(self, bid: Bid, t: float):
        """INTERNAL — called by Session. You implement receive_offer instead.
        This method:
        1. Copies bid, recalculates utility from agent's own preference
        2. Appends to last_received_bids history
        3. Calls estimator.update(bid, t) for ALL registered estimators
        4. Calls self.receive_offer(bid, t)
        """

    @abstractmethod
    def receive_offer(self, bid: Bid, t: float):
        """YOUR CODE: Called when opponent makes an offer. Update your state."""

    @abstractmethod
    def act(self, t: float) -> Action:
        """YOUR CODE: Return Offer(bid) or Accept(bid).
        
        Example (linear bidding + AC_Next):
            target = max(reservation_value, t)
            bid = preference.get_bid_at(target)
            if can_accept() and bid <= last_received_bids[-1]:
                return Accept(last_received_bids[-1])
            return Offer(bid)
        """

    def terminate(self, is_accept: bool, opponent_name: str, t: float):
        """Called when negotiation ends. Clean up, learn from session."""

    def can_accept(self) -> bool:
        """Returns True if we've received at least one bid (can't accept in round 0)."""
        return len(self.last_received_bids) > 0

    @property
    def accept_action(self) -> Accept:
        """Convenience: Accept(last_received_bids[-1])"""
```

### Action Types

```python
class Action(ABC):
    bid: Bid

class Offer(Action):
    """Make a counter-offer."""

class Accept(Offer):
    """Accept the opponent's last bid."""
```

### Time Model

```python
t = get_time()  # Returns normalized time in [0.0, 1.0]

# If time-based deadline:  t = elapsed_seconds / deadline_seconds
# If round-based deadline: t = current_round / max_rounds
# If both (mixed):         t = max(time_based, round_based)
```

## 4. Domain Generator

**Source**: `domain_generator/domain_generator.py` [Source 1]; IJCAI paper §2.1 [Source 2]

### Parameters

| Parameter | Range | Description |
|-----------|-------|-------------|
| Number of issues | user-defined | How many issues in the negotiation (e.g., price, quality, delivery) |
| Values per issue | user-defined | Discrete values per issue |
| Opposition | 0.0 – 1.0 | How much the agents disagree (0 = same preferences, 1 = total opposition) |
| Balance score | 0.0 – 0.05+ | Whether utility distribution favors one agent (0 = balanced) |
| Utility range | [min, max] | Scale value weights to this range |
| Value boost | float | Asymmetric boost to one profile's values |
| Reservation value | float | BATNA utility if no agreement |

### How Domains Are Generated

```python
class Preference:
    def __init__(self, issues_values, inverse, reservation_value, value_boost, ...):
        # For each issue:
        #   - Issue weight = position-based + Gaussian noise
        #   - Value weight = position-based + Gaussian noise
        #   - If `inverse=True`: reverse the ordering (creates opposition)
        
        # Two profiles are generated:
        #   Profile A: inverse=False (values issue weights ascending)
        #   Profile B: inverse=True  (values issue weights descending)
        # This creates natural opposition — what A values most, B values least
```

### Balance Score Formula (from paper [Source 2])

```
balance = (1/n) × Σ(U_A(outcome_i) - U_B(outcome_i))
```

Zero means perfectly balanced. Positive means Profile A has systematically higher utilities.

### Usage

```python
# From domain_generator.py — creates JSON domain files
# Configurable via domain_generator.json or Web UI

# Example domain_generator.json:
{
    "domain_size_range": [0, 100000],
    "opposition_range": [0.0, 1.0],
    "balance_score_range": [0.0, 0.05],
    "num_issues": [3, 5],
    "num_values": [3, 10]
}
```

Domains are saved as JSON files in the `domains/` directory and can be loaded by the tournament system.

### NegotiatorGrid Application

Generate domains that model NegotiatorGrid scenarios:
- Issues: `price` (0-100 USDT), `latency` (10-500ms), `uptime` (95-99.9%), `throughput` (100-10000 req/s)
- Opposition: High (buyer wants low price, seller wants high price)
- Balance: Adjustable per test scenario

## 5. Logger Callbacks — When Do They Fire?

**Source**: `nenv/logger/AbstractLogger.py` and `nenv/Session.py` [Source 1]

### Callback Timeline

```
Tournament starts
├── For each session:
│   ├── logger.before_session_start(session)     ← BEFORE agents are initiated
│   │      Returns: list of extra sheet names for logging
│   │
│   ├── Session.start()
│   │   ├── agentA.initiate()
│   │   ├── agentB.initiate()
│   │   │
│   │   ├── Round 0:
│   │   │   ├── agentA.act(t) → Offer
│   │   │   ├── logger.on_offer("A", bid, t, session)     ← EVERY offer
│   │   │   │      Returns: dict for session log
│   │   │   ├── agentB.receive_bid(bid, t)
│   │   │   ├── agentB.act(t) → Offer or Accept
│   │   │   ├── logger.on_offer("B", bid, t, session)     ← EVERY offer
│   │   │   └── ...
│   │   │
│   │   ├── Round 1..N:
│   │   │   └── Same pattern...
│   │   │
│   │   └── Termination:
│   │       ├── If Accept:  logger.on_accept(agent, bid, t, session)
│   │       ├── If Timeout: logger.on_fail(t, session)
│   │       └── If Error:   logger.on_fail(t, session)
│   │
│   └── logger.on_session_end(final_row, session)    ← AFTER session ends
│          Returns: dict for tournament log
│
└── logger.on_tournament_end(logs, agents, domains, estimators)  ← AFTER all sessions
       Generate graphs, aggregate statistics
```

### Logger Method Signatures

```python
class AbstractLogger(ABC):
    def before_session_start(self, session: Session) -> List[str]:
        """Before session. Return extra sheet names for Excel log."""

    def on_offer(self, agent: str, offer: Bid, time: float, session: Session) -> dict:
        """Fired on every offer. 'agent' is 'A' or 'B'. Return round-level log data."""

    def on_accept(self, agent: str, offer: Bid, time: float, session: Session) -> dict:
        """Fired when negotiation ends WITH agreement. Return session log data."""

    def on_fail(self, time: float, session: Session) -> dict:
        """Fired when negotiation ends WITHOUT agreement (timeout/error)."""

    def on_session_end(self, final_row: dict, session: Session) -> dict:
        """Fired after session terminates. Return tournament-level log data."""

    def on_tournament_end(self, tournament_logs, agent_names, domain_names, estimator_names):
        """Fired after all sessions. Generate graphs, summary statistics."""
```

## 6. Benchmarking Opponent Models Independently

**Source**: IJCAI paper §2.1 [Sources 2, 3]; `AbstractOpponentModel.py`, `Session.py` [Source 1]

### How It Works

This is NegoLog's key innovation. The architecture separates opponent model evaluation from agent strategy:

```
Session receives opponent bid
    │
    ├── agentA.receive_bid(bid, t)
    │       ├── estimator1.update(bid, t)   ← ALL estimators get the bid
    │       ├── estimator2.update(bid, t)
    │       ├── estimator3.update(bid, t)
    │       └── agent.receive_offer(bid, t)  ← Agent may or may not use estimators
    │
    └── For each estimator:
            logger tracks: estimator.calculate_error(real_opponent_pref)
            → RMSE, Spearman, Kendall-Tau at every round
```

### The Key: Estimators Are Registered at the Tournament Level

From the tournament YAML config, you specify which estimators to evaluate. They're injected into agents but **the agent doesn't have to use them**. The loggers evaluate them independently:

```yaml
# tournament_example.yaml (conceptual)
agents:
  - BoulwareAgent
  - ConcederAgent
estimators:
  - ClassicFrequencyOpponentModel
  - BayesianOpponentModel
  - ConflictBasedOpponentModel
loggers:
  - EstimatorMetricLogger
  - EstimatorOnlyFinalMetricLogger
domains:
  - domain1
  - domain2
```

### Metrics Computed per Estimator per Round

From `calculate_error()`:

```python
# For each bid in the domain:
#   real_utility = org_pref.get_utility(bid)
#   estimated_utility = estimated_pref.get_utility(bid)

RMSE = sqrt(mean((real - estimated)^2))  # Lower is better
Spearman = rank_correlation(real_order, estimated_order)  # Higher is better  
Kendall_Tau = kendall_tau(real_order, estimated_order)  # Higher is better
```

For NegotiatorGrid, you can:
1. Create a custom `OnChainReputationOpponentModel` that uses counterparty transaction history
2. Register it alongside classic frequency models in a tournament
3. NegoLog will benchmark all models head-to-head on the same negotiation data
4. Compare RMSE/Spearman to prove your on-chain model outperforms naive frequency analysis

## NegotiatorGrid Architecture Mapping

```
NegoLog Component           →  NegotiatorGrid Component
──────────────────────────────────────────────────────────
AbstractAgent               →  NegotiatorGrid agent base class
  .receive_offer(bid, t)    →  Process incoming A2A negotiation message
  .act(t) → Action          →  Generate next offer or accept, send via A2A
  .initiate(opponent)       →  Load counterparty reputation from Kite chain
  .terminate(...)           →  Trigger Kite approve_payment() on agreement

AbstractOpponentModel       →  NegotiatorGrid opponent modeler
  .update(bid, t)           →  Feed each received offer into the model
  .preference               →  Predicted counterparty utility function
  .calculate_error()        →  Benchmark model accuracy (for dev/demo)

EstimatedPreference         →  Mutable counterparty preference estimate
  ["price"] = 0.4           →  Update issue weight from observed behavior
  .get_utility(bid)         →  Predict counterparty satisfaction with our offer
  .normalize()              →  Re-normalize after weight updates

Session                     →  NegotiatorGrid negotiation engine
  .start()                  →  Run SAOP between two agents
  .get_time()               →  Normalized deadline tracking

AbstractLogger              →  NegotiatorGrid analytics/observability
  .on_offer(...)            →  Log each offer to chain / dashboard
  .on_accept(...)           →  Trigger x402 settlement
  .on_fail(...)             →  Record failed negotiation for reputation
```

### Why NegoLog's Architecture Maps Perfectly to NegotiatorGrid

1. **Decoupled opponent model**: NegoLog evaluates opponent models independently of bidding strategies. NegotiatorGrid needs the same separation — the opponent model runs server-side, the bidding strategy runs in the agent.

2. **`EstimatedPreference` is mutable**: As offers arrive over the network (via A2A), NegotiatorGrid updates the preference estimate in real-time. The `normalize()` after each update keeps weights valid.

3. **The `receive_offer` → `act` loop maps directly to A2A message exchange**: `receive_offer` = process incoming JSON-RPC message; `act` = generate outgoing JSON-RPC message.

4. **Logger callbacks = on-chain attestation hooks**: `on_offer` → log to Kite chain; `on_accept` → trigger `approve_payment`; `on_fail` → record disagreement for reputation.

5. **25 ANAC agents = instant benchmarking**: Run NegotiatorGrid's custom agent against 25 proven competition agents to validate strategy quality.
