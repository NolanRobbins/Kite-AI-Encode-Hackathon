## 1. Three-Layer Architecture → Where Negotiation Lives

**Doc Section**: Whitepaper §2 "Architecture Overview"; Architecture & Design Pillars "Four-Layer Architecture" [Sources 1, 3]

Kite actually defines a **four-layer** architecture (the whitepaper says "three-layer identity" but four layers of infrastructure):

| Layer | Purpose | Negotiation Relevance |
|-------|---------|----------------------|
| **Base Layer** | EVM-compatible L1 (Avalanche subnet), stablecoin-native fees, state channels, dedicated payment lanes | Settlement substrate — where escrow locks and payment finality happen. NegotiatorGrid's on-chain settlement anchors here. |
| **Platform Layer** | Agent-ready APIs for identity management, authorization APIs, session key generation, payment processing, SLA enforcement | **NegotiatorGrid's primary integration point.** Session key APIs create negotiation-scoped spending authority. SLA enforcement APIs encode deal terms. |
| **Programmable Trust Layer** | Kite Passport, x402 protocol, Agent SLAs (smart contract templates), protocol bridges (A2A, MCP, OAuth 2.1, AP2), reputation system | **NegotiatorGrid lives here.** Negotiation is a trust-layer concern: two agents establishing mutual commitments before payment. Agent SLAs are the output artifact of negotiation. Reputation feeds into opponent modeling. |
| **Ecosystem Layer** | Application Marketplace + Agent Ecosystem, service discovery, reputation networks | Discovery layer — where agents find counterparties to negotiate with. |

### Verdict
NegotiatorGrid straddles the **Programmable Trust Layer** (negotiation logic, SLA creation, reputation queries) and the **Platform Layer** (session key management, spending rule enforcement). The negotiation protocol itself is a Trust Layer primitive; the enforcement of negotiated outcomes drops down to Platform Layer APIs.

### Key Quote
> "Programmable Trust Layer: Introduces novel primitives including Kite Passport (cryptographic agent IDs), Agent SLAs (smart contract interaction templates), and compatibility bridges to A2A, MCP, and OAuth 2.1." — Architecture & Design Pillars [Source 3]

## 2. Identity Model: How a Negotiating Agent Proves Identity

**Doc Section**: Core Concepts "Identity & Trust Infrastructure" + "Three-Layer Identity Architecture"; Whitepaper §3.3.1 "The Three Layer Identity Imperative" [Sources 1, 2]

### Identity Chain for Negotiation

```
User (EOA in secure enclave)
  └─ KitePass (cryptographic identity card)
       ├─ DID:  did:kite:alice.eth
       ├─ Binds to Gmail, Twitter via cryptographic proofs
       └─ Contains capabilities: spending limits, service access
            └─ Agent (BIP-32 derived address)
                 ├─ DID:  did:kite:alice.eth/chatgpt/portfolio-manager-v1
                 ├─ Own wallet + own reputation score
                 └─ Session (ephemeral random key)
                      ├─ Single-use authorization token
                      ├─ Self-contained proof of authority + chain of trust + validity period
                      └─ Becomes cryptographically void after use
```

### How Agent A Proves Identity to Counterparty Agent B

1. **Agent A presents its DID**: `did:kite:alice.eth/negotiator-agent-v1` — structured identifier encoding the user→agent hierarchy [Source 2, "Decentralized Identifier (DID)"]
2. **Counterparty resolves via on-chain resolver**: `GetAgent(AgentID)` → returns AgentDomain, AgentAddress. No central authority needed. [Source 2, "Protocol Compatibility" / "Identity Resolution"]
3. **Verifiable Credentials (VCs)**: Agent can present signed attestations proving compliance training, trading licenses, reputation thresholds. Enables fine-grained access control. [Source 2, "Verifiable Credentials"]
4. **Proof of AI**: Immutable blockchain-anchored logs proving complete lineage from user authorization to current action. Indisputable evidence for disputes. [Source 2, "Proof of AI"]
5. **Selective disclosure**: KitePass enables proving ownership without revealing full identity. [Source 2, "Kite Passport"]

### NegotiatorGrid Application
- Before negotiation starts, both agents exchange DIDs and resolve each other's identity on-chain
- VCs can encode negotiation prerequisites ("this agent has >95% SLA compliance score")
- Reputation score (accumulated from verifiable behavior, not self-reported) feeds directly into opponent modeling and trust calibration
- The triple-verification chain (Standing Intent → Delegation Token → Session Signature) proves every negotiation action traces to an authorized user [Source 1, §3.3.3 "Cryptographic Primitives"]

### Cryptographic Primitives for Identity Proof

```protobuf
// From Whitepaper §3.3.3 [Source 1]
message AgentDID {
  string did = 1;

  repeated VerificationMethod verification_methods = 3;
```

## 3. Wallet Architecture: Which Wallet for NegotiatorGrid Agents?

**Doc Section**: Core Concepts "Wallet Architecture"; Whitepaper §3.2.3 "Wallets Structure"; Account Abstraction SDK [Sources 1, 2, 6]

### Comparison for Negotiation Use Case

| Wallet Type | How It Works | Spending Limits? | Negotiation Fit |
|-------------|-------------|-----------------|-----------------|
| **EOA** | Private key in secure enclave. Root of authority. Signs initial authorizations. | No on-chain enforcement — binary control. | ❌ Too rigid. No programmable constraints. Use only as root authority for the user. |
| **AA Wallet (ERC-4337)** | Smart contract account with programmable logic. Single on-chain account, multiple agents operate via session keys. | ✅ On-chain spending rules: caps, rolling windows, whitelisted merchants, conditional logic. | ✅✅ **Best fit.** Spending rules can encode negotiated price as a hard cap. Session keys scope authority per negotiation. |
| **Embedded Wallet** | Self-custodial, integrated into apps. No seed phrase management. One-click agent authorization. | Inherits from AA wallet underneath. | ✅ Good UX layer on top of AA wallet for end-user-facing products. |

### Why AA Wallet Wins for NegotiatorGrid

The AA wallet implements a **unified account model** where:
- User owns a **single on-chain account** holding shared funds in stablecoins [Source 2, "AA Wallet"]
- Multiple agents operate via their own session keys
- Each agent is constrained by smart contract rules: `"ChatGPT limit $10,000/month, Cursor limit $2,000/month"` [Source 1, §3.2]
- Rules are **temporal** (increase limits over time), **conditional** (reduce if volatility spikes), and **hierarchical** (cascade through delegation levels)

2. This makes the negotiated price a **cryptographically enforced ceiling** — the agent literally cannot spend more than P, even if compromised

## 4. SPACE Framework → Which Components Enforce Negotiation Outcomes?

**Doc Section**: Whitepaper TL;DR + §2; Introduction & Mission "SPACE framework" [Sources 1, 7]

### SPACE Breakdown

| Letter | Component | Enforces Negotiation? | How |
|--------|-----------|----------------------|-----|
| **S** | **Stablecoin-native** payments — sub-cent fees, instant settlement | ✅ Settlement medium | Negotiated price settles in stablecoins. Predictable costs enable precise pricing. Micropayments down to $0.000001 via state channels. |
| **P** | **Programmable constraints** — spending rules enforced cryptographically | ✅✅ **Primary enforcement** | Negotiated price becomes an on-chain spending cap. Rolling windows enforce rate limits. Whitelisted merchants enforce counterparty binding. Conditional logic ("if quality drops, reduce payment") maps directly to deal terms. |
| **A** | **Agent-first authentication** — hierarchical identity + BIP-32 delegation | ✅ Identity binding | Ensures negotiation parties are who they claim. DID resolution proves authority chain. VCs establish negotiation prerequisites. |
| **C** | **Compliance-ready** — immutable audit trails with selective disclosure | ⚠️ Indirect | Proof of AI creates auditable negotiation history. Useful for dispute resolution but not enforcement per se. |
| **E** | **Economically viable micropayments** — state channels, $1/million requests | ✅ Execution mechanism | Pay-per-request pricing at negotiated rates. State channels enable streaming payments locked to negotiated terms. Bidirectional channels support refunds for SLA violations. |

### Summary
**P** (Programmable constraints) and **S** (Stablecoin-native) are the direct enforcement mechanisms. **A** (Agent-first auth) provides the trust foundation. **E** (Economically viable micropayments) provides the execution rails. **C** (Compliance) provides the audit trail for disputes.

### Key Enforcement Primitives

From the whitepaper [Source 1, §3.2.5]:

**Spending Rules (On-Chain)**:
- Spending caps that cannot be exceeded even if agent tries
- Rolling windows ("$1,000 per day") enforced at protocol level
- Whitelisted merchants — only authorized recipients can receive funds
- Conditional logic: "If volatility >20%, reduce limits by half"

**Policies (Off-Chain)**:
- Evaluated in user's local environment or Kite's TEE
- Session TTL, operation categories, recipient allowlists

| Dimension | Spending Rules | Policy |
|-----------|---------------|--------|
| **Scope** | Asset/stablecoin-related (programmable money) | Full control for complex logic |
| **Evaluation** | Entirely on-chain via smart contracts | Off-chain in user's TEE or local env |
| **Interoperability** | Any on-chain account, fully decentralized | Platform-specific |
| **Use Cases** | Spending limits, rolling windows | Session TTL, categories, recipient lists |

## 5. Session Keys / Ephemeral Keys → Can a Session Key Have spending cap = negotiated price?

**Doc Section**: Core Concepts "Session Keys / Ephemeral Keys"; Whitepaper §3.3.2 + §3.3.3 [Sources 1, 2]

### Answer: YES — explicitly supported

Session keys are designed exactly for this pattern. From the whitepaper [Source 1]:

> "A session key might authorize 'transfer maximum $10 to providers A, B, or C for data feeds between 2:00 PM and 2:05 PM today.' The key executes its authorized operation then becomes cryptographically void forever."

### Session Key Properties

| Property | Value | Negotiation Mapping |
|----------|-------|-------------------|
| **Generation** | Completely random, never derived from permanent keys | Each negotiation round gets fresh session key |
| **Amount limit** | Specific `valueLimit` per session | Set to negotiated price |
| **Recipient set** | Defined `targetProviders` | Lock to counterparty's address |
| **Time window** | `validUntil` timestamp | Deal expiration window |
| **Scope** | Single `functionSelector` | Lock to `pay()` or escrow function |
| **Forward secrecy** | Compromising one session ≠ compromise of others | Negotiation sessions are isolated |
| **Revocation** | `removeSessionKeyPermission()` or auto-expire | Walk away from negotiation = revoke session |

### On-Chain Implementation

```solidity
// From Whitepaper §3.3.2 [Source 1]
addSessionKeyRule(
  address sessionKeyAddress,    // The newly generated session key
  bytes32 agentId,              // Negotiator agent performing the actions
  bytes4 functionSelector,      // Allowed function (e.g., pay())
  uint256 valueLimit            // ← SET THIS TO NEGOTIATED PRICE
)
```

The user signs this as a `UserOperation` packaged for the ERC-4337 bundler. Sessions expire automatically when `validUntil` timestamps pass.

### Cryptographic Chain for a Negotiated Payment

```
Standing Intent (SI) — User's root authorization
  ├─ agentId: "negotiator-agent-v1"
  ├─ capabilities: ["max $500/day", "providers: [0x...]"]
  ├─ validUntil: timestamp
  └─ signature: user's EOA signature (ECDSA/EdDSA)

    └─ Delegation Token (DT) — Agent's session authorization
         ├─ sessionKeyAddress: 0x333n88...
         ├─ operationScope: "pay()"
         ├─ standingIntentHash: hash(SI)  ← proves bounded by SI
         ├─ validUntil: short window
         └─ signature: agent's key

              └─ Session Signature (SS) — Transaction execution proof
                   ├─ transactionHash: the actual payment
                   ├─ delegationTokenHash: hash(DT)
                   ├─ timestamp: execution time
                   └─ signature: session key

Services verify ALL THREE before accepting payment.
```

### NegotiatorGrid Design Pattern
1. Agents negotiate off-chain (via A2A/MCP messaging)
2. When deal is reached at price P:
   - Buyer agent creates session key with `valueLimit = P` and `targetProviders = [seller]`
   - Session key is scoped to `pay()` function only
   - Time window = deal validity period
3. Session key becomes the cryptographic commitment to the negotiated deal
4. If deal falls through, session expires harmlessly

## 6. SLA Contracts → Can NegotiatorGrid Deal Terms Be Encoded as SLA?

**Doc Section**: Core Concepts "SLA (Service-Level Agreement) Contracts"; Whitepaper §3.2.5 "Governance and Safety Mechanisms" [Sources 1, 2]

### Answer: YES — SLAs are the natural output artifact of NegotiatorGrid

### SLA Contract Architecture

From Core Concepts [Source 2]:

> "Smart contracts that transform vague service promises into mathematically enforced guarantees. Unlike Traditional SLAs (legal enforcement, manual claims): Kite SLAs automatically execute penalties and rewards through smart contract code."

### Supported Guarantee Types (directly map to negotiation terms)

| SLA Metric | Example | NegotiatorGrid Mapping |
|-----------|---------|----------------------|
| **Response time** | <100ms with automatic penalties | Negotiated latency SLA |
| **Availability** | 99.9% uptime with pro-rata refunds | Negotiated uptime commitment |
| **Accuracy** | <0.1% error rate, reputation slashing | Negotiated quality threshold |
| **Throughput** | 1,000+ req/sec minimum | Negotiated capacity guarantee |
| **Price** | Fixed or tiered pricing | **The negotiated price itself** |

### Enforcement Pipeline

```
Off-chain telemetry measures SLA metrics (latency, uptime, accuracy, throughput)
        ↓
Oracle submits signed attestations or zk/TEE proofs
        ↓
On-chain SLA contract evaluates oracle reports
        ↓
Automatic triggers: refunds, penalties, reputation slashing
```

[Source 2, "SLA Implementation Details"]

### ServiceRegistry Contract

Deployed at `0xc67a4AbcD8853221F241a041ACb1117b38DA587F` (testnet) [Source 5]:
- Stores service types, pricing models, unit prices
- Service discovery for agents
- **NegotiatorGrid can register negotiated service terms here** — making the deal discoverable and verifiable

### Programmable Escrow as Deal Enforcement

From Whitepaper [Source 1, §3.3.2] + Example Contracts [Source 8]:

Kite provides programmable escrow with full lifecycle:
- **Authorization** → Buyer locks negotiated amount
- **Capture** → Partial or full release based on verified outcomes
- **Charge** → Final settlement
- **Void** → Cancel if deal terms not met
- **Reclaim** → Buyer reclaims on SLA violation
- **Refund** → Automatic on quality failure

The `EscrowService.sol` example contract [Source 8] implements:
```solidity
createSession(bytes32 sessionId)    // Lock funds in escrow
confirmService(bytes32 sessionId)   // Release to seller on satisfaction
disputeService(bytes32 sessionId, string reason)  // Raise dispute
acceptDispute(bytes32 sessionId)    // Full refund to buyer
challengeDispute(bytes32 sessionId) // Split 50/50 on challenged dispute
```

### NegotiatorGrid → SLA Mapping

After negotiation concludes:
1. **Price** → Encoded as `valueLimit` in session key + `budget` in spending rule + escrow amount
2. **Latency** → SLA contract metric with oracle attestation, auto-penalty on violation
3. **Quality** → SLA accuracy threshold with reputation slashing on failure
4. **Availability** → SLA uptime guarantee with pro-rata refund logic
5. **Deal expiry** → `validUntil` on session key + escrow expiry condition
6. **Dispute resolution** → Escrow dispute flow (accept/challenge) + Proof of AI audit trail

## Action Items for NegotiatorGrid

1. **Use AA Wallet + ClientAgentVault** as the wallet pattern. The `gokite-aa-sdk` npm package is your entry point. Deploy vaults with spending rules that encode negotiated prices.

2. **Session keys are your commitment mechanism.** After negotiation, create a session key with `valueLimit = negotiatedPrice` and `targetProviders = [counterparty]`. This is the cryptographic binding between negotiation and settlement.

3. **Fork/extend `EscrowService.sol`** from example-contracts to add NegotiatorGrid-specific deal terms (latency thresholds, quality metrics, multi-round negotiation state).

4. **SLA enforcement requires you to build the oracle.** Kite describes the pattern (off-chain measurement → oracle attestation → on-chain evaluation) but hasn't shipped oracle contracts. NegotiatorGrid will need to implement or integrate an oracle for quality/latency verification.

5. **DID resolution is a gap you'll need to work around.** For the hackathon, consider using direct address-based identity (AA wallet addresses are deterministic) rather than depending on the unshipped DID resolver APIs.

6. **Reputation system is not queryable yet.** For opponent modeling, you'll need to build your own reputation tracking from on-chain transaction history (payment success/failure rates, SLA violation events) rather than querying a Kite reputation API.

7. **State channels are whitepaper-only.** For the hackathon, use direct on-chain escrow + x402 facilitator settlement rather than state channels. State channels would be the production scaling path but there's no SDK to build on today.

8. **Register negotiated services in ServiceRegistry** (`0xc67a4AbcD8853221F241a041ACb1117b38DA587F`) to make deals discoverable. The contract supports service types, pricing models, and unit prices.

9. **Apply for Kite Agent Passport testnet access** if not already invited — the Session/Delegation model maps perfectly to negotiation commitment/execution phases.

10. **The AP2-kite repo** (fork of Google's Agent Payment Protocol) defines how payment intents should be expressed. NegotiatorGrid's negotiation output should produce AP2-compliant payment mandates that Kite settles on-chain.
