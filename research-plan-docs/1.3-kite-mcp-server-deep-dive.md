## Critical Discovery: There Are TWO Different MCP Servers

Kite operates two separate MCP server endpoints with **different tool sets** for different purposes:

| Server | URL | Auth | Tools | Purpose |
|--------|-----|------|-------|---------|
| **Kite AIR MCP** (App Store) | `https://mcp.prod.gokite.ai/{api_key}/mcp` | API key in URL path | `get_service_details`, `call_service` | Service discovery + paid service calling via KitePass |
| **Kite Passport MCP** (Payments) | `https://neo.dev.gokite.ai/v1/mcp` | OAuth 2.1 bearer token | `get_payer_addr`, `approve_payment` (+ more in Agent Builder Guide) | x402 payment authorization + wallet ops |

Both identify as **"Kite Passport MCP" v1.12.3** in their server info (confirmed live), but they expose different tool sets depending on authentication context.

## 1. Exact MCP Server URLs and Transport Type

### Confirmed by Live Probing [Source 6]

**Transport**: **Streamable HTTP** (SSE-backed JSON-RPC over HTTP POST)

When I sent a POST without the correct Accept header, the server returned:
```
{"code":-32600,"message":"Not Acceptable: Client must accept both application/json and text/event-stream"}
```

This confirms the server requires `Accept: application/json, text/event-stream` — the hallmark of MCP's Streamable HTTP transport (not pure SSE, not stdio).

### Server A: Kite AIR MCP (App Store)

```
URL:    https://mcp.prod.gokite.ai/{api_key_value}/mcp
Auth:   API key embedded in URL path (prefix: api_key_)
Trans:  Streamable HTTP (POST with SSE responses)
```

**Live initialization response:**
```json
{
  "protocolVersion": "2024-11-05",
  "capabilities": {
    "experimental": {},
    "prompts": {"listChanged": true},
    "resources": {"subscribe": false, "listChanged": true},
    "tools": {"listChanged": true}
  },
  "serverInfo": {
    "name": "Kite Passport MCP",
    "version": "1.12.3"
  }
}
```

### Server B: Kite Passport MCP (Payments)

```
URL:    https://neo.dev.gokite.ai/v1/mcp
Auth:   OAuth 2.1 bearer token (requires user authentication flow)
Trans:  Streamable HTTP
```

This server rejects unauthenticated requests with:
```json
{"error":"invalid_token","error_description":"Missing or invalid authorization header"}
```

### Alternate URL from Getting Started docs [Source 3]

The Getting Started page also mentions:
```
https://mcp.prod.gokite.ai/{api_key_value}/mcp
```
With the note that `api_key_value` has the prefix `api_key_`. This is Server A.

## 4. Custom Python MCP Client — Yes, Fully Supported

**You are NOT limited to Claude Desktop.** The MCP server uses standard Streamable HTTP transport (JSON-RPC 2.0 over HTTP POST with SSE responses). Any MCP client can connect.

### Minimal Python MCP Client Example

```python
import asyncio
from mcp import ClientSession
from mcp.client.streamable_http import streamablehttp_client

async def connect_to_kite():
    api_key = "api_key_YOUR_KEY_HERE"
    url = f"https://mcp.prod.gokite.ai/{api_key}/mcp"
    
    async with streamablehttp_client(url) as (read, write, _):
        async with ClientSession(read, write) as session:
            await session.initialize()
            
            # List available tools
            tools = await session.list_tools()
            for tool in tools.tools:
                print(f"Tool: {tool.name}")
                print(f"  Description: {tool.description}")
                print(f"  Input schema: {tool.inputSchema}")
            
            # Call a tool
            result = await session.call_tool(
                "get_service_details",
                arguments={"service_id": "agent_LpzYVzWGzjGiZBI3HTm4ZCKj"}
            )
            print(result)

asyncio.run(connect_to_kite())
```

**Requirements**: `pip install mcp` (the official MCP Python SDK)

### Raw HTTP Approach (no SDK needed)

Since the transport is just HTTP POST:

```python
import requests
import json

API_KEY = "api_key_YOUR_KEY_HERE"
BASE = f"https://mcp.prod.gokite.ai/{API_KEY}/mcp"
HEADERS = {
    "Content-Type": "application/json",
    "Accept": "application/json, text/event-stream"
}

def mcp_call(method, params=None, id=1):
    payload = {
        "jsonrpc": "2.0",
        "id": id,
        "method": method,
        "params": params or {}
    }
    resp = requests.post(BASE, json=payload, headers=HEADERS)
    # Parse SSE response
    for line in resp.text.strip().split('\n'):
        if line.startswith('data: '):
            return json.loads(line[6:])

# Initialize
init = mcp_call("initialize", {
    "protocolVersion": "2024-11-05",
    "capabilities": {},
    "clientInfo": {"name": "negotiatorgrid", "version": "0.1"}
})
print(f"Connected to: {init['result']['serverInfo']['name']} v{init['result']['serverInfo']['version']}")

# List tools
tools = mcp_call("tools/list", {}, id=2)
for tool in tools['result']['tools']:
    print(f"  {tool['name']}: {tool['description'][:80]}...")

# Call a tool
result = mcp_call("tools/call", {
    "name": "get_service_details",
    "arguments": {"service_id": "agent_LpzYVzWGzjGiZBI3HTm4ZCKj"}
}, id=3)
print(result)
```

## 5. x402 Payment Handling — How Much Does MCP Automate?

### The Answer: MCP Handles Authorization, NOT the Full Handshake

The MCP server is a **payment authorization tool**, not an end-to-end payment middleware. Here's what each layer handles:

```
┌─────────────────────────────────────────────────────┐
│                    YOUR AGENT CODE                    │
│                                                       │
│  1. Call service → receive HTTP 402                   │  ← You implement this
│  2. Parse 402 response (payee_addr, amount, token)    │  ← You implement this
│  3. Call MCP: get_payer_addr()                        │  ← MCP handles this
│  4. Call MCP: approve_payment(payer, payee, amount)   │  ← MCP handles this
│  5. Receive signed X-Payment header                   │  ← MCP returns this
│  6. Retry request with X-Payment header               │  ← You implement this
│  7. Service verifies + settles via facilitator         │  ← Service side handles
│  8. Receive service response                          │  ← You consume this
└─────────────────────────────────────────────────────┘
```

### What MCP automates:
- ✅ Wallet address resolution (`get_payer_addr`)
- ✅ Payment signing within session budget constraints (`approve_payment`)
- ✅ Session budget enforcement (rejects if over budget)
- ✅ On-chain authorization signature creation (AA wallet signs)

### What YOU still implement:
- ❌ The initial service call that receives HTTP 402
- ❌ Parsing the 402 response body to extract `payee_addr`, `amount`, `token_type`
- ❌ Calling the MCP tools with extracted payment info
- ❌ Base64-encoding the X-Payment header
- ❌ Retrying the service call with the payment header
- ❌ Error handling (session expired, insufficient budget, etc.)

### Complete Payment Flow (from Developer Guide) [Source 1]

```javascript
async function callX402Service(serviceUrl, requestData) {
  // 1. Call service (may return 402 Payment Required)
  let response = await fetch(serviceUrl, {
    method: 'POST',
    body: JSON.stringify(requestData)
  });

  // 2. Handle 402 response
  if (response.status === 402) {
    const paymentInfo = await response.json();
    
    // 3. Get payer address via MCP
    const payer = await mcpClient.callTool('get_payer_addr', {});
    
    // 4. Approve payment via MCP
    const auth = await mcpClient.callTool('approve_payment', {
      payer_addr: payer.payer_addr,
      payee_addr: paymentInfo.payee_addr,
      amount: paymentInfo.amount,
      token_type: paymentInfo.token_type
    });

    // 5. Retry with payment header
    response = await fetch(serviceUrl, {
      method: 'POST',
      headers: { 'X-Payment': auth.x_payment },
      body: JSON.stringify(requestData)
    });
  }

  return await response.json();
}
```

### Implication for NegotiatorGrid

NegotiatorGrid's payment flow becomes:

1. **Negotiation phase** (NegotiatorGrid logic): Two agents exchange offers, converge on price P
2. **Commitment phase** (MCP): Buyer calls `approve_payment(amount=P, payee=seller_addr)` → gets signed X-Payment
3. **Execution phase** (x402): Buyer sends request to seller's service with `X-Payment` header
4. **Settlement phase** (facilitator): Seller's service calls facilitator `/v2/settle` to execute on-chain transfer

**NegotiatorGrid only needs to insert the negotiation loop between steps 1 and 2. The payment infrastructure is already built.**

## 6. Can NegotiatorGrid Register Negotiation Endpoints as MCP Tools?

### Short Answer: Not Directly on Kite's Server, but YES via Your Own MCP Server

Kite's MCP server is a **hosted, closed server** that exposes Kite's own tools. You cannot add custom tools to it. However, MCP is designed for multi-server composition:

### Option A: Run Your Own MCP Server Alongside Kite's

NegotiatorGrid registers its own MCP server that exposes negotiation tools:

```json
{
  "mcpServers": {
    "kite-passport": {
      "url": "https://mcp.prod.gokite.ai/api_key_XXX/mcp"
    },
    "negotiatorgrid": {
      "url": "https://your-negotiatorgrid-server.com/mcp"
    }
  }
}
```

Your MCP server would expose:

| Tool | Description |
|------|------------|
| `start_negotiation` | Initiate price negotiation with a counterparty agent |
| `submit_offer` | Submit a price offer to the counterparty |
| `accept_deal` | Accept the current offer and commit to purchase |
| `reject_deal` | Reject and counter-offer |
| `get_negotiation_status` | Check current negotiation state |
| `list_negotiable_services` | Discover services that support price negotiation |

An AI agent (Claude, Cursor) would then have access to BOTH Kite payment tools AND NegotiatorGrid negotiation tools simultaneously.

### Option B: x402-Style Negotiation Service (The "Wow Moment")

Register NegotiatorGrid as a **service on the Kite App Store** that returns HTTP 402 with negotiable terms:

```json
// NegotiatorGrid service returns a modified 402 with negotiation offer
{
  "error": "Negotiation required before payment",
  "accepts": [{
    "scheme": "gokite-aa",
    "network": "kite-testnet",
    "maxAmountRequired": "5000000000000000000",  // ceiling price
    "minAmountAccepted": "1000000000000000000",  // floor price
    "negotiation_endpoint": "https://negotiatorgrid.example.com/negotiate",
    "negotiation_protocol": "negotiatorgrid-v1",
    "payTo": "0xSellerAddress",
    "asset": "0x0fF5393387ad2f9f691FD6Fd28e07E3969e27e63",
    "merchantName": "NegotiatorGrid Demo Service"
  }],
  "x402Version": 1
}
```

The buyer agent would:
1. Detect the `negotiation_endpoint` field (NegotiatorGrid extension to x402)
2. Run the negotiation protocol
3. Arrive at price P
4. Use Kite MCP `approve_payment(amount=P)` to authorize
5. Retry with `X-Payment` header at the negotiated price

### Option C: A2A + MCP Hybrid (Recommended for Hackathon)

From the Agent Builder Guide [Source 5]:
- Register NegotiatorGrid agents via `POST /v1/agents/register` with A2A Agent Cards
- Expose negotiation as an A2A skill
- Other agents discover NegotiatorGrid via `GET /v1/agents/search?tag=negotiation`
- Negotiation happens over A2A protocol
- Payment settlement uses Kite MCP tools

This is the cleanest architecture because it uses Kite's existing discovery + payment rails and only adds the negotiation logic layer.
