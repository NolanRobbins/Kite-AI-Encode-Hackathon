### How Negotiation Works (Critical for NegotiatorGrid)
From the transcript at [3:24]:
> "The task requires Hedera schedule transaction plus market analysis. So it requests 5 HBAR for the additional complexity. The counter offer is submitted — 5 HBAR for DCA. And the commerce agent accepts the 5 HBAR counter offer."

From the README task lifecycle:
```
create_task → negotiate_task → accept_offer → submit_work → review_work
     ↓              ↓               ↓              ↓              ↓
  Commerce      DeFi proposes    Commerce        DeFi          Commerce
  posts task    different price  accepts         submits audit  rates 5/5
```

**Assessment:** This is a **single-round counter-offer** — one propose, one accept. The "negotiation" is:
1. Commerce agent posts task
2. DeFi agent proposes a price (5 HBAR) based on complexity
3. Commerce agent accepts

There is no:
- Multi-round back-and-forth
- Concession curves or strategy adaptation
- BATNA reasoning (what if the offer is rejected?)
- Opponent modeling (learning from past interactions)
- Rejection + re-proposal cycles
- Game-theoretic equilibrium seeking

**This is the single biggest gap NegotiatorGrid fills.** Agentic Markets calls it "negotiation" but it's really "proposal + acceptance."

### Kite Primitives Used
- **x402 (gokite-aa scheme):** Payment-gated agent discovery. Agent hits `/api/kite/discover` → gets 402 → constructs payment → retries with `X-PAYMENT` header → Pieverse facilitator verifies → resource delivered. Custom `gokite-aa` scheme (not standard `exact`).
- **Kite Passport:** Three-tier identity (User DID → Agent DID via BIP-32 → Session keys with 60s TTL). Standing Intents → Delegation Tokens → Session Signatures.
- **Kite Reputation:** Multi-dimensional (reliability, quality, speed, communication) tied to Passport DID.
- **MCP Tools (3):** `kite_discover_agents`, `kite_check_reputation`, `kite_hire_agent`

### What Made It Stand Out
1. **Sheer breadth** — 4 chains, 57 MCP tools, real transactions on all of them
2. **Live on-chain proof** — real tx hashes on Hedera explorer during demo
3. **Telegram notifications** — real-time alerts when HSS swaps execute
4. **Kite Passport implementation** — most detailed identity integration
5. **README as product** — the documentation is a submission artifact itself

**Repo:** No public GitHub repo found (Team Run Rhyno, ETHDenver 2026)

### Demo Format
- **Type:** Live web UI demo — query submitted, results rendered in real-time
- **Flow:** User submits query ("SEC vs Ripple") → waits ~3 min → sees verified/contradicted/inconclusive claims with prize pool breakdown
- **Duration:** ~4:23 video, slower pace with explanation during processing wait

- VeriScore agent + Classifier agent run as backend processes

### Reproducibility: Unknown — no public code

### How VeriScore Verification Works
From the transcript:
1. User submits a query to 3 LLM agents (OpenAI, Gemini, Claude)
2. Each agent **stakes tokens** on their response via Kite Escrow
3. VeriScore agent verifies each claim as: **supported**, **contradicted**, or **inconclusive** (~1-1.5 min)
4. Classifier agent sorts claims into **majority** (consensus) vs **minority** (novel) (~1 min)
5. Agent with the most novel + verified claims wins the prize pool
6. Total pipeline: ~3 minutes

**Escrow pattern:**
- LLM agents stake before responding (skin in the game)
- VeriScore agent also gets a stake cut for verification work
- Winner: highest % of novel claims that verified as correct
- In demo: OpenAI won with 43% precision on novel claims; Claude 4 had 4 contradictory claims

### Kite Primitives Used
- **Kite Escrow:** Token staking/reward mechanism for incentivizing quality responses
- **VeriScore:** Verification layer (unclear if this is a Kite primitive or their own — likely built on top of Kite)
- That's it — no x402, no ERC-8004, no MCP

### What Made It Stand Out
1. **Novel concept** — LLM fact-checking as a competitive market (agents stake on accuracy)
2. **Clean framing** — "minority report" metaphor resonates instantly
3. **Live processing** — watching the pipeline work in real-time during demo
4. **Practical utility** — solves a real problem (LLM hallucination detection)

### What NegotiatorGrid Does That They Didn't
- No agent commerce or pricing mechanism
- No x402, no MCP, no ERC-8004 — minimal Kite integration
- No multi-agent economic interaction — agents cooperate, don't negotiate
- Single-use query tool, not a reusable protocol

### Steal-Worthy Patterns
| Pattern | What They Did | How NegotiatorGrid Adapts |
|---------|--------------|--------------------------|
| Staking mechanism | Agents put skin in the game before acting | Require negotiation deposits before entering bilateral negotiation |
| Real-time pipeline visibility | Users watch processing stages complete | Show negotiation rounds progressing in real-time UI |
| Novel vs. majority framing | Clear binary that judges understand instantly | Frame "fixed pricing" vs "negotiated pricing" as our binary |
| 3-minute end-to-end | Kept demo tight and completable live | Aim for <2 min full negotiation cycle in demo |

### Reusable Escrow Pattern?
The Kite Escrow staking pattern is interesting but different from what NegotiatorGrid needs. They use escrow for **quality incentives** (stake → verify → reward best). We need escrow for **deal settlement** (negotiate → agree → release payment). The mechanics differ:

- Minority Report: Escrow holds stakes from all participants, releases to winner based on verification
- NegotiatorGrid: Escrow holds buyer payment, releases to seller when negotiated terms are met

We can cite their staking concept but implement our own escrow logic around negotiation agreement.

### How ERC-8004 Identity Works
Three-layer identity architecture:

| Layer | Identity | Role |
|-------|----------|------|
| Human EOA wallet | User identity | Full ownership — sets the rules |
| AA wallet | Agent identity | Constrained execution within human-defined boundaries |
| Session key | Session identity | Fine-grained per-task scope: budget cap, time window, tx range, platform restrictions |

**Implementation details from repo:**
- Contracts: `IdentityRegistryV1` at `0x60BF18964FCB1B2E987732B0477E51594B3659B1`
- CLI: `npm run erc8004:deploy`, `npm run erc8004:register`, `npm run erc8004:read`
- Manifest: `agent.json` — ERC-8004 manifest with contract addresses, capability declarations, MCP surfaces
- Execution log: `agent_log.json` — full lifecycle runs with real tx hashes
- Public API: `GET /.well-known/agent.json` — standards-compliant agent manifest endpoint

**Key design principle:** Pre-emptive prevention (spending constraints at crypto level) + post-hoc accountability (on-chain receipts). Agents can make autonomous payments but are cryptographically constrained to human-defined boundaries.

### Kite Primitives Used (Deepest of Any Project)
- **ERC-8004:** On-chain agent identity with trust publication anchors. Deployed contracts, CLI tools, manifest endpoint.
- **ERC-8183:** Open job escrow — publish, claim, execute, validate, settle. `JobEscrowV4` at `0x95260b27c509Bf624B33702C09CdD37098a6967D`.
- **x402:** Pay-per-call micropayment settlement via AA session keys. Receipt surface at `GET /api/receipt/:requestId`.
- **MCP:** Tool surfaces for Claude and any MCP-compatible client. POST `/mcp`, `/mcp/stream`, `/mcp/connect/:token`.
- **On-chain anchors:** `TrustPublicationAnchorV1`, `JobLifecycleAnchorV2` — tamper-evident receipts for every execution step.
- **Testnet USDT:** `0x0fF5393387ad2f9f691FD6Fd28e07E3969e27e63`

### What Made It Stand Out
1. **Deepest Kite integration** — uses more Kite primitives than any other project
2. **"Proof surfaces" concept** — explicitly guides judges to verifiable evidence
3. **Multi-agent collaboration** — 3-agent workflow (Requester → Executor → Validator) with no human involvement
4. **Live deployment** — kiteclaw.duckdns.org with public APIs
5. **Hourly automated runs** — the system runs hourly news briefs autonomously, building a track record
6. **CLI tooling** — `npm run ktrace` CLI for all operations
7. **Bilingual docs** — English + Chinese README

### What NegotiatorGrid Does That They Didn't
- **No negotiation** — Kite Trace uses ERC-8183 bounty model: requester posts price, worker claims or doesn't. No price discovery.
- **No opponent modeling** — agents don't learn from each other's behavior
- **No strategy adaptation** — capabilities are priced statically
- **No bilateral interaction** — their model is "publish → claim" (one-sided), not "propose → counter → concede → agree" (bilateral)
- **No game theory** — no BATNA reasoning, no Nash equilibrium seeking, no concession curves
